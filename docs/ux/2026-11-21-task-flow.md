# 讓日常任務有一致的開始、處理狀態與結果

本輪從 `main 27ad30c0a098908b2161950303fcf9209764a083` 開始，接續既有的五區導覽、共用表單與原生對話框。範圍為 Web 的教師今天、課表重試、附件核對、社群表單、匯入撤銷確認和共同頁面結構。

## 決策依據

產品已經有足夠多的入口與功能。這一輪優先處理使用者做完一項任務時，能否辨認目前狀態、知道資料是否保留，並順利完成下一步。

| 觀察到的問題                                   | 使用者承擔的後果                           | 修正                                                         |
| ---------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| 教師課表載入、讀取失敗與真正沒有課共用空白提示 | 把無法確認的安排理解成沒有課               | 五種課表狀態分開顯示，各有對應入口或重試                     |
| 教師頁以學生的個人待辦推導學生作業期限         | 沒有讀取教師期限，卻顯示沒有即將到期的作業 | 首頁只呈現已確認的授課課程，進入課程工作台查繳交、批改和教材 |

| 今天首頁自建外框，漏掉其他頁面的系統提示       | 在最常用頁面看不到離線與新版本             | 抽出 AppFrame，首頁與 SiteShell 共用；提示字體採既有文字偏好 |

課表重試另外修正了共用資料 hook：重新讀取會同時涵蓋匯入紀錄與手動課表，讓儲存區恢復可讀後的重試真正有效。

撤銷整批匯入也改為共用 ConfirmModal，保留原本的刪除說明、取消優先、帳號／校園檢查與寫入鎖。操作完成前留在確認視窗；身份重驗時明確隱藏 portal，避免視窗繞過原有的暫停工作區。

## 互動原則

- 一個畫面說清楚目前狀態。載入中、無資料、未設定與失敗有不同意義，不能共用「沒有」的結論。
- 先保留使用者已填內容，再說明復原方法。失敗不清空表單，不把無法確認的伺服器結果宣稱為已成功。
- 長時間等待時允許先離開視窗。等待時間經過不代表寫入已取消；原請求尚未確認時不開放第二次送出，重開仍接續同一筆操作。
- 相同互動採相同元件。這次沿用已有的原生對話框、欄位和按鈕，讓真正的業務操作也具備相同的焦點、觸控區域與動態偏好。
- 以當下帳號、校別和開啟期間約束非同步結果，避免舊操作干擾新的工作。
- 動態效果用來表達開啟、關閉和處理狀態；沿用既有短轉場及減少動態支援。

## 架構與資料邊界

`AppFrame` 負責跳到主要內容、離線提示、頁首、版本與安裝提示，以及唯一的 main。`SiteShell` 保留服務頁的標題、麵包屑、課務導覽和頁尾；今天首頁保留自己的助理入口、內容錨點與版型。

教師首頁仍使用原有的課程來源和個人課表。此頁沒有新增教師待批改統計 API，因此不宣稱已取得待批改數量或學生作業期限。

`useCommunityFormSession` 限定每次表單開啟只能有一個進行中的寫入。離開帳號、校園或貼文後，已卸載表單的回應不能呼叫新表單的成功回呼。這是介面送出互斥與回應生命週期控制，不代表後端具備跨裝置的冪等寫入。

Firestore 的離線寫入可能持續等待確認。表單等待 15 秒後提供「先關閉」，父層保留同一個帳號／校園／貼文範圍內的表單與寫入；重新開啟仍顯示原內容及處理狀態。只有原請求實際確認成功或拒絕後才解除送出鎖。等待時間經過不被當成失敗，也不會產生一筆新的寫入。

附件分類仍使用既有 `classifyAssignmentFile` 與原有照片、文件上限。伺服器的權限、內容魔術位元組驗證、繳交協定和儲存來源不變。選取成功只代表附件已加入本次草稿，不等於作業已繳交。

## 驗收

- 元件與整合測試驗證課表各狀態、真實校別地圖入口、部分來源保留、獨立重試、附件混合接受／拒絕、配額釋放、取消選檔、表單單次送出與卸載後晚到回應。
- 原有作業整體流程繼續驗證照片預覽、實際呼叫上傳邊界與遲交回條。
- 社群驗證欄位標籤、原生星等、搜尋清除、處理中取消與重複送出、失敗保留草稿、跨帳號／校園／貼文隔離。
- 以持續等待的合成寫入及可控制時鐘，驗證長時間等待後先關閉、重開接續原內容、禁止第二筆寫入，以及原請求完成後的復原。
- 新瀏覽器驗收載入真正產品元件與 CSS，只替換明確標示的帳號、路由及網路資料邊界，使用合成資料而不操作正式帳號。
- 瀏覽器覆蓋桌機、手機深色、320px 與 200% 文字，以及減少動態；確認原生模態狀態、鍵盤背景隔離、Esc 焦點返回、長圖捲動與可操作的表單。
- 每次瀏覽器驗收產生截圖、JSON 結果及來源 SHA-256。精確提交的測試結果以 PR 與 Actions 產物為準。

## 後續產品方向

以下為後續建議，沒有在本輪宣稱完成。

### 1. 讓「我的工作」直接列出真實待辦

目前 `AccountWorkspaces` 的教學區列出授課課程，教師的請假核閱、申訴與批改仍分散在不同入口。下一輪應依已確認的責任與權限彙整具體工作，讓教師直接開啟待批改繳交、請假或申訴；多重身分者仍能辨認該工作屬於哪個課程、校園或門市。管理員既有的實際案件佇列可提供共同模式。

完成標準是「從首頁開啟一筆真實工作、完成處理、返回原清單並看到已確認結果」。需要接上真實工作資料；課程數量不能代替待辦數量，讀取失敗也不能顯示零件。

### 2. 以課程為中心串起課務

主要導覽的「課務」目前開啟 `/timetable`，教材與作業位於 `/classroom`。已連結課班的項目能銜接，但未連結項目從「今天」回課表，從課表的「作業與教材」則進課程搜尋。下一輪應以課程總覽串起本週安排、教材、作業、測驗與批改，並把匯入中心既有的明確課班連結帶到日常入口。

完成標準是「今天的課程 → 教材或作業 → 完成回條 → 返回今天」一路保留同一課程與校別。相似課名不能直接視為同一課班；需要使用者確認既有授權課班連結。

### 3. 讓工作位置可以重新開啟，先補門市

`AccountIdentity` 的各門市入口都指向 `/merchant/workspace`；`MerchantWorkspace` 選定的門市仍保存在元件 state，重新整理後需再選。下一輪應為具體門市與案件提供穩定網址，沿用管理員工作區的路由狀態及服務目錄的返回位置模式。

完成標準是「點進指定門市、重新整理仍在同一位置、處理後回到原篩選與焦點」。網址只描述位置；重新開啟仍由目前帳號確認權限，舊帳號的內容與未確認結果不得進入新帳號畫面。

這三項完成後，再用登入後真實帳號、Safari 和 iOS／Android 裝置驗證主要任務與發布條件。

## 設計與行為參考

- [Apple Human Interface Guidelines — Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback)：狀態與結果放在適當位置，讓使用者理解發生什麼事與下一步。
- [Apple Human Interface Guidelines — Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)：一致操作、可調文字、鍵盤與多種感知方式。
- [Apple Human Interface Guidelines — Motion](https://developer.apple.com/design/human-interface-guidelines/motion)：動態有用途、簡短、可減少，且不阻礙操作。
- [Apple Human Interface Guidelines — Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)：主要分區可預期並保留導覽狀態。
- [Firebase JavaScript API reference — Firestore](https://firebase.google.com/docs/reference/js/firestore)：`addDoc`、`updateDoc` 需要遠端確認才會完成，離線寫入可能長時間等待；等待時間經過不能當作取消或拒絕。
