# 個人行程 Agent：實際執行、讀回核對與失敗復原

## 本輪的完成定義

助理只有在正確帳號與校園的個人行程資料中，重新讀到與使用者確認內容完全相符的事件，才能宣告「已核對並加入個人行事曆」。HTTP 200、模型文字、工具呼叫成功與單一 `confirmed: true` 都不構成完成證據。

這個成果代表行程已保存。它不代表作業已完成或繳交，也不代表推播已排程。點餐頁交接保留為服務入口，不當成訂單已送出或付款完成。

本輪延續 `2026-11-07-service-connections.md` 的服務目錄與個人成績讀取；沒有把 41 個入口宣稱為 41 種可直接執行的交易。

## 可操作的兩條流程

| 使用情境 | 實際流程 | 儲存位置與完成證據 |
| --- | --- | --- |
| Web：幫我排今晚寫作業 | 現有 V2 讀待交事項與已同步課表／事件，提出具體時段；使用者確認後按順序執行多張卡 | 原有平台 personal-imports ledger；重新讀回相同事件後回傳單筆收據，再合入目前 owner 的本機行事曆 |
| 手機：幫我明天 19:00 到 20:00 安排英文讀書 | 本機辨識單一明確行程，顯示日期、起訖時間與名稱；使用者確認後寫入並讀回 | 目前平台或校園帳號、目前學校的既有裝置 personal-import ledger；回執可開啟 `PersonalCalendar(eventId)` |

手機流程不需要模型理解或下載模型。它的範圍是明確建立單一個人行程，不會猜缺少的時間、推估作業截止日，或把複合請求中的提交／付款／通知當成行程名稱。原有較廣泛的課業規劃依舊保持來源與資料涵蓋範圍。

Web 保留現有模型、資料與寫入開關；沒有替開發者開啟正式環境寫入。手機只保存目前裝置的個人行程，不會順便啟用整份個人資料同步。

## 共同的收據契約

`packages/shared/src/assistantExecution.ts` 定義並驗證以下資訊：

- `version: 1`、`operation: calendar.create`、狀態與儲存來源。
- 與原確認相同的 `schoolId`、`mutationId`、事件 ID／批次 ID。
- 精確標題、日期、起訖時間、全天／跨日設定及選填地點。
- 核對時間、是否重複查核，以及帳號儲存來源必備的 revision。
- 僅包含已核對的單筆事件；不接受額外成績欄位、原始匯入文字、getter 或其他隱藏資料。

驗證器只驗證格式與一致性，不能自行證明真的執行。因此收據只能由儲存層讀回結果後產生，前端再以原確認卡核對一次。

## Web 執行生命週期

1. 送出前先檢查目前 owner 的本機資料能否讀取、是否有未核對的同步、容量，以及與個人行程的重複／時間重疊。這是預檢，不代表預約時段；伺服器仍需重新核對。
2. 原有簽章、帳號、session、對話、校園、參數摘要、五分鐘期限、版本與前一步依賴檢查保留。
3. 使用同一個 mutation ID 寫入既有資料層，之後重新讀 ledger，核對完整預期事件。
4. 將收據中的事件合入本機同一 owner／school；不覆蓋被使用者修改或刪除的同 ID 紀錄，不新增另一筆相同語意的事件。
5. 逐項顯示已核對、未完成、待核對與已停止的提議；有不明結果就停止後面的寫入。
6. 後續對話的記憶由這些狀態產生，包含整批完成數與不明數。token、事件 ID、原始匯入資料不進入這段完成摘要。

### 斷線與重新核對

新增 `POST /api/nuni/assistant/reconcile`。它仍要求目前有效 session、same-origin、正確帳號／對話／學校綁定，以及原 token 的 HMAC 與參數摘要。只讀核對可接受過期、被新提議取代或舊 process 發出的合法卡片；這不會重新授予寫入權限，也不依賴存活的舊 Fly machine。

確認回應遺失時，Web 自動做一次唯讀查核；讀到相符事件可繼續原批次。仍無法核對時保留原操作，提供「重新核對結果」，不產生新 ID 重送。查不到事件只表示查詢當時未讀到；只有伺服器明確允許時，才提供原 token、原 ID 的重試。

已成功的回執不會被下一次網路查核失敗抹掉。畫面保留上次核對時間及結果，另提示最新查核未完成；只有實際讀到缺失或不同內容，才更新目前的紀錄狀態。

### 同分頁重新整理與返回

Web 在送出確認／撤銷前，先將原行程卡與 conversation ID 存入同分頁 `sessionStorage`，依平台 owner、學校及登入 context 精確隔離。待核對清單最多 16 項／64 KB，不含整段對話、學業資料、模型同意狀態或 sessionHandle。

重新整理或離開後返回同分頁時，從原卡執行唯讀查核。只有事件已核對且本機可見，或明確撤銷未執行提議後，才移除待核對紀錄。儲存損壞、空間不足或清單已滿時不覆寫舊紀錄，也不送出新的無法追蹤操作。

這項恢復以同分頁、同一有效登入 context 為範圍；不宣稱能跨分頁關閉、清除網站資料、重新登入或更換帳號恢復舊寫入授權。

每次操作查核有獨立的 15 秒 client deadline，不會為了停止一個卡住的請求而撤銷整個對話。自動恢復遇到第一個無法核對的連線結果就暫停，保留其餘卡片供後續查核，讓本機服務入口仍可使用。

### 撤銷與部分成功

撤銷只針對未執行提議。取消與確認在同一操作鎖內處理；已派送但結果不明的寫入不能被描述成已撤回。若取消時讀到已建立的相符事件，回傳 verified 收據。

批次取消每成功一項就立即保存狀態。再次查核或接續取消不會卡在前面已撤銷的項目。已建立行程的編輯或刪除仍使用行事曆既有流程。

### 本機顯示失敗

若帳號中的寫入已核對，但裝置空間、同步 pending 或本機衝突阻止顯示，UI 保留「帳號中已儲存」的證據，說明此裝置尚未更新。重試先查核原結果，不能再建立另一筆行程。

行事曆的 `eventId` 入口只在目前 owner／school 的真實本機紀錄中尋找事件，再切換日期、月份與列表並定位；不從網址採信事件內容。找不到時顯示明確狀態，不換帳號搜尋。

## 單筆核對與既有同步

只把遠端新事件 append 到本機而不記錄來源，之後遠端刪除該事件時，三方同步可能將它誤認成尚未上傳的新事件，重新建立它。

因此同步狀態增加可選的 `acknowledged` 單筆證據，記錄事件與讀回 revision。它不是完整遠端 snapshot，不會偽造或替換 `base`。

- 本機鏡射維持 `enabled`、完整 base 與原 pending payload 的語意；存在未核對 pending 時先阻止新增鏡射。
- 同步只在遠端版本足夠新時，將單筆證據用於該 ID 的三方合併基準。
- 遠端刪除與本機未改動可正確合併為刪除；雙邊不同修改保留為衝突供核對。
- pending 重送內容保持不變，未被完整 base 涵蓋的單筆證據不提前丟棄。
- 取得並保存完整成功 snapshot 後，可清除已涵蓋的單筆證據。

## 手機的執行限制

操作 ID 在顯示草稿前固定，確認時使用既有序列鎖、帳號與校園 scope guard。已嘗試的操作只做原 ID 查核，無法確認時不再建立新事件。讀回時除了事件內容，也核對原建立時間與來源。

確認卡由訊息資料控制，執行結果不只存在卡片自己的暫時 state；下一則對話後仍可查看及查核。切換帳號／session／校園後的晚到結果不能寫入或顯示在新範圍。

手機回執與待核對操作目前保留在本次對話生命週期，未新增跨 app 重啟的任務 journal。已建立的事件本身保存在既有個人行事曆，可直接查看；不以這個事實宣稱已完成跨重啟的任務恢復。

## 驗收與界線

回歸涵蓋：沒有確認不寫入；回應格式與範圍錯誤不能顯示成功；寫入成功但回應遺失可恢復；同 ID 不重複；批次部分成功保留；撤銷不假稱刪除；本機保存失敗可重新核對；跨帳號／學校晚到結果隔離；同步刪除不復活；個人行事曆能定位真實事件。

CI 執行 shared receipt 與單筆 acknowledgement 契約，以及 Web 全套測試、手機 focused Agent suites 和既有型別／建置檢查。這些是受控回歸證據；不等於正式環境使用者任務完成率，也不等於已實測領先競品。

本輪不新增另一套 saved-plan 儲存：PR #523 的計畫保存／個人勾選與本輪實際事件寫入證據是不同資料。既有其他業務寫入與正式環境部署，仍需各自的授權、資料來源和必要合併閘門。
