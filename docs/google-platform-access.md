# Google 帳號與校園服務入口

更新：2026-11-07（Asia/Taipei）
基準：`4357441c686a1ce4b4bf493f7b51dcc4c4850ebb`
後續整合：main `d1555303423d5e57da47048a2695fb22ef11a1b1`

## 問題與決定

一般平台功能不應因學號登入尚未開放而無法使用。Google 平台登入、個人裝置資料、學校帳號與課班／工作角色是不同的授權來源。

主線有兩個實際斷點：

1. `/social` 把使用者導向僅認 Firebase 校園身分的 `/community`，但既有 `SocialWorkspace` 與 `/api/social` 已支援 Nuni Google 平台帳號。
2. OAuth 的安全返回清單漏掉已支援平台帳號或本機個人資料的路徑。登入頁又用這張清單判斷是否需要學校帳號，導致 Google 按鈕被隱藏，或成功登入後回到無關的課程頁。

這次恢復既有功能入口，不建立 Google→Firebase 身分橋接，不建立學校 member，不修改資料庫或 Firestore 權限。

## 網頁服務邊界

| 服務 | 入口 | 帳號與資料邊界 |
| --- | --- | --- |
| 公開校園資訊 | 地圖、公車、公開公告、活動、餐廳目錄、圖書館入口 | 可先以訪客瀏覽；來源與供應依各校而定 |
| 地圖收藏 | `/map` | Google-only 可在目前瀏覽器保存，依平台帳號／校園隔離；已連線學校帳號沿用原有雲端收藏 |
| 個人課表與行程 | `/timetable`、`/calendar` | 可自行新增／匯入；平台、學校與訪客的本機資料依既有 scope 隔離 |
| 資料匯入 | `/import` | 不需學校密碼；平台雲端同步依部署能力與使用者啟用狀態提供 |
| 個人住宿備忘 | `/dormitory` | 本機紀錄依帳號／校園隔離；不是校方正式申請或報修受理 |
| 公開交流 | `/social` | Google 平台 session；只讀取後端允許的公開貼文，發表資格由後端決定 |
| 平台課班 | `/classroom` 與既有課程頁 | Google 平台帳號，再檢查課班成員／邀請資格 |
| 課程回饋 | `/grades` 預設、`/classroom/grades` | 平台課班公布的回饋；不是校方學期成績 |
| 教材收藏 | `/classroom/material-bookmarks` | 只查看本人可存取的課班教材 |
| 餐飲服務 | `/food` | 平台帳號自己的訂單與取餐資訊；下單仍受既有點餐開關與店家狀態限制 |
| 舊店家根入口 | `/shops`、手機 `campus://shops` | 導回平台餐飲，不要求學校帳號；校園瀏覽參數不當成餐飲租戶或操作權限 |
| 店家申請與工作區 | `/merchant` 等既有入口 | Google 可登入／申請；審核與門市操作權限另外檢查 |
| 校方學期成績 | `/grades?tab=semester` | 保留學校驗證與官方來源限制 |
| 校內社群、限動與舊服務 | `/community` 等 | 保留原有身分／成員限制，提供公開交流替代入口，不掛載未授權的讀取元件 |

`GradesPage` 僅在第一個 `tab` 值為 `semester` 時顯示校方紀錄；其他值都進平台課程回饋。返回清單與頁面使用相同判斷，並測試重複 query 參數。

## 登入體驗

一般登入先顯示 Google，學校帳號區預設收合。即使學校登入選項讀取失敗，也不能封鎖獨立的 Google 入口。只有明確學校任務或 `reconnect=school` 才自動展開學校連線。

手機登入首頁也先顯示 Google 帳號入口，再顯示選校與校務資料匯入。未選校、尚未登入或已有 Google session 時，都可進入既有的 `NuniWorkspace`；進入工作區不會自動登入學校、發出校務請求或改寫既有 session。學校私人資料、已驗證學生服務與店家管理仍各自檢查資格。

OAuth 開始與回呼均重跑同一份內部返回網址檢查，保留核可任務的 query／hash，不接受外站、登入循環或未列出的子路徑。

`/community` 沒有校園帳號、校園帳號讀取失敗，或尚未選校時，都能找到公開交流入口。導向 `/social` 時只攜帶校園範圍，不把原校內貼文編號、帳號參數或 token 當成公開社群權限。

## Google 地圖收藏

Google-only 使用者可以收藏、取消收藏、只看收藏，以及確認後清除此裝置的本校收藏。資料存於目前瀏覽器，不承諾跨裝置同步，也不複製學校帳號的雲端收藏。

每個地點各自存一筆，以已確認的 `platformAccountId` 與校園構成獨立 namespace；新增地點不覆寫同範圍的其他收藏，不需要 Web Locks 才能操作。讀取會驗證版本、範圍、地點 ID、大小與數量，更新後回讀確認；儲存拒絕、資料損壞或不確定結果都不顯示成功。損壞資料只在使用者明確確認清除後才移除。

Google 帳號、session context、校園切換或進入登入復原／登出中狀態時，立即換掉畫面 scope；舊讀取與寫入完成後不套用到新帳號。跨分頁只重新讀取本帳號、本校園的 namespace，不採信 storage event 裡的資料內容。若同時有有效學校帳號，維持既有學校雲端收藏，畫面說明目前來源。

## 舊餐飲連結

Web `/shops` 只保留既有 `school`、`schoolId`、`campus` 瀏覽資訊後轉到 `/food`，餐飲頁登入後仍帶回這些資訊。`tenant + order` 沿用餐飲頁原先的格式驗證與回跳條件；不把學校代碼推定為餐飲 tenant。Google 安全返回清單只增加 `/shops` 與 `/shops/`，未開放任意子路徑。

手機 `shops` 根深鏈導向 `NuniWorkspace` 的 food 分頁，保留單一且格式合法的校園提示；不接受 tab、角色、帳號、憑證或任意回跳參數。錯誤百分比編碼不造成原生導航例外。舊 vendor／detail 子路徑沒有對應頁面，因此不會假裝已開啟特定店家或訂單。

## 後續需要真正遷移的服務

失物招領、好友、私人訊息、部分舊校園收藏目前仍依賴另一套帳號。它們不應永久被學號綁住，但需要以平台 principal、物件擁有者與原可見範圍逐項接通。

不能直接把任意 Google 帳號塞進舊學校登入流程：`writeSchoolLoginProfile` 會建立學校成員；舊角色預設與 Firebase／Nuni 的獨立登出生命週期也需要處理。這些問題不應以放寬 UI guard 或資料庫規則掩蓋。

### 失物招領的下一步

現有失物 Firestore 規則主要檢查「已登入」與本人 `userId`，並不是每次都要求學校會員；實際限制來自兩端使用 Firebase SDK／UID，而 Google 是另一套平台 session。目前沒有可直接接通的 Nuni 失物 CRUD。下一輪遷移應完成一個含列表、本人刊登／編輯／結案／下架的完整 API，並同時處理：

- 伺服器透過 live platform session 決定 owner，不接受 body 自填帳號；不授予學籍或發出 Firebase 登入 token。
- 新舊資料與聯絡資訊可見範圍；不得依 email 或 displayName 自動認領歷史紀錄。
- 穩定刊登編號、冪等重試、版本衝突與帳號／校園切換時的草稿及結果隔離。
- 平台帳號關閉時的下架與聯絡方式清理。現有 Nuni 帳號關閉只處理平台資料庫／session，不會自動清理新增的 Firestore store。
- 手機公開導航入口、發文額度、真實資料庫回歸與正式伺服器所需的 Admin 設定。

本輪未建立這個新資料集，也未把失物招領或私人訊息標記成已支援 Google。

## 驗證與發布

回歸涵蓋 Google-only 公開交流、未登入不發出公開社群請求、校內讀取未掛載、回跳原任務、校園範圍保留、個人資料帳號隔離、OAuth 同源／state／端點限制與真正校務頁面仍要求學校身分。

測試使用模擬 session／API；不代表正式 Google OAuth、真實帳號、實機畫面或生產發布已驗收。完整結果與精確提交請見本輪 PR。

main 必須經 PR 與指定 GitHub App 的「審查通過」檢查。既有 #511、#519 也修改登入／首次選校流程；整合時需保留兩套身分與明確校園範圍，並在合併後重跑對應回歸。
