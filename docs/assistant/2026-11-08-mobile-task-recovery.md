# 手機行程任務：跨畫面與 App 重啟恢復

## 交付範圍

延續 `2026-11-07-verified-execution.md` 的明確行程確認流程，新增手機端持久化操作紀錄。使用者確認後，助理先保存原操作的證據，再允許那一次行程寫入。重新掛載助理畫面或重開 App 後，以目前帳號與學校找回原操作，讀取實際行程核對結果。

這份紀錄不保存聊天全文，也不恢復雲端對話、模型同意、通知排程或新的寫入權限。範圍為同一台裝置仍保留資料、同一個已驗證帳號及學校；清除 App 資料、移除 App 或更換裝置不在本輪恢復能力內。

主線 `ff8a5b9`（PR #518）的雲端對話 `sessionId`、帳號隔離及取消／期限修正一併保留。行程操作的持久 key 使用穩定帳號，而即時登入 context 只參與活躍範圍檢查；因此同帳號更新登入 session 後仍可讀取原操作，但不繼承原 session 的任何寫入授權。

## 實際使用

1. 輸入「幫我明天 19:00 到 20:00 安排英文讀書」，核對名稱與台灣時間。
2. 按「確認加入個人行事曆」。系統檢查目前帳號、學校、時段重疊、資料容量及開始時間，先保存並讀回操作紀錄，再寫入行程。
3. 從真正的個人行程資料讀到完全相符的紀錄後，顯示成功與核對時間；可直接開啟該筆行程。
4. 助理畫面重新掛載或重開 App 後，「找回的行程紀錄」會重新讀回核對。尚未完成讀取時不顯示成功，也不開放新的行程操作；仍停留在原畫面時，可從卡片重新核對。
5. 查不到、內容已改或暫時無法讀取，均保留原操作並提供唯讀核對。若使用者再提出同一個明確日期、時間及名稱的行程，即使聊天歷史為空，也先找原操作，不產生另一筆寫入。

恢復區與聊天分開保存狀態。切換回答模式會保留操作紀錄；同一筆紀錄若已在聊天卡片顯示，不再重複顯示於恢復區。區塊先呈現最近 16 筆，可按「顯示更多行程紀錄」查看其餘內容。查找同一事件涵蓋完整保存集合，不受初始顯示數量限制。

## 持久化契約

`apps/mobile/src/services/assistantCalendarJournal.ts` 使用獨立的 `campus.assistant-calendar-journal.v1` namespace，依 `firebase:<uid>` 或 `nuni:<accountId>` 與 `schoolId` 隔離，不讀取未分帳號的舊 key。每筆包含：

- 原 proposal：固定 `mutationId`、建立時間、帳號、學校與已解析的明確事件欄位。
- 嘗試時間。
- 最後查核狀態、時間，以及通過共用驗證器的收據或歷史收據。

整份資料須通過版本、容量、scope、重複 ID／事件、欄位白名單、日期及收據驗證。讀取失敗或資料損壞不能被當成空歷史。寫入後再次讀回相同序列化內容，才允許取得本次操作的一次性記憶體 permit；序列化的 proposal、恢復卡片或舊收據不能取得寫入能力。

容量上限是每個帳號與學校 **256 筆、512 KiB**。不自動淘汰成功或未知操作，也不因使用者刪除行程而移除操作證據。滿額時阻止新的操作，既有操作仍可核對，一般助理查詢仍可使用。本輪沒有提供歸檔或清除證據的入口，避免以清空紀錄恢復舊操作的寫入能力。

## 競態與不明結果

| 狀況 | 處理方式 |
| --- | --- |
| 操作紀錄已保存，行程還沒寫入就中斷 | 重啟後只核對原 ID；查不到仍為待核對，不自動重送。 |
| 原生儲存已寫入，但回應遺失 | 讀回同一筆實際行程；完全相符才產生成功收據。 |
| 兩個畫面同時確認同一事件、使用不同 ID | 在既有 ledger 鎖內查找持久紀錄，第二次回到第一筆的原 ID，更新發起確認的卡片，不重複新增。 |
| 已成功的行程被使用者刪除或修改 | 查核更新為不存在或內容不同；歷史收據標示為歷史，不覆蓋或補建。 |
| 上次有收據，本次重啟讀不到 ledger | 顯示待核對及歷史時間，不能用舊收據冒充本次查核成功。 |
| journal 損壞、配額不足或讀回不一致 | 保留原資料，不寫入無法追蹤的新行程；顯示重新載入／核對入口。 |
| 帳號、學校或登入 context 切換 | 丟棄晚到結果；舊操作不寫入或顯示到新範圍。 |
| I/O 等待超過期限 | 解除畫面等待並撤銷本次後續寫入資格；底層尚未完成的操作仍維持序列化，不因逾時釋放鎖而重複執行。 |

鎖順序固定為 personal-import ledger → journal。恢復先完成並釋放 journal 讀取鎖，再讀取一次 ledger snapshot 核對全部操作；更新查核狀態使用一次批次寫回。journal 自身不呼叫 ledger，避免反向等待。

若實際行程已成功讀回，但保存最新查核狀態失敗，保留當次可信回執並提示操作紀錄尚未更新；先前寫入前保存的 attempt 證據仍在，下次仍可讀回原 ID。

## 驗證方式

- `assistantCalendarJournal.test.ts`：嚴格讀取、容量、一次性 permit、並行 reserve、保存回應遺失、範圍切換及逾時。
- `assistantCalendarExecution.test.ts`：原有明確意圖與真 ledger 執行，以及 journal 寫入前置、重啟 proposal、未知／刪改紀錄不重建。
- `campusAssistantCalendarRecovery.test.tsx`：以真 journal 和個人 ledger，驗證恢復畫面、空聊天重問、雙登入、hydration 競態、範圍切換、失敗重試與超過 16 筆顯示。
- 原 `campusAssistantCalendarIntegration`、`AssistantCalendarAction`、`CampusAssistantScreen`、feature／service 回歸保留；儲存斷言精確區分 journal 與真正行程 ledger，不把必要的操作紀錄保存誤認為重複建立行程。

新增兩份 journal／恢復測試加入 `Mobile Agent Regression` 的明確測試清單；一般 Mobile CI 仍執行全部測試。實際通過數與完整 CI 結果以本輪提交的驗證紀錄及 PR 為準，不沿用舊提交的綠燈。

這些測試驗證受控情境下的結果與不重複寫入；不等於真機被 OS 終止的實測，也不等於正式使用者任務完成率或競品比較結果。

### 本輪本機結果

使用既有 frozen lockfile、Node 22.23.4 與 Jest 正式測試環境，逐批單 worker 執行，避免資源互相干擾。**12 suites、360 個不重複案例全部通過**：

| 範圍 | 通過 |
| --- | ---: |
| Journal／execution 單元測試 2 suites | 87 |
| 新的跨畫面恢復整合 | 19 |
| 原行程流程整合 | 17 |
| 原行程確認卡 | 6 |
| 原助理畫面，含主線新增雲端 session 隔離 | 62 |
| 原 feature、semantic、服務整合、課業交接／工作台／本地讀取結果 6 suites | 169 |

6 個 runtime 變更檔以 TypeScript compiler 解析真實相依模組，scoped syntactic／semantic、options 與 global diagnostics 為 0。12 個 runtime／測試變更檔的 ESLint 為 0 errors，保留助理畫面原有兩項 hook dependency warnings；`git diff --check` 通過。

原助理畫面的 9 個平台案例新增等待 journal hydration 完成，沒有關閉 production loading gate，也沒有替換恢復 hook、加入動畫 stub 或削弱原有斷言。getter 防護測試以 `Object.defineProperty` 建構真 accessor，避免 Babel 展開物件時先求值，確實驗證驗證器不執行 getter。
