# 學校登入 Adapter 評估與設計

這份文件只做評估與設計。沒有改正式程式、沒有部署、沒有寫入正式資料庫。

目標：使用者用「學號＋學校密碼」向各校 e 校園（或同等身分系統）驗證，**絕不存學校密碼**。驗證成功後只發我們自己的登入。靜宜大學當第一間，但設計必須撐住**任何學校改版**，不能只修靜宜那一頁。

更硬的目標：**學校改版時，已經綁過第二種登入的學生要完全不受影響，照樣進得來。** 只偵測改版、畫面寫「暫時連不上」不夠。

---

## 0. 現況（寫設計前對過的事實）

正式後端是 Fly `nuni-api`（原始碼綁在 `deploy/nuni-api/`，用 `python3 deploy/nuni-api/build.py` 建）。Web／App 的平台登入是 Google authorization code + PKCE，換成 Nuni 平台 session。學校資格目前是「送合作學校信箱、等校方驗證」，跟學號密碼驗證不是同一條路。

學號登入在正式畫面是關掉的。登入選項由 API 的 `sign-in-options` 決定；`studentId` 不是 true 時，表單不出現，文案是「學號登入還在準備，目前請用 Google 帳號登入」。

舊的靜宜實作還在 repo 裡，但**不能當正式接法**：

| 現況 | 問題 |
| --- | --- |
| `backend/functions/puScraper.js` 對 `alcat.pu.edu.tw/index_check.php` 送 `uid`／`upassword` | 綁死單一網頁；改版就壞 |
| `signInPuStudentId` 失敗多半回 401「學號或密碼錯誤」 | 學校掛了、改版、帳密錯會混在一起 |
| `identity.pu.edu.tw` Keycloak CAS 已用來登 TronClass | 這條比 e 校園表單穩，卻不是主登入 |
| 手機 `tronClassClient` 會把學號密碼存起來以便重登 | 違反「不存密碼」 |
| `packages/shared` 已有 OIDC／CAS／SAML 設定契約；Functions 有 `sso/providerRegistry.js` | 這是對的方向，但還沒接到 Nuni 正式登入 |
| App 的 `AdapterRegistry`／`PUAdapter` 在客戶端 | 學校帳密不該出裝置直連學校；設定改了還要發版 |

結論：新接法做在 **nuni-api**，一校一份 adapter 設定。客戶端只跟我們說話。舊 Functions／手機直連學校當成要退役的路，不擴充。

平台 Google 帳號 ≠ 學校身分。這點維持。學號驗證成功後，是在**既有平台帳號上加上學校保證**，或當場引導綁定，不是另造一套會跟 Google 對不上的 Firebase UID。

## 1. 每校獨立的接法

### 1.1 原則

- 一校一個 `schoolId`（靜宜用現有的 `pu`）。
- 一校一份 **adapter 程式**（處理該校協議差異）＋一份 **設定**（URL、欄位、指紋、開關、文案）。
- 新增或修好一間，只動那間的 adapter／設定。共用核心只放「契約、失敗分類、限流、發我們自己的登入、健康檢查框架」。
- 沒登記的學校，API 直接拒絕收帳密，不拿靜宜當預設後端。現有 App 測試已有這條防呆，正式 API 也要守。

### 1.2 建議放哪

```
nuni-api（Fly，唯一驗學校帳密的地方）
  school-login/
    core/          契約、失敗分類、限流、發 session、健康檢查排程
    adapters/pu/   靜宜：CAS／表單／信箱規則
    adapters/<id>/ 之後各校
  設定來源（熱更新，見第 5 節）
    school_login_adapters 資料表：策略順序、選擇器、指紋、狀態、畫面文案版本
```

客戶端（Web／App）只呼叫我們的 API：列出可用登入方式、送學號密碼、綁第二種登入、用已綁方式進來。**不**把學校密碼送到 `alcat.pu.edu.tw` 或任何學校網域。

舊的 `apps/mobile/src/data/apiAdapters/` 可繼續管課表／公告等資料，但 `authenticate(username, password)` 不該再由手機打學校。

### 1.3 一校設定長什麼樣（概念，不是要現在落地的 schema）

每校至少有：

- `schoolId`、顯示名稱、學號格式
- `status`：`live`／`testing`／`degraded`／`outage`／`disabled`
- `strategies[]`：依優先順序排列的驗證策略（下一節）
- `identity`：怎麼從成功回應取出學號、姓名、學校信箱
- `email`：允許的信箱網域、學號對信箱的規則（靜宜現況常是 `{學號}@pu.edu.tw`，仍須校方確認）
- `health`：不需帳號的頁面指紋、可選的測試帳號檢查
- `copy`：給畫面的短文案（帳密錯、暫時連不上、請改用已綁定方式）
- `bindPolicy`：第一次學號驗證成功後，要強迫／引導綁哪些第二因素

加一間學校＝新增 adapter 套件（若協議是新的）＋一列設定。修一間＝改那列設定或那份 adapter。別校的策略陣列不會被碰到。

### 1.4 靜宜當第一間時怎麼切

靜宜會有**多個策略、同一個 adapter 套件**，不是「一個 PHP 登入頁＝整間學校」：

1. `identity.pu.edu.tw` Keycloak（CAS，必要時再申請 OIDC client）
2. 學校信箱／Microsoft 365（靜宜學生雲端主力是 M365 `@o365st.pu.edu.tw`，111 學年起不配發 Google）
3. `alcat.pu.edu.tw` 表單模擬（最後手段，且要有版本化解析，見第 4、5 節）

TronClass、成績頁、選課頁是**資料連線**，不是登入是否成功的唯一依據。登入成功只需要「校方身分系統承認這組學號密碼」；課表稍後抓不到，應標資料降級，不把人踢出去。

## 2. 各校可用的驗證方式優先順序

一律由我們的伺服器執行。順序固定：

1. **官方 SSO／OAuth／OIDC／CAS／SAML／LDAP（LDAP 只在校方要求、且不經過我們轉存密碼時才用）**
2. **校方提供的驗證 API**（有文件、有穩定錯誤碼）
3. **網頁表單模擬**（最後手段；必須當會壞的東西來養，不能當主路徑）

「能直接用學校 Google／Microsoft 帳號登入、免爬網站」的條件是：學校把學生帳號放在 Google Workspace 或 Microsoft 365，**而且**我們能驗證 `hd`／tenant，不是私人 Gmail／個人 Outlook。現有平台 Google 登入沒有限制學校網域，所以**不能**把「用 Google 登進 Nuni」直接當成「這人是靜宜學生」。要嘛另開「學校 Google／Microsoft」綁定，要嘛在既有 Google 上再驗一次 hosted domain 與學號對照。

### 2.1 台灣主要大學常見系統（公開資訊盤點，不是已簽約清單）

下列是台灣大學常見的身分做法。**「可免爬」是指協議上做得到，實務仍要校方同意發 client、提供測試帳號。** 沒談妥之前，只能當候選，不能寫進 live 設定。

| 類型 | 常見情況 | 對我們的意義 |
| --- | --- | --- |
| Google Workspace for Education | 不少國立／私立把 `@學校.edu.tw` 放在 Google | 用學校 Google 當SSO 或當第二因素，免爬 e 校園。要驗 `hd`，拒私人 Gmail |
| Microsoft 365／Entra ID | 部分學校行政或師生帳號在微軟 | OIDC／SAML；同樣要鎖 tenant |
| Apereo CAS | 很多校務入口、圖書館、LMS 前面 | 協定穩，比模擬登入頁耐改版。要註冊 service |
| Keycloak（CAS 或 OIDC） | 靜宜 `identity.pu.edu.tw` 已在用 | 靜宜應**先走這條**，不要先死守 alcat 表單 |
| 校務入口自製 OAuth | 例如 seed 裡示範的台科大 `portal.ntust.edu.tw/oauth` | 有 client 就能當官方策略 |
| LDAP／AD | 多半藏在 IdP 後面 | 不要讓使用者密碼經過我們去 bind；請校方開 SSO |
| 校務系統商表單（宏碁 Alcat／e 校園、巨耀、其他） | 靜宜 e 校園就是這類 | 最後手段；選擇器一改就壞 |
| LMS（TronClass、Moodle 等） | 靜宜 `tronclass.pu.edu.tw` 走 CAS | 可當資料源，不宜當唯一身分來源 |

各校粗分（**未向校方核實，實作前要再問一次**）：

| 學校 | 較可能的官方路 | 還能不能免爬 |
| --- | --- | --- |
| 靜宜 `pu` | Keycloak CAS（`identity.pu.edu.tw`）；學生雲端主力 M365 `@o365st.pu.edu.tw`（111 學年起不配發 Google）；信箱網域 `pu.edu.tw` | 若校發 M365／信箱 OTP 可用，日常登入可完全不碰 e 校園網頁 |
| 台科大 | 入口 OAuth（公開路徑曾見 `portal.ntust.edu.tw/oauth`） | 有 client 就可免爬 |
| 台大、清大、成大、陽交大、中央、師大、政大等 | 多為校務入口＋Google 或 CAS | 優先談 SSO／學校 Google，不要先寫爬蟲 |
| 輔大、東海、長庚、中原、東吳、北醫等 | 入口／Google／微軟混用 | 一校一查；沒 SSO 才考慮表單 |

盤點原則：新學校先問「學生日常登入 Google 還是微軟還是校務 CAS」。答案是前三者，就不該開表單模擬。

### 2.2 為什麼表單模擬不能當主架構

靜宜舊爬蟲驗的是「登入後頁面有沒有學生脈絡」。任何學校換成新前端、加驗證碼、改欄位名稱、改網域，都會讓同一套程式一次全滅。這不是靜宜獨有。所以表單策略必須：

- 版本化（`form-v1`、`form-v2`），新舊並行
- 設定與程式分開，改選擇器不必發佈映像
- 永遠排在官方 SSO／API 後面
- 失敗要能分成「帳密錯」和「網站變了」（第 3 節）

## 3. 改版偵測與失敗分類

### 3.1 三種失敗，不能混

| 分類 | 意思 | 使用者看到的（白話） | 限流怎麼算 |
| --- | --- | --- | --- |
| `credentials_invalid` | 校方明確說帳號或密碼錯 | 「學號或密碼不對」 | 計入防暴力試 |
| `school_changed` | 登入頁結構／流程對不上已知指紋，或成功條件消失 | 「學校網站改版，我們正在接。若你已綁過 Google／passkey／學校信箱，請改用那些方式。」 | **不計**暴力試 |
| `school_down` | DNS／TLS／5xx／逾時／維護頁 | 「學校系統現在連不上，不是你的帳密錯。」已綁定者請用第二種登入 | **不計**暴力試 |
| `our_fault` | 我們自己逾時、設定缺漏 | 「登入服務暫時有問題，請稍後再試」 | 不計 |

舊 `signInPuStudentId` 把驗證頁失敗也說成帳密錯，這是要改掉的契約，不是小文案。

無法分類時，**預設當 `school_changed` 或 `school_down`，不要當帳密錯。** 誤殺會讓人一直改密碼。

### 3.2 健康檢查（定時，一校獨立）

兩層，失敗只標**那一校**：

1. **免帳號**：抓登入頁（或 IdP discovery／`.well-known`）。比對指紋：主機、TLS、表單 action、欄位名稱、關鍵字、CAS／OIDC metadata。對不上 → `school_changed`。連不到 → `school_down`。
2. **有測試帳號**（校方或我們持有的專用帳）：走完整 verify。成功＝通路活著。明確帳密錯＝測試帳號本身壞了（另開警報，**不要**把全校標成連不上）。結構失敗＝改版。

檢查結果寫進該校狀態（`live`／`degraded`／`outage`），給登入 API 和畫面讀。**不寫正式使用者資料。**

官方 SSO 策略活著時，表單策略掛了只算資料爬蟲降級，不算「這間學校不能登入」。

### 3.3 登入當下也要分類

即使用戶正在登入，也走同一套分類。若該校已是 `outage`／`school_changed`：

- 已綁定第二種登入：這條學號密碼路徑直接告訴他改走綁定方式，**不要再試學校網站**（避免害他被學校鎖帳）。
- 未綁定：走第 4 節新生備援（學校信箱驗證碼），不要只停在「暫時連不上」。

## 4. 改版期間照樣能登入

這一節是產品底線：**學校網站改版 ≠ 我們的 App 進不去。**

把「證明你是這間學校的學生」和「今天學校網站長什麼樣」拆開。學校網站只在**第一次**（或定期重驗）需要；之後靠我們自己的登入。

### 4.1 第一次學號驗證成功後，立刻綁第二種登入

學號＋密碼通過校方驗證之後，這次請求只把密碼留在記憶體裡用完即丟，接著發我們自己的 session，並**強迫或強烈引導**綁至少一個不依賴學校網站的方式：

| 第二種登入 | 怎麼證明 | 改版時還能不能用 |
| --- | --- | --- |
| 學校信箱驗證碼 | 寄到該校允許網域（靜宜即 `@pu.edu.tw` 這類）。能收信＝控有校發信箱 | 能。寄信不經過 e 校園登入頁 |
| 學校 Google／Microsoft | 官方 OAuth，鎖 hosted domain／tenant，並與已驗學號綁在同一人 | 能。走 Google／微軟，不走學校網站 |
| Passkey（WebAuthn） | 在我們的網域註冊，綁的是「已通過學校驗證的這個人」 | 能。之後完全不連學校 |

建議產品規則：

- 第一次成功後，畫面不讓人「以後再說」就關掉（至少綁一樣）。可以選哪一種，不能一種都不綁。
- 平台 Google 若 email 網域不是該校，只能當平台帳號，**不能**自動當成學校身分；要另綁學校 Google 或信箱。
- 綁定紀錄只存：方式、subject／信箱、綁定時間、assurance。不存學校密碼。

這樣，**已綁定學生在改版當下跟學校網站零關係。** 這就是「完全不受影響」。

### 4.2 已綁定：長效登入＋定期重驗失敗時的寬限期

已綁定之後：

- 日常登入只走我們：session、passkey、學校 Google、信箱驗證碼。
- **不要每次打學校。** 學校網站慢、掛、改版，都不該擋進 App。
- 背景定期重驗（例如每 30 天，用不到使用者密碼：能走 SSO 就走 SSO；表單策略若還需要密碼，這條就**跳過表單**，只做免帳號指紋＋測試帳號）。
- 重驗失敗且分類是 `school_changed`／`school_down`：進入**寬限期**（建議 90 天，可調）。寬限內：
  - 登入照常
  - 課表／成績等即時校務資料標「暫時同步不到」
  - 不提示帳密錯誤
- 寬限結束仍沒接好：還是讓已綁定者登入（身分保證降為「先前已驗證，待重驗」），但敏感校務資料維持只讀快取或隱藏。**不因為我們沒修好接法就把人鎖在門外。**
- 只有校方明確說此人已退學／帳號廢止，或使用者自己解除綁定，才撤銷學校身分。

畢業生、休學生怎麼處理要產品決定（第 8 節），但不能跟「網站改版」混成同一種踢出。

### 4.3 新生碰到改版：學校信箱驗證碼就能進

沒綁過、學校網站又正在改版或掛掉時，學號密碼這條會失敗。備援：

1. 選學校、填學號、填**該校網域信箱**（或由學號推導後請他確認）。
2. 我們寄一次性驗證碼（短效、單次、限流）。
3. 驗證碼正確 → 發我們的登入，assurance 標成 `email-otp`（比學號密碼弱）。
4. 立刻引導綁 passkey 或學校 Google，之後就跟已綁定學生同一條路。
5. 學校網站恢復後，再請他補一次學號密碼或官方 SSO，把保證升成 `password-verified`／`sso-verified`。在那之前，正式課表／成績可以先不開放或只給公開校園功能——這點要產品拍板，但**進 App 這件事不能沒路。**

這條備援的前提：該校學號對應得到校發信箱，且我們寄得出信。靜宜現有程式假設 `{學號}@pu.edu.tw`，**上線前要校方或實測確認**，不能當全台通用規則。

信箱 OTP 被冒用的風險（撿到別人學號去收公開規則信箱）要用：驗證碼短效、每學號／每 IP 限流、信箱必須落在該校 allowlist、升級保證前不開放成績。

### 4.4 自動修復：多策略備援＋測試帳號重建解析

改版時已綁定者不受影響；同時我們要儘快把「第一次驗證／重驗／資料同步」修好。

**登入策略備援（同一校、一次請求內）：**

1. 官方 SSO（OIDC／CAS／SAML）
2. 校方 API
3. 表單新版解析（`form-v2`）
4. 表單舊版解析（`form-v1`）——學校常會新舊網址並存幾天
5. 全部失敗 → 分類，導向已綁定登入或信箱 OTP，絕不說成帳密錯

**測試帳號自動重建：**

健康檢查發現指紋變了以後：

1. 存登入頁快照（去掉個人資料，只留結構）。
2. 用已知規則猜新欄位（`uid`／`username`／`account` 這類）。
3. 用**測試帳號**在隔離環境試候選解析，成功才算數。
4. 成功：寫入新設定版本、該校策略切到新版、舊版留著當備援、狀態拉回 `live` 或 `degraded`。
5. 失敗：該校標 `degraded`／`outage`（只影響「第一次學號驗證」和校務同步，不影響已綁定登入），開修正提交（設定 diff、指紋前後、測試帳號結果是成功／失敗，**不含密碼**），並警報。

**目標修復時間（人時／鐘點，不是日曆週）：**

| 情況 | 目標 |
| --- | --- |
| 只改 URL／欄位／選擇器，測試帳號能自動對上 | 設定熱更新後數分鐘內恢復第一次驗證 |
| 要改 adapter 程式（新驗證碼、多步驟） | 數小時內可合併的修正；這段期間已綁定者不受影響 |
| 要跟校方申請 SSO client | 不在我們能保證的時間內；申請期間靠綁定登入＋信箱 OTP |

自動寫入 live 設定要有開關：預設「自動套用到 testing，人工確認後才 live」。誤傷正式登入比慢修更糟。第一季建議自動只進 `testing`，live 要人按。

## 5. 快速修復流程（設定改了不必重新部署）

### 5.1 熱更新

adapter **程式**跟映像走；adapter **設定**（URL、欄位、指紋、策略順序、文案、status）放在 nuni-api 可讀的資料表或簽過名的設定檔，啟動後定期重讀（例如 30–60 秒）或管理 API 一改就生效。

不把學校登入選擇器寫死在客戶端、也不寫死在必須發佈 Docker 才能改的常數裡。Fly 映像只在協議真的變了（例如從表單改走 OIDC）才需要重佈。

操作：管理 CLI 或已驗證的 ops API 更新單一 `schoolId` 的設定，預設 dry-run，`--apply` 才寫入。每次寫入留版本號，可一鍵回退上一版。

測試帳號、OAuth client secret 走既有 Fly secret，不進 git、不進設定 JSON 明文。

### 5.2 警報

每校獨立。建議通知：該校變 `degraded`／`outage`、測試帳號無法登入、自動修復成功／失敗、回退被觸發。內容含學校、分類、設定版本、時間。不含學號明文亦可，若要排錯最多雜湊；**一定不含密碼。**

通知管道（Slack／信件／其他）要你指定，見第 8 節。

### 5.3 回退

- 設定：回上一版即可，不用部署。
- 程式：沿用現有 nuni-api 映像回退方式；資料庫只加欄、不加破壞性遷移。
- 某校 adapter 出包：只把那校 `status=disabled` 或拿掉該策略，其他學校與平台 Google 不受影響。
- 回退時已綁定登入仍在。回退的是「怎麼跟學校網站說話」，不是「誰已經是學生」。

## 6. 安全

| 規則 | 做法 |
| --- | --- |
| 密碼只在記憶體 | 請求進來 → 交給當次策略 → 函數結束即丟。不寫 DB、Redis、log、錯誤訊息、analytics |
| 不存學校 cookie 當長期登入 | 舊流程把 e 校園 cookie 存起來做課表；新登入不靠這個當身分。要同步校務另開短命資料 session，並與「能不能進 App」分開 |
| 只發我們自己的登入 | 校方驗證成功後發 Nuni session（或把學校保證掛在既有平台 session 上）。之後 API 只認我們的票，不認學校 cookie |
| 限流與防暴力試 | 每 IP、每學號、每校分開；只有 `credentials_invalid` 計次。改版／學校掛了不鎖使用者 |
| 記錄 | schoolId、結果分類、策略與設定版本、時間、請求 id。學號可雜湊。密碼、驗證碼、cookie 禁止出現 |
| 傳輸 | 使用者→我們、我們→學校都是 TLS。不跟隨不明 redirect 把帳密送到別的網域 |
| 客戶端 | 正式 App／Web 不存學校密碼（現有 TronClass 重登存密碼要廢）。Passkey 私鑰留在裝置 |
| 權限 | 學校保證 ≠ 平台管理員。沿用現有分層授權：校籍、課程、店家各自再驗 |

信箱 OTP、passkey 註冊本身也要限流，避免被拿來掃學號。

## 7. 階段與工時估算

工時是「人時」，不是日曆上的幾週。實作前這份文件本身不算進下面。

| 階段 | 做什麼 | 規模 | 大約人時 | 風險 |
| --- | --- | --- | --- | --- |
| A. 契約與核心 | 失敗分類、sign-in-options、設定表、限流、發我們的 session、一校 status | 動 nuni-api 新路由與設定，客戶端只接文案與開關 | 16–24 | 要對齊現有平台 session，不能另造會衝突的 UID |
| B. 靜宜 adapter | Keycloak CAS 優先，表單當備援且版本化；健康檢查與分類 | 靜宜套件＋指紋；不碰別校 | 24–40 | 沒測試帳號就無法安全測 CAS／表單 |
| C. 綁定與改版備援 | 信箱 OTP、學校 Google／passkey 綁定、長效保證、寬限、新生 OTP | 帳號模型與登入畫面；**這階段一做完，改版就傷不到已綁定者** | 32–48 | 信箱規則、Google hd、是否強迫綁定要你先定 |
| D. 自動修復 | 多策略備援、測試帳號試解析、開修正提交、警報與回退 | 排程與 ops；預設不自動推 live | 24–40 | 自動猜表單有誤傷風險，所以 live 要人工閘 |
| E. 下一間學校 | 有官方 SSO：主要是設定；只有表單：新 adapter | 有 SSO 約 8–16／校；只有表單約 16–32／校 | 取決於校方 | 沒同意就不要上 live |

建議上線順序：**A → C 的綁定骨架與平台 Google 既有帳號對齊 → B 靜宜第一次驗證 → C 其餘備援 → D。** 若 B 比 C 先上、又還沒強迫綁定，下一次靜宜改版仍會把人擋在門外。

驗收時至少要測：帳密錯、學校網站結構被換成假改版、學校連線逾時、已綁定者在 outage 時仍能進、新生 OTP、設定回退、密碼不出現在 log。

## 8. 需要你決定的事

沒有這些，靜宜不該開正式學號密碼：

1. **測試帳號**：靜宜至少一組不會進真實成績的測試學號（登入用）。沒有它，健康檢查與自動修復只能做免帳號指紋，改版會比較慢才發現。
2. **校方是否同意**：Keycloak／CAS 或 OIDC client、用學號密碼代驗是否允許、測試帳號、`@pu.edu.tw` 是否可收 OTP。沒同意就只能停在設計，或只開「已有平台 Google 的人綁學校信箱」這類不碰 e 校園密碼的路。
3. **強迫綁定還是可跳過**：建議強迫至少一種。可跳過＝下一次改版，沒綁的人又會進不來。
4. **新生 OTP 能不能進 App、能進多深**：只進公開校園，還是也能看已快取課表。建議 OTP 先當「進得去」，成績等升保證後再開放。
5. **學校 Google 與平台 Google 要不要同一顆按鈕**：同一顆較省事，但要能區分「私人 Gmail 平台帳」和「`@pu.edu.tw` 學校帳」，並處理一人兩顆 Google 的綁定。
6. **寬限期長度、畢業／離校怎麼撤銷**。
7. **警報要打去哪**。
8. **自動修復可否直接改 live**：建議第一季不行，只進 testing。
9. **下一間學校是誰、有沒有 SSO**。沒有官方路就不要承諾跟靜宜同一天開。

## 9. 靜宜第一間：建議接法（摘要）

1. 使用者送學號密碼 → 只進 nuni-api。
2. 依序試：Keycloak CAS →（若有）學校 M365／校方 API → alcat 表單新版 → 表單舊版。
3. 成功：密碼丟棄；發我們的 session；強迫綁信箱 OTP／學校 M365／passkey。靜宜不要把「學校 Google」當預設第二因素：學生雲端主力是 M365 `@o365st.pu.edu.tw`，111 學年起不配發 Google。
4. 之後登入：已綁定方式，不打學校。
5. 學校改版：已綁定者無感；新生走信箱 OTP；健康檢查標靜宜 `degraded`，自動試新解析並開修正提交。
6. 畫面：帳密錯就說帳密錯；其他情況不說帳密錯，並把已綁定入口放最上面。

這樣不是「把靜宜網站修到永遠不會改」，而是「網站一定會改，但登入已經不綁在那一頁上」。
