# 從讀書計畫一次完成多份作業的準備安排

## 學生能完成的事情

在手機 nuni 上課助理的即時計畫中，選取 2–4 份作業，讓助理依各自截止時間、手機已保存課表與個人行程，各安排 30 分鐘。使用者核對整份預覽並確認一次後，助理逐筆建立個人行程、讀回同一筆紀錄，再進入下一筆。

每筆完成卡都能開啟實際建立的行程。中斷後保留已完成與尚未開始的進度；重開 App 會重新讀取操作結果，使用者再次確認後才接續原先預覽的時段。

這一輪接續已合併的 PR #537，以 main `040957b6` 為開發基底。沿用單筆行程的 journal、鎖內驗證、一次性 permit 與讀回機制，沒有新增另一條寫入路徑。

## 範圍與使用流程

1. 選取即時計畫中的 2–4 份作業。優先事項與逐日清單中的同一來源只出現一次；同名、不同 ID 的作業分開保留。
2. 重新讀取全部選取來源，核對本人、學校、學期、課程連結與目前作業狀態。
3. 共用一份課表與個人行程快照，依截止先後分配時段。各段 30 分鐘，彼此至少間隔 10 分鐘。
4. 顯示整份安排、課程、截止時間與準備時段；這時僅保存預覽，沒有行程操作紀錄或寫入權限。
5. 使用者確認後，先核對全部尚未開始的作業，再於每一步建立前重新核對該來源及固定時段。
6. 每筆保存後讀回；只有核對成功才計入完成數量。結果不明、來源變更、衝突、逾時或停止操作都會擋住後續步驟。

自動配置限今天起七天內、08:00–22:00、已知課間空堂，並沿用課程及私人行程前後的 10 分鐘緩衝。空白或無法完整核對的課表不會被當作確定有空。找不齊全部選取作業時，回報無法安排的項目，且不保存縮減版批次。

作業已繳交、關閉、沒有明確期限、無法核對近期課堂或來源資料不完整時，保留原有查看作業入口。測驗、歷史計畫副本與另一帳號的來源不進入這個選取流程。

## 持久化與來源核對

| 資料 | 用途 | 不代表的權限 |
| --- | --- | --- |
| `kind: coursework-study` 與保留 ID 前綴 | 辨認來源型批次，防止遺失來源欄位後降級成一般行程 | 不授權執行 |
| 帳號、學校、學期、workspace、assignment ID | 重新找回精確來源 | 不代替目前登入與 API 授權 |
| 作業名稱、課程名稱、期限、課程身分摘要 | 比對使用者原先預覽的來源 | 不代替最新作業狀態 |
| Journal proposal 的 `origin.batchId/stepId` | 對應這個步驟真正送出的原操作 | 不讓反序列化 proposal 取得 fresh grant |
| 原 mutation ID 與讀回回執 | 核對實際保存結果、防止重送 | 歷史回執不證明目前內容仍相同 |

批次只保存重新尋找來源所需的 IDs 與預覽摘要，不保存完整作業內容、繳交附件、完整 coursework read、slot proof、write check 或確認權限。

來源型批次缺少 resolver 時，核心 runner 也拒絕新的 dispatch。這項限制不只依靠畫面隱藏按鈕。同名同時段的一般行程或其他批次的回執，不能被認列為這份作業的完成結果。

每次來源讀取保留既有的授權、BFF 上限與重複 ID 檢查。整組預覽與 preflight 讀取期間，任何已讀來源、課表或個人行程變更都會撤銷當次結果。逐筆檢查的來源訂閱保留至寫入邊界，與空堂的 ledger fingerprint 一起限制寫入。

## 中斷與恢復

- 單筆已送出但結果不明時，停止後續行程，只核對原操作，不建立新的同名操作。
- 第一筆寫入會更新 ledger；第二筆使用新的資料重查，不沿用第一筆前的 fingerprint。
- 停止、離頁、換帳號或換學校後，晚到的來源結果不能啟動後續寫入。
- 重開 App 的恢復階段只讀取計畫與原操作；接續必須再按確認，且仍重新核對來源及原定時段。
- 取消尚未開始的行程會持久保存決定。已建立的行程與待核對操作保留，不把「取消後續」描述成刪除已建立事件。
- 已保存的讀書計畫仍是移除即時來源的歷史副本；需要重新規劃取得目前來源。

## 測試與驗收

回歸涵蓋來源驗證、完整排程、持久化格式、origin 關聯、逐筆寫入、恢復與實際畫面。畫面整合測試使用真正 planner、來源 reader、空堂計算、batch runner、journal 與 ledger；只替換 API、原生儲存介面和時鐘。

重點驗收包括：一次確認建立兩筆互不重疊事件、整組 preflight 在第一筆前發現第二份作業變更、第一筆後來源變更只保留已完成結果、停止後重開再確認只接續剩餘步驟，以及預覽查詢取消後保留輸入草稿。

本輪本機驗證共 **73 組、2,411 項通過，沒有跳過案例**。完整回歸先有 72 組通過；唯一失敗是新測試把恢復後的 fresh readback 誤期待為舊回執的 `replay` 與時間戳記。修正測試後，受影響的整組 35 項全部通過；保留原 proposal、mutation ID、storage、完整 record 相等與不重送斷言，明確要求 `replay: true` 及新的核對時間。這個修正沒有更動 runtime。

測試路徑納入 `.github/workflows/mobile-agent-regression.yml`。精確案例數、提交與遠端 CI 結果記錄在本輪 PR，不能用上一輪綠燈替代本輪檢查。main 的既有必要 App 審查與分支規則保持原樣。

這裡完成的是「準備行程安排」，作業完成及繳交仍以課程頁為準。此功能不代表已實作跨裝置同步、外部行事曆、行程通知、代交作業或自動替換已確認時段；也不據此宣稱競品任務完成率已被超越。
