# 作業狀態同步

自有課程作業主清單與教師最後選取且可見的一份收件，在上次讀取完成後等待 **60 秒**自動更新。原先的五秒目標已取消；約每分鐘自動看到更新，網路與伺服器耗時另計。回到畫面、切回作業分頁、恢復網路、自己寫入或按更新時立即補讀，仍受同一路徑在途請求串行限制。只有目前課程作業分頁啟用；背景、pagehide、不可見、離線、其他分頁、收合或搜尋隱藏的收件停止排程。不可將此敘述當作延遲上限或正式環境保證。

成功後等待 60 秒；失敗保留 5、10、20、40、60 秒退避並封頂，成功歸零。回前景作廢舊世代，本機寫入增加 revision，過期回應不能覆蓋確認收據與回饋。401／403／404／工作階段變更清空並停止。草稿保留，已送出請求不取消。「已同步」及裝置時間只代表最近一次清單成功，送出以伺服器確認收據為準。

## 間隔決策及未達成的容量條件

先以產品要求的 30 秒估算，再降低至 60 秒。以下採 100 份合成作業、每份標示 100 份收件；學生只下載自己的狀態，不下載教師完整收件。每次 HTTP 清單有三次上游 GET，300ms 合成耗時。原本 2.5 秒樣本每人每小時外推 1,290 次，2,000 人每天前景一小時為 2,580,000 次。

為避免短樣本首次讀取放大偏差，容量表採零延遲的保守公式 `floor(3,600,000 / 間隔毫秒) + 1`，包含每小時一次首次讀取。每次 JSON 約 31,208 bytes（由本次平均 31,207 bytes 向上取整），UTF-8 未壓縮，不含 HTTP／TLS；月為 30 天，每人每天前景一小時。額外手動、寫入、反覆回前景、教師收件與其他既有流量另計。

| 成功間隔 | 每人每小時 HTTP | 2,000 人每日 HTTP | 每日上游 GET | 每日 JSON bytes | 每月 JSON GB（十進位） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 30 秒 | 121 | 242,000 | 726,000 | 7,552,336,000 | 226.570 |
| 60 秒（採用） | 61 | 122,000 | 366,000 | 3,807,376,000 | 114.221 |
| 120 秒（評估） | 31 | 62,000 | 186,000 | 1,934,896,000 | 58.047 |
| 只做每日首次讀取（沒有定期讀取） | 1 | 2,000 | 6,000 | 62,416,000 | 1.872 |

60 秒相對原樣本每日 HTTP 減少約 95.27%。若每人每天前景 24 小時，保守估計再乘 24：2,928,000 次 HTTP／日、8,784,000 次上游 GET／日、91,377,024,000 bytes／日。教師另開一份收件增加相同頻率的排程，但其位元組取決於收件數，不能冒用學生清單大小。

### 官方額度與合理估算

查核日期：2026-11-01。沒有讀帳號、金鑰或正式用量，以下不是實際剩餘額度。

- [Neon 官方方案](https://neon.com/pricing)：Free 每專案每月 100 CU-hours、1GB 儲存、5GB public network transfer。100 projects 不代表單一資料庫可使用一百倍配額。
- [Fly 官方定價](https://docs.fly.io/about/pricing)：新組織採用量計費，沒有可假設的永久免費運算／對外流量額度；亞太對外傳輸 $0.04/GB，北美／歐洲 $0.02/GB。
- [Fly 舊方案](https://docs.fly.io/about/discontinued-plans)：符合舊方案資格才有最多三台 shared-cpu-1x 256MB、總共 3GB volume，亞太等區每月 30GB 對外流量，北美／歐洲 100GB。沒有證據證明目前組織適用。

先假設既有功能已使用一半免費額度（只是預算情境）：Neon 剩 50 CU-hours／2.5GB，增量門檻為 25 CU-hours／1.25GB；Fly 舊亞太剩 15GB，門檻 7.5GB。60 秒 BFF 回傳估計 114.221GB／月，為舊亞太完整額度 380.7%、估計剩餘 761.5%，仍遠超門檻；30 秒為 755.2%／1510.5%。即使改成 120 秒仍有 58.047GB。若該回傳完整經 Fly 對外流出，60 秒約 $4.57／月；有舊額度且全數可用時約 $3.37，未含運算、其他流量與壓縮影響。這些是部署路徑假設，不是帳單實測。

Neon 的資料庫輸出不等同 BFF JSON；若暫以相同資料量估算，60 秒為完整 5GB 的 2284.4%、估計剩餘 2.5GB 的 4568.8%。即使完全取消定期輪詢，首次讀取 1.872GB 也超過上述 1.25GB 門檻。因此不存在只調整正數輪詢間隔就能保證達標的解；Fly 新方案的零免費配額也無法靠延長間隔達標。未為了產生表面通過數字，將更新改成數小時或刪掉必要的首次／手動讀取。**採用 60 秒降低負載，但整體免費容量條件仍未達成；不能宣告免費上線驗收通過。**

CU-hours 不能由 GET 數推算。僅以 0.25 CU 舉例，所有使用者集中一小時加五分鐘閒置，每月約 8.125 CU-hours（估計剩餘 50 的 16.25%）；分散整日使資料庫常醒則約 180 CU-hours（360%）。2000 人查詢所需真實 CU 未量測，這不是上下界或容量保證。上游 GET 也不等於 SQL；100 份作業的附件索引可能另做 100 次 countWithdrawn SQL。本功能沿 PostgreSQL／HTTP 路徑，不產生 Firestore 文件讀取，不能以 Firestore 零讀取推論 Neon／Fly 免費。

## 條件讀取評估

既有 `apps/web/src/lib/nuni/api.ts` 作業清單依序呼叫作業、課程與身分，接著補附件索引；共用傳輸回傳解析後 JSON。查核現有實作沒有 ETag／If-None-Match 或涵蓋作業、收據、回饋、附件與撤權的輕量版本號。BFF 在完整讀取後才雜湊回 304，只減少最後一段回傳，仍保留上游與 SQL 成本；跨使用者快取又必須處理個人收據與權限。本次不新增端點或快取授權捷徑，不採條件讀取。後續需另有受授權的版本／差異讀取設計及隔離環境實測，才能解決剩餘容量條件。

測試使用 `EXPO_NO_DOTENV=1`、專用 `/tmp/jest_rs/nuni359-fix4`；Web `--no-cache --maxWorkers=2`，Mobile `--runInBand` 並指定該目錄下快取。只在沒有 node_modules 時安裝，完成後清理本次安裝與暫存。
