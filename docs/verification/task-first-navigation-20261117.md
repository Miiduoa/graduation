# 首頁、登入與服務使用流程重整

日期：2026-11-17（台灣時間）

## 要解決的問題

本輪從 `afca3204dc105fbcee03e6afef53e1203d761f4d` 的實際 Web／Mobile 元件開始盤點。首頁同時顯示課務待辦與 Agent 的同一批作業，學生證放在主標題之前；登入頁先展開多個角色入口；生活頁自行維護服務名稱、權限及搜尋字詞，和全站目錄已不一致。全站雖然已有父子服務資料，畫面仍把全部次級入口一起展開。

開發期間已快轉整合 main `e71bccf0ab8ea10fccb7b092271d2810a9e06bf8` 的公開查課修補（#662）；其兩個修改檔與本輪不重疊。

改造原則是先呈現當下工作、常用功能固定在第一層、次級操作按需求展開，以及離開再返回時維持原有位置。沒有增加新的首頁或第二套示範入口。

## 改版後的主要流程

| 起點 | 使用者看到的順序與結果 |
| --- | --- |
| 今天 | 今天標題、真實課表／課程待辦、安排與對話助理、個人化建議、學生證等工具 |
| 從某項任務登入 | 主要登入方式、返回原任務提示、需要時展開其他身分入口 |
| 全站更多／所有服務 | 每類四個常用服務；其他服務與父項下的相關服務另外展開 |
| 生活 | 出門與交通、吃飯與取餐、住宿與日常、安排課餘時間 |
| 搜尋 | 同時搜尋已展開與收合的服務，命中的次級服務可直接前往 |
| 從服務返回 | 還原查詢、分類及已展開的群組；不把曾經前往的目的地誤標為目前所在頁 |
| 原生 App | 常用服務優先、其餘分類收合；首頁課務載入／重試時保留詢問草稿 |

## 重要實作決定

### 同一份服務資訊

生活頁以 `campusServices.ts` 的服務名稱、說明、存取需求及開關為準，頁面只維護呈現分組與圖示。失物招領顯示實際 Google 帳號入口；已存在的職涯工作區重新納入全站查找；公車及借還書的生活用語合併回共用搜尋字詞。校園助理的存取說明不再誤寫成只接受學校帳號。

全站選單和完整目錄共用常用入口順序，仍保留每一個既有服務。功能開關先過濾，再建立目錄；關閉的校方作業與線上訂單不會因搜尋或展開而重新出現。

導覽仍尊重不同課程來源：學校／Firebase 的 `/course/*` 不會被誤接到 Google 課程 `/classroom`，避免使用者在已有課程中被帶到另一套帳號。教材收藏則正確歸在原本的 Google 課程導覽中。

### 少量入口與可接續的返回

全站預設第一層共 16 個服務連結，按四類分組。子服務與低頻角色入口仍能藉由分類展開或文字搜尋直接抵達。原生展開控制具鍵盤焦點與至少 44px 操作高度。

全站返回快照僅新增固定服務／分類 ID 的展開資訊，去重並設上限，兼容舊快照。它不儲存帳號、任務內容或登入 token。生活頁以 URL 保存搜尋／分類／免登入篩選與合法群組的展開狀態；服務目的地只帶原有校園白名單參數。

### AI 任務狀態優先於收合

首頁的 Agent 待辦選擇改成收合區，與上方課務清單分工。規劃後的預覽、確認按鈕、未知結果、查核及需要處理的追蹤仍直接顯示。只有已確認沒有可安排的待辦、沒有結果、沒有讀取／錯誤／追蹤／未完成操作時才省略空面板。

候選待辦先依原始來源識別排除已有安排，再取最近三件；前三件已安排不會藏掉第四件尚未安排的作業。同一來源重新讀取時保留選擇區 DOM、展開及鍵盤焦點，暫停安排按鈕；不快取已清空或撤權的舊任務。

Web 與 Mobile 的課務載入與重試不再拆掉助理元件；原有帳號／校園作用域切換仍清除舊草稿與拒絕晚到回應。沒有修改規劃 API、權限、確認、寫入或讀回契約。

### 原生路由一致

失物招領的自然語句捷徑與生活頁入口均指向已有的 `PlatformLostFound`，並補齊跨分頁路由登錄。舊校務失物路由保留供原用途使用；不同來源的訂單也維持原有分流。

合計為本輪直接相關的 **23 個測試檔、799 項測試**；Web 690 項、Mobile 109 項。Menu／Search 的 80 項在補強原生展開狀態斷言後再次通過，課務導覽也在修正來源分流後重跑；重跑不重複計入總數。這是相關流程回歸範圍，沒有宣稱整個 repository 的所有測試均執行。

Web ESLint 的 1 項警告為原有 `app/page.tsx` 第 187 行 `react-hooks/set-state-in-effect`，來自既有首次載入的 `refresh()`。以未修改的 main 同檔透過相同 ESLint 設定重現相同警告；本輪未更動該請求生命週期、未關閉規則，也沒有新增警告。

Mobile 訂單返回測試使用實際 `NavigationContainer`，驗證展開分類、搜尋、進入訂單、返回及清除搜尋後的接續狀態。原生 `details` 的測試直接檢查 `open` 與祖先狀態，避免 jsdom 仍可查到收合內容而產生假陽性。

### 瀏覽器實際檢查

以正式編譯成品啟動獨立預覽，並在真正 Chromium 頁面操作：

- 1363px 桌面寬度：確認首頁待辦／助理／個人工具順序、登入主要區塊先於其他身分、生活頁四組與 7 個常用入口，以及全站目錄的 16 個常用連結。
- 生活頁：展開日常、搜尋「借書」、前往圖書館，再返回；查詢保留，清除搜尋後日常分類仍展開。目的地沒有帶入查詢或展開參數。
- 全站目錄：展開學習與課務、展開成績相關服務、前往 `grades?tab=feedback` 再返回；實際 DOM 的 `group:study` 與 `service:/grades?tab=semester` 均為 `open=true`。
- 窄版：環境禁止 DevTools 裝置模擬，因此使用一般瀏覽器 400% 縮放，實測 `innerWidth=340`、`innerHeight=234` CSS px。首頁、生活、搜尋及登入頁均為 `documentElement.scrollWidth=334`，未出現水平溢出；生活四組皆改為約 295px 的單欄。
- 窄版鍵盤流程：Ctrl+K 開啟服務搜尋、輸入「借書」、前往圖書館再返回，選單仍展開且保留查詢；Escape 關閉並將焦點還給 `SUMMARY`。
- 深色外觀：在獨立預覽的設定切換深色，實際檢查生活頁與服務選單的文字、分隔線、焦點及收合控制；驗收後還原系統外觀與 100% 縮放。

獨立預覽中的圖書館目的頁呈現校園目錄讀取失敗、Google 登入呈現暫時不可用狀態；本輪瀏覽器驗證的是入口、版面與返回接續，沒有把這些畫面誤當成正式登入成功。799 項元件／路由測試使用受控來源，亦不代表真人校務帳號、原生實機或正式後端已完成驗收。
