## 5️⃣ 跨角色事實流測試（最厲害的 demo 點）

### 場景 A：請假鏈
1. 學生身分 → 提交請假
2. 切到教師 → 收件箱出現待審
3. 教師按「核可」
4. 切到家長 → 收件箱出現「孩子請假已核可」
5. 切到系主任 → 出席率即時更新

### 場景 B：成績鏈
1. 教師身分 → 駕駛艙看到「AI 已預批 24 份」
2. 切到 TA → 看到「你負責 16 份，AI 預批 12」
3. 教師覆核 → 發布成績
4. 切到學生 → 收件出現「HW3 已批改：82 分 + AI 個人化檢討」
5. 切到家長 → 週報顯示「孩子 HW3 表現」（不顯示具體分數）

### 場景 C：商家鏈
1. 商家身分 → 「上架咖哩雞腿飯」
2. 切到學生（無花生過敏） → 推薦該菜
3. 切到學生顧晉瑋（花生過敏） → AI 過濾掉該菜，推薦其他
4. 學生下單 → 切到商家 → 看到新訂單

## 🎯 預期口試委員會問的 3 個尖銳問題 + 答案

### Q1：「你說 AI 主軸，但我看到的就是條件式 if-else，跟一般 App 有什麼不一樣？」
**答**：
> 「我們的 AI 主軸有三層：
> 1. **資料層**：每個 mission 都帶 AI 推算的『省下時間』，量化貢獻
> 2. **編排層**：同一個事實（如學生 GPA 下降）AI 會對學生、教師、家長、系主任**生成不同版本**的提醒
> 3. **執行層**：AI 不只『建議』，會替使用者『預先做』（如預批、預訂、草擬訊息）
>
> 您看到的 if-else 是 mission 卡 demo 的呈現；背後 `aiBrain.ts`、
> `aiOrchestrator.ts` 等模組在持續監測訊號、做跨課程關聯。」

### Q2：「9 個角色都做太多了，能聚焦嗎？」
**答**：
> 「我的論點正好相反 — 校園 App 失敗的原因就是只考慮學生和老師。
> 但學生的請假需要家長知道、商家的菜單影響學生選擇、TA 的批改節省教師時間。
> **AI 編排的價值就在角色之間的互通**，少一個角色都講不完整。」

### Q3：「demo 是 mock，正式環境跑得起來嗎？」
**答**：
> 「Demo 隱私模型跟正式環境結構一致 — 訊息查詢都用 viewer + participants 條件。
> 後端 Firestore rules 在 `firestore.rules` 也有對應的 `request.auth.uid in resource.data.participants`
> 規則保證同樣的隔離。Demo 模式只是『不打網路、改讀 in-memory 資料』，
> **權限邏輯完全相同**。」
