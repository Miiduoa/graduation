# 靜宜校園 3D：公開建築輪廓實作與驗收

## 目前入口

靜宜地圖 `/map?schoolId=pu` →「空間導覽」。開啟視窗後，Web 端才初始化 Three.js，並嘗試讀取同站 `/api/public/campus-footprints` 的輪廓快照。取得建築輪廓時，依經緯度換算成公尺後立體擠出；資料讀取失敗時仍提供原本的地點標記、列表與步行導航，不用任何假建築補滿畫面。

請勿把此版本描述為「靜宜數位孿生」、「真實 3D 建築」或「可室內導航」。目前是**以已知外輪廓繪出的建築量體示意**，不包含立面、屋頂、地勢、入口、高精度高度、樓板或無障礙通道。

## 來源與資料邊界

1. 校舍名稱、編號、用途及主顧樓樓層以[靜宜大學官方校園地圖實境導覽](https://www.pu.edu.tw/p/404-1000-1131.php?Lang=zh-tw)核對。官方另有[校史沙鹿校區地圖](https://archives.pu.edu.tw/p/412-1121-4218.php)，僅供核對，不重製照片、校方圖像及 720° 環景。
2. 建築座標及 OSM way ID 沿用專案共用 `packages/shared/src/providenceCampus.ts` 已記載來源的資料。此功能只請求其中 `cross-checked` 且來源為 OpenStreetMap way 的地點，不把公車站、停車場或單點建物硬擠成立體建築。
3. 伺服器向固定的 [OpenStreetMap Overpass](https://overpass-api.de/) 服務查詢指定 way ID，並檢查來源、閉合輪廓、座標是否在靜宜附近、合理面積、重複 way、形狀自交、非相鄰邊界相接與重疊。輪廓必須涵蓋對應的校舍 POI，或其邊界距離該 POI 不超過 30 公尺；避免 OSM way 遷移後仍冠上原校舍名稱。這是資料漂移容差，**不代表入口位置已驗證**。限制最多 128 筆來源圖徵、每棟最多 160 個頂點；避免把外站任意資料顯示成靜宜的校舍。
**名稱漂移保護（2026-11-13）**：OSM 建築圖徵若明確提供 `name`，必須與校方交叉核對的地點名稱一致；若同時有 `name:zh`，則以該中文名稱對照，允許英文主名稱與已核對中文名稱並存；但若 `name` 明確是**另一個中文建築名稱**，即使 `name:zh` 正確也拒絕該輪廓，不讓翻譯標籤掩蓋來源矛盾。缺少名稱標籤的正常建築不因此拒絕；空白、非文字、或明確改成其他地點的名稱，會略過該 3D 外框，保留原 POI、平面地圖及外部導航，待人工比對後才能更新來源白名單／別名。這僅是避免**錯誤建物名稱與 OSM 幾何對應**的程式防護，非校園現地辨識結果；測試使用合成改名資料，不將 OSM 暱稱自動當作校方正式名稱。

4. 即使 way ID 已在白名單內，也要確認 Overpass 回傳仍具有有效的 `building=*` 標籤；`building=school;construction`、`yes;no` 等分號／逗號／直線分隔的多重分類不能被當成完整建築類型，即使其中含有 `yes` 也先略過，避免把須重新核對的 OSM 標籤畫成完好校舍（此為合成資料防錯，並非已發現靜宜真實 OSM 有此異常）。已移除建物標籤或標成 `building=no`、`construction`、`proposed`、`roof`、`ruins` 等不呈現完整建築量體。即使保留 `building=yes`，如同時帶有非否定的 `demolished:building`、`disused:building`、`abandoned:building`、`construction:building` 等生命週期標籤，也先拒絕渲染並待來源重新核對；這類互相矛盾的標籤不能當作建築仍存在或可進入的證據。另檢查 OSM 也常使用的非前綴生命週期標籤（如 `building=yes` 同時有 `ruins=yes`、`demolished=yes`、`construction=yes`），以及 `ruins:building=*`；不將已成廢墟、拆除或施工中的圖徵擠出成完好的地面建築。明確的 `no`／`false`／`0` 狀態不會單憑該欄位排除正常建築。 若生命週期標籤存在卻是空字串、只有空白或非文字／`null`，視為狀態不明，**不繪製完整建築**；只有標籤不存在或明確否定值才可繼續檢查其他條件。此判斷已加入 parser 與公開 API 回歸測試。這是保守的資料呈現規則，不等於每個 OSM 標籤均經實地確認；參考 [OSM 廢墟標籤](https://wiki.openstreetmap.org/wiki/Key:ruins:building) 及[停用／廢棄標籤](https://wiki.openstreetmap.org/wiki/Key:abandoned)。無來源時保留地點標記而不補造建築。此判斷只表示 OSM 圖徵可用於外框示意，**不證明建物目前開放或可進入**。 另外，OSM 的 `area=no` 表示封閉線**不是可填滿的面**；即使同時殘留 `building=*` 標籤與閉合座標，也不將線內部擠出成屋頂及牆面。若有不明確的 `area` 值先略過，沒有此標籤或明確 `area=yes` 才繼續檢查既有建築條件。這遵循 [OSM Key:area](https://wiki.openstreetmap.org/wiki/Key:area) 的面／線語意；新增合成 tag 正反向回歸，**不是靜宜現地核驗**。
**進行中拆除標籤保護（2026-11-13）**：當白名單 way 改成 `building=demolition`／`building=demolishing`，或仍有 `building=yes` 卻出現非否定的 `demolition:building`、`demolishing:building`、`demolition`／`demolishing`，不把其外框畫成完好的 3D 屋頂及牆面，保留原有 POI／平面圖／導航。若明確標示 `no`／`false`／`0`，不能單憑該欄位推斷正進行拆除；空值或未知值仍保守拒絕。參考 [OSM 生命週期前綴](https://wiki.openstreetmap.org/wiki/Lifecycle_prefix) 與[拆除施工的標記討論](https://community.openstreetmap.org/t/how-to-tag-buildings-undergoing-demolition/130350)。本次僅新增合成標籤防錯及 API 不快取回歸，**不代表靜宜有建築正在拆除、亦非真實 Overpass 或現地查核**。

5. 目前只支援地面起算的整棟外框量體；若白名單 OSM way 同時帶有 `building:part=*` 且不是明確 `no`／`false`／`0`，或誤以 `building=part` 標示，**不把它畫成完整校舍**。OSM 的 [Simple 3D Buildings](https://wiki.openstreetmap.org/wiki/Simple_3D_buildings) 明確區分整棟 `building=*` 與多段 `building:part=*`：後者可能只代表不同高度的某個分段。空字串、非字串亦不視作已確認的完整建築；仍保留 POI、平面地圖與導航。這項保護不代表已找出隱藏於其他 way 的所有 3D building parts，也不等於完成了真實建築外觀。已補 parser 與 API 回歸。
6. 若 OSM 另有非零或無法確認為零的 `min_height`／`building:min_level`，代表圖徵可能從高於地面的標高開始；目前量體是由地面直接擠出，無法正確呈現這種高架／架空建築部位，因此**先排除該圖徵**，保留已核對的地點標記與導航，不補造底部牆面。只有明確的零偏移才按一般外框處理。此規則依 [OSM `min_height` 定義](https://wiki.openstreetmap.org/wiki/Key:min_height) 與 [`building:min_level` 定義](https://wiki.openstreetmap.org/wiki/Key:building:min_level) 設計，並有模擬 OSM 標籤回歸，**不代表已實地確認哪些靜宜建築有架空結構**。
7. 若 OSM `height` tag 是可解析的公尺數值，僅用於示意高度；支援明確公尺小數至六位，例如 `18.125 m` 或 `18.125m`，避免把有效的來源高度誤換成 12 公尺。明確的 `50 ft`、`50 feet`、`50'6"` 等英呎／英吋標籤，現在依 `1 ft = 0.3048 m`、`1 in = 0.0254 m` 精確換算；英吋不得達 12，其他單位、區間、逗號小數及超出合理範圍的值仍拒絕。換算結果仍是 OSM 使用者標註，**不代表校方測量或實地驗證**。**只有完全沒有 `height` 標籤**時，才以 12 公尺的視覺示意值繪製；如果標籤明確存在，但值是無法解析的單位、空白、`null`、非文字或不合理數值，會直接略過該立體量體，保留 POI、平面地圖與導航。不得把「資料明確矛盾或格式未知」與「沒有高度資料」混為一談，憑空畫成 12 公尺。OSM 使用者標註不等於校方或實地測量。`building:levels` 不用公式直接猜高度。此解析有模擬標籤回歸，但實際靜宜 way 是否含此格式仍待線上查核。
8. 立體化來源需顯示 **© OpenStreetMap 貢獻者** 與[授權資訊](https://www.openstreetmap.org/copyright)。OSM 原始資料遵循 ODbL；如未來將修改後的建築資料對外散布，需再檢查相應署名與資料庫授權義務。正式產品應確認快照更新、API 使用政策與容量。

## 步行導航目的地與無障礙提示

空間導覽的「開啟步行導航」沿用目前所選的校園地點**座標**開啟外部地圖，並不是經查證的建築入口、道路拓樸或無障礙路線。先前按鈕只顯示「開啟步行導航」，容易讓現地使用者誤以為系統已驗證可走到入口。本版在連結旁新增常駐的短句提醒，並透過 `aria-describedby` 將警語關聯到外部導航連結，讓螢幕閱讀器在操作連結時也能得知限制；不改寫原始 POI 座標或外部目的地參數，也不擅自引入未查證的路網。回歸驗證跨校共用情境中目的地經緯度、步行模式、警語可見性與輔助科技關聯。這是目的地風險揭示，**不是已完成靜宜校園的實地找教室／無障礙通行驗證**。

## 選定校舍的高度來源標示

空間導覽選定靜宜校舍後，詳細資訊會對**該棟**通過檢查的 OSM 外框說明高度依據，而不只在全校資訊列寫「OSM 標註或 12 公尺示意」。若來源有合法的 `height`，顯示轉換後公尺數與「OSM 使用者標註，非校方實測」；若沒有高度標籤，只顯示「12 公尺示意，非實際樓高」。已選地點沒有可用外框時，明確寫明只顯示原地點標記、**不是已確認的入口**；在地圖套用同校地點篩選後，選取資訊依當下可見外框重算，不延續已被篩掉的舊高度。

這是 React 元件與資料來源呈現修補，回歸使用合成 OSM 資料的三種情境（標註、示意、無外框）；**未進行真實 Overpass 逐棟查核，也不能據此宣稱現地樓高或導航正確**。

## 3D 地點標記與中庭邊界

OSM 外框與中庭是平面幾何，不是量測過的屋頂可達區域。對於 **OSM 明示公尺高度**的校舍，只有地點 POI 嚴格位於外環內、且不在中庭內或任何外環／內環邊界上，才將其 3D 標記放到量體頂部；示意高度則始終保留地面標記。先前的射線法在矩形中庭**右側邊緣**會把恰好落在邊上的地點判定為「不在中庭」，錯放到屋頂。本次新增邊緣距離核對，邊界點一律保守顯示在地面。此處僅用極小的經緯度浮點捨入容差，不宣稱測得牆厚、實際入口或可通行動線。`campusSpatialScene.test.ts` 已加入中庭內、右側內環邊界、外環邊界及真正屋頂內部的對照回歸；仍需正式 CI 與現地驗證。

## 可靠性

- **非完整 HTTP 2xx 回應不作為建築來源**：公開 Overpass 完整 JSON 查詢只接受 HTTP `200 OK`。Fetch 的 `response.ok` 對 `203 Non-Authoritative Information` 與 `206 Partial Content` 仍為 true，但這些狀態不足以證明取得完整、未被代理改寫的 OSM 輪廓；即使 body 可解析為合法 JSON，也不建立新的 24 小時快照。異常回應立即嘗試取消未讀串流，依既有 503／`no-store`／10 分鐘冷卻流程處理；先前仍在七天期限內的已驗證快照維持標示來源日期的 `stale` 備援。新增 203、206 及原有快照更新遇 206 的 API 回歸；**尚未取得真實 Overpass 發出此類狀態的樣本**。

- **拒絕無法確認的 HTTP 內容編碼（2026-11-13）**：上游 `Content-Encoding` 缺省或明示 `identity` 時才進行未壓縮回應的位元組數核對；可辨識的單一 `gzip`、`br`、`deflate` 仍依 Node Fetch 解碼後 500 KB、編碼長度 1 MB 界限處理。若代理回傳空白、未知編碼或混用／疊加多個編碼（例如 `gzip, br`、`identity, gzip`），不因它「不是 identity」就跳過未壓縮的長度核對並將 JSON 快取為可靠輪廓，而是取消未讀 body、回傳 503／不快取，遵守原有冷卻與舊快照備援。新增 4 組異常編碼拒絕、1 組不等待卡住串流取消，以及 4 組允許格式的合成 API 回歸；**沒有進行公開 Overpass 或 CDN 的真實壓縮傳輸驗證**。
- **壓縮傳輸宣告零位元組（2026-11-13）**：`gzip`、`br` 或 `deflate` 若帶 `Content-Length: 0`（含 `000`），表示編碼後傳輸沒有任何內容，不可能同時解碼成有效 OSM JSON。原版因為壓縮傳輸不適用「宣告長度＝解碼後長度」核對，會錯誤接受這類自相矛盾的已解碼 body。現在在讀取 body 前拒絕、best-effort 取消流、回傳 503／`no-store` 並延用冷卻及舊快照備援；無長度標頭與合法的非零編碼長度仍照原規則處理。新增 3 組零長度編碼拒絕與 1 組不等待卡住串流取消測試；全為合成資料，並非聲稱真實 Overpass 曾回覆此標頭。
- **HTTP `Content-Length` 格式必須正確**：若 Overpass 或中介代理宣稱有回應長度，只接受純十進位非負整數，且在未壓縮時不得超過 500,000 bytes；若為 `gzip`／`br` 等壓縮傳輸，編碼後長度另設 1,000,000 bytes 防護界限，解碼後仍以 500,000 bytes 為上限。空字串、科學記號、十六進位、小數及超大數一律拒絕並嘗試取消未讀串流；不能把 `Number()` 可轉換的字串誤認為合法 HTTP 長度。沒有此標頭的合法分塊回應仍按逐塊解碼 byte 上限讀取。新增模擬回歸驗證無效長度在 12 秒總逾時前快速回傳 503／`no-store` 且不反覆回源。尚未取得公開 Overpass 真實異常標頭樣本。

- **拒絕上游重新導向，守住伺服器出站範圍**：Overpass 查詢僅使用固定 `https://overpass-api.de/api/interpreter`，並設定 Fetch `redirect: 'error'`。若來源回傳 `Location` 指向其他網站、內網位址或同站其他路徑，伺服器不自動跟隨，依既有 503／`no-store`／冷卻備援；避免固定公開資料源被 3xx 改寫為任意伺服器請求。新增模擬 302 指向 `127.0.0.1` 的 API 回歸，驗證 Fetch 選項、拒絕與快取隔離；另外以 Node.js 22 原生 Fetch 的本地 HTTP 重新導向試驗核對 `redirect: 'error'` 不會請求目標。**不是**對公開 Overpass 真實連線或內網漏洞的入侵測試。若未來合法換網址，需重新審查固定端點與來源政策，不自動信任跳轉。

- **服務端完整請求期限**：除了向上游傳送 `AbortSignal`，伺服器現在對 **fetch 與串流 body 讀取整段流程**設 12 秒獨立期限。即使不可靠代理不回應中止訊號、連線或回應本體永遠不結束，也能解除共用 pending 狀態，依原 10 分鐘失敗冷卻回傳 503／no-store；沒有直接將失敗的資料當作有效輪廓。新增 2 組假上游「永不回應」與「headers 已收到但 body 永不結束」的受控時鐘回歸，另驗證冷卻後可以重新取得輪廓。**這是伺服器 request 狀態的防卡住測試，不代表公開 Overpass 或實機網路已實測**。中止訊號不受遵守時，底層連線的釋放仍取決於網路實作；正式高流量需額外監控連線與並行資源。
- **超量／異常 Content-Length 先行拒絕**：若未壓縮上游 HTTP 標頭明示超過 500 KB，或壓縮傳輸明示超過 1 MB，或長度格式非法，伺服器尚未讀取 body 即回到 503／冷卻流程，同時對尚未讀取的串流發送 best-effort 取消，不把已拒絕的回應留在背景傳輸。即使 `cancel()` 永不完成也不會阻塞 API；新增超量及多種非法標頭格式的模擬回歸，要求 1 秒內結束且避免再次回源。此測試只驗證應用層取消訊號，不保證代理／TCP 已立即斷線。
- **超量回應的取消不阻塞 503**：逐塊串流讀取超過 500 KB 時，取消上游 reader 仍會發出，但**不等待 `reader.cancel()` Promise** 才結束原本已確認的超量錯誤；有些代理或串流在取消後永遠不 settle，舊行為必須拖到 12 秒整體 deadline 才回傳 503。新增永不完成的 `cancel()` 模擬，要求 1 秒內（遠短於整體 deadline）得到 503／`no-store`，避免無效資料持續佔用共用 pending 狀態。取消底層網路資源仍屬 best-effort，且本測試不是公開 Overpass 實際傳輸量測。
- **Overpass 資料庫同步時間**：若上游 JSON 附帶 `osm3s.timestamp_osm_base`，會另外檢查它是否為有效 UTC 日期、沒有超前伺服器時間逾五分鐘，且與查詢當下相差不超過 **48 小時**；否則不將整份輪廓誤標成最新快照，改走既有舊快照期限或 503／地點標記備援。這是上游**資料庫複寫狀態**，不是建築 way 最後編輯日期，也不是實地確認時間。若回應**整個省略 `osm3s`**，為相容舊格式／既有測試資料，仍只依建物白名單、幾何與抓取時間檢查；但**明確包含 `osm3s` 卻缺少 `timestamp_osm_base` 或設為 `null`**，屬來源同步日期不完整，現在會拒絕新快照，保留先前有日期標註的合格過期備援或回傳 503。此修補有拒絕新快取、保持舊快照的回歸案例；**尚未取得真實 Overpass 成功回應**。
- **同步延遲會縮短新鮮快照壽命**：有合法 `osm3s.timestamp_osm_base` 時，新鮮快取期限取「HTTP 抓取後 24 小時」與「OSM 資料庫同步後 48 小時」較早者。若資料庫已落後 47 小時 30 分，建築快照最多只可再被標成新鮮 30 分鐘，CDN `s-maxage` 也不得超過該期限；到期後需重新詢問上游。若上游仍未追上，走既有有日期標示的舊快照／503 備援，不假稱資料仍新。缺少同步 metadata 的舊格式仍沿用原 24 小時快取規則。已補受控時鐘回歸，真實 CDN 與 Overpass 時延尚待驗證。
- **瀏覽器再次檢查同步時效**：即使 CDN 或中介快取仍回傳 `stale=false`，只要裝置端計算已達 `OSM 資料庫同步時間 + 48 小時`，前端也會把仍在七天備援期限內的輪廓標記為「暫用舊快照」，不誤稱最新；`osmBaseAt` 缺省的舊回應仍依原 HTTP 抓取後 24 小時標準判斷。這是前端的二次防護，不代表已完成線上 CDN 或校園現況測試。
- **日期顯示不混淆**：API 另外傳回經來源驗證的 `osmBaseAt`，3D 視窗同時標示「資料讀取」與「OSM 資料庫同步」。兩者不可互稱，且都不是實地查證日期。前端會再次檢查同步時間的 UTC 格式、與原始快照抓取時間的先後關係（最多 5 分鐘時鐘差），以及兩者不超過 48 小時；遭修改的異常來源日期不得在視窗顯示為可靠資料。沒有 `osm3s.timestamp_osm_base` 的舊快照保留既有輪廓檢查，但不憑空顯示同步日期。此處以 mock API／React 回歸驗證，尚未確認公開 Overpass 真實同步時間。
- 服務端有 24 小時記憶體快照，CDN 公用快取最多 1 小時且**不可超過該快照剩餘有效秒數**：例如在快照失效前 10 秒讀取，回應 `s-maxage=10` 而不是額外快取 1 小時。快照過期後必須回源確認，失敗時依下方規則標示舊資料或停用建築，不延長「最新」狀態。此行為已有模擬時鐘與 HTTP 標頭回歸；尚未在真實 CDN 驗證。
- 服務端有 24 小時記憶體快照、同時請求共用、一般上游失敗後至少 10 分鐘冷卻；若 Overpass 回傳 HTTP 429／503 並提供有效 `Retry-After`（秒數或 HTTP 日期），尊重較長的伺服器等待要求（上限 24 小時），並回傳對應剩餘等待秒數供客戶端參考。不會在被限制時每 10 分鐘強制重試。避免使用者每次開 3D 都直接對 Overpass 發出大量請求。另有 500 KB 逐塊串流回應上限及識別 nuni 的 User-Agent，避免惡意／異常回應一次耗盡記憶體並符合公開 Overpass 的使用辨識要求。跨多台伺服器的冷卻不會共享；若流量成長，應改成受控的離線定期快照，而不是大量查公開 Overpass。
- 向 Overpass 請求 `out meta geom`，公開輪廓附 OSM way 版本與最後編輯時間（僅保留 `version`、`timestamp`，不回傳編輯者帳號等資訊）；在選取建築時顯示。**圖徵最後編輯時間不是資料抓取時間，更不是現場查證時間；OSM way 的節點可能移動而不改變 way 版本。** 舊快照或缺少合法 metadata 時不虛構版本；若 way 最後編輯時間比伺服器／裝置時鐘超前逾五分鐘，也只移除不可信的版本與日期，保留已通過獨立位置／建築標籤／外框驗證的輪廓，不宣稱該筆編輯時間已核實。
- **非成功 HTTP 回應也要釋放串流**：`fetch` 在收到 HTTP 標頭後即完成，Overpass／代理回傳 406、429、503 或其他非 2xx 時，錯誤回應的 body 仍可能持續傳送。既然我們只需要狀態碼與 `Retry-After`，後端現在會對未讀取的錯誤 body 立即發出 best-effort `cancel()`，不等待取消 Promise 才進入既有冷卻／503；避免已確知的上游拒絕仍持續佔用無用串流。新增 406／429／503／500、取消永不完成的模擬回歸，檢查快速結束、`no-store`、冷卻與不重試。這只證明應用層發出取消，**不代表公開服務已解除拒絕或代理的 TCP 連線已實際釋放**。
- **HTTP 406 存取阻擋保護**：公開 Overpass 伺服器若回傳 406（可能代表 User-Agent／來源遭拒），不再每 10 分鐘對同一來源重試，而是於目前服務實例暫停回源至少 **24 小時**。無快照時 API 回傳 503／`no-store` 與剩餘 `Retry-After`；仍在七天期限內的既有快照只作**標日期的舊資料備援**，不重新標為最新。此決策避免因反覆查詢加劇公共服務的拒絕／封鎖；回應 406 的根本原因仍須查看服務端記錄與上游政策，**24 小時並不保證解除封鎖**。已新增受控時鐘 API 回歸，非即時線上解除封鎖驗證。參考 [overpass.ch 對 406 與封鎖的說明](https://overpass.ch/guides/overpass-api-ip-banned)。
- 公開 Overpass 可能因負載限制回傳 429／503。現在會識別 `Retry-After` 的秒數或 HTTP 日期，遵守較長的冷卻並在舊快照仍有效時繼續標示舊資料。無快照時維持 503／`no-store`，不將 429 當成成功抓取建築輪廓。測試使用模擬回應，**不等於實際對公共 API 的容量或 SLA 驗證**。
- Overpass 回應若同時包含兩筆相同的**已核對建築 way ID**，即使其一的輪廓與標籤看似正確，也拒絕整份回應；同一圖徵不可能在一次查詢中同時具有兩種高度或外框。不能依回應順序默默取第一筆並宣稱來源可信。其他未列入建物白名單的圖徵不影響既有安全資料。已加入 parser 與 503／不快取 API 回歸。
- 除了服務端拒絕重複的已核對 OSM way ID，**前端也拒絕 API 快照中重複的已核對校舍 POI ID**，不論重複項的樓高、名稱或外框是否合法、順序如何。出現矛盾時整份校舍量體快照不呈現，保留原地點標記、步行導航及手動重試入口；非白名單的停車場或其他地點不會冒充校舍。已新增來源重複、異常第二筆與調換順序的回歸案例。這是防止資料混淆，不是線上 OSM 的逐棟實地證據。
- Overpass 的 JSON **即使 HTTP 200 也可能附帶 `remark`**（例如查詢逾時、記憶體不足），且 `elements` 可能只回傳部分結果。API 現在會拒絕所有帶頂層 `remark` 的回應，不把局部建物當成 24 小時完整成功快照；已有快照時依下述期限顯示過期備援，否則 503。此情況納入 API 回歸測試。參考 [Overpass 回應錯誤說明](https://overpass.ch/guides/overpass-api-errors)。
- 已有快照但更新失敗時會回傳來源時間與 `stale`，前端標明「暫用舊快照」。**HTTP 抓取日期或可驗證的 OSM 資料庫同步日期滿七天（取較早失效者）即不再提供舊建築輪廓**，改回傳 503 並保留原地點標記／平面地圖／外部步行導航，避免把長期失效資料看成現況。七天只是過期防護門檻，不等同現場核實期限。首次無快照且連線失敗時也只顯示原地點標記。

- **校園地圖篩選時同步限縮建築**：空間視窗仍開啟時，若使用者切換為只顯示部分地點，3D 只接受目前 `model.points` 內的 POI 所對應建築輪廓。畫面上的「公開建築輪廓」棟數、選定地點的 OSM 版本資訊及相機最高量體取景，都以目前可見 POI 為準；已被篩掉的舊輪廓不應暗中拉遠視角或在資訊列繼續計數。用同校清單更新的元件回歸與無可見 POI 的 Three.js 相機斷言保護這個行為。這是模擬地圖清單／WebGL 邊界測試，並非手機 GPU 實測。

- Three.js 僅在開啟空間視窗時載入；對話框關閉、場景失去可見性或 WebGL 失敗時沿用原本的資源釋放、焦點、鍵盤、低動態與備援流程.前端建築輪廓請求最長等待 15 秒（含回應本體讀取），逾時中止請求，**即使上游代理或回應本體不遵守 AbortSignal、Promise 永不結束，也會獨立結束讀取提示**，保留原有 POI、平面地圖與步行導航。逾時後才到的合法資料不可重新覆蓋失敗狀態；使用者可自行重新讀取。元件回歸模擬不遵守 abort 的延遲回應與逾時後成功，驗證不會無限等待或使用過期請求結果。此測試不代表公開 Overpass 線上可用性、手機實機效能或現地驗收已完成。
- 前端對回傳資料再次檢查學校 ID、建築 ID、來源網址、名稱、範圍及數值，阻止跨校或惡意輪廓混入。另要求 API 快照明示 `OpenStreetMap`、標準 ISO 抓取日期與布林 stale；若裝置時間判定抓取日期或已提供的 OSM 資料庫同步日期已達七天、日期非法或超過五分鐘的未來時間，一律不顯示舊建築。即使快取錯報 `stale=false`，滿 24 小時仍顯示舊快照提示；裝置時鐘大幅失準時會保守回到 POI 與步行導航。尤其 `illustrative` 高度必須嚴格等於固定 12m，不能接受外部 API 中自行膨脹的 99m 示意樓高；若回應不一致，該建築不會顯示，保留原有 POI 導覽。

- **POI 與屋頂圖釘的對位**：OSM 外框可能在既有 POI 位置附近（允許最多 30 公尺誤差），但 POI 並不一定落在建築多邊形內。原本只要接受輪廓，就會把 POI 圖釘升到該棟示意／OSM 高度，造成屋頂以外的空中漂浮圖釘。現在只有 POI **確實位於已接受外框內，且 OSM 具有可解析的來源高度標註**才使用屋頂高度。若 OSM 沒有高度資料，即使 POI 落在建築外框內，12 公尺也只是視覺示意量體，圖釘必須留在原地面座標；外框外的 POI 也保留地面標記和資訊操作。建築量體及相機取景仍保留。新增來源外框內／距外框約 18 公尺的**合成**案例，檢查 Three.js 實際圖釘矩陣與建築擠出數；不把 POI 自動改寫成入口、教室或步行終點，也不將合成資料宣稱為靜宜現況。


- **上游回應讀取逾時也必須取消 body reader**：`fetch` 已拿到 200 標頭後，回應內容仍可能只傳一部分便停止；單靠中止原先的 `fetch` 不一定會取消已交付給 `ReadableStream` 的讀取器。現在 12 秒伺服器 deadline 會額外向 body reader 發送取消要求，不等待可能永遠不完成的取消 Promise；被中止的分段 JSON 不得被當成完整 OSM 快照。新增先送出語法完整的 JSON 片段、但永不結束串流的 API 回歸，檢查取消、503／`no-store` 與不快取。Node.js 22 原生串流的獨立重現觀察到取消要求一次且等待中的 read 結束；**正式專案測試、線上 Overpass 實況及網路連線是否真正釋放，仍以新 head CI／現地驗證為準**。

- **非地面 OSM 圖徵不擠出為地面校舍**：即使 way ID 已在校園白名單內，後續編輯仍可能帶入 `location=underground/underwater/roof/overhead`、非零 `layer`、`bridge=yes` 或 `tunnel=yes`。目前立體化只支援從地面開始的整棟外框；沒有可靠的基底高程、上下層幾何時，這些圖徵必須被排除，而不是把地下空間或懸空建物繪成從地面延伸的牆。沒有定位標籤、明示 `location=surface`／`layer=0` 與 `bridge=no` 等否定旗標時，仍須通過原有 way 白名單、座標、外框及樓高檢查。新增加 OSM parser 的正反例及 API 503／`no-store`／冷卻回歸，使用**合成標註**，不代表已發現靜宜真有地下或橋上校舍，也未完成實際 Overpass 抽樣。參考 [OSM location 語意](https://wiki.openstreetmap.org/wiki/Key:location) 和 [建築局部／基底高度](https://wiki.openstreetmap.org/wiki/Key:building:part)。

## 固定校舍 ID 查詢的公開服務資源預算（2026-11-13）

固定白名單的 Overpass QL 使用 `[timeout:8][maxsize:67108864]`：將查詢計算時間設為最多 8 秒、宣告記憶體上限 64 MiB，不要求公開服務為這個小型校舍 ID 集合預留預設 512 MiB。服務端另有**完整 fetch／回應主體 12 秒**的獨立 deadline，因此即使查詢接近上限，仍預留網路與 JSON 傳送時間；前端原有 15 秒逾時與 POI／導航備援維持不變。參考 [Overpass 官方資源預算說明](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)。這是降低不必要的排程資源宣告，**不是**已證實真實 Overpass 在 64 MiB／8 秒內完成，也不是已驗證靜宜逐棟輪廓；若公開服務出現 timeout、remark 或資源限制，仍應保守拒絕不完整快照，不自動擴大無上限的請求。

## Overpass HTTP 200 主體長度完整性

本版額外核對 **identity（未壓縮）** 的 HTTP 回應 `Content-Length` 與實際讀取的 UTF-8 位元組數。如果雖為 HTTP 200、JSON 格式也正確，但完成串流後位元組數少於／多於標頭宣告，一律視為不可信的 Overpass 快照；不建立 24 小時新鮮快取，改用既有 503／冷卻／有日期舊快照備援。對沒有 `Content-Length` 的 chunked 回應，仍採既有 500 KB 解碼位元組上限與 12 秒 deadline。

對 `Content-Encoding: gzip`／`br` 等壓縮回應不直接比較兩者：Node Fetch 可能將 body 解壓後提供給程式，但保留壓縮前網路回應的 **編碼後長度** 標頭，兩個位元組數本來就不同。壓縮傳輸的宣告長度另設 1 MB 防護界限，不拿其編碼後長度誤當解碼後大小；所有編碼仍受解碼後 500 KB 上限保護。新增合成「壓縮 wire 長度 500,001 bytes、解碼後合法 JSON」、超量解碼 JSON 與編碼後超過 1 MB 的快速取消回歸。這些是 Fetch 標頭／body 合成測試，不代表已取得真實 Overpass 壓縮流量或解決所有代理行為。新增 HTTP 200 合成有效 JSON／錯誤長度、匹配長度及模擬已解壓 Fetch 回應之回歸，**不是對真實 Overpass 發生部分回應的證據**；對無長度標頭且回傳有效但不完整 JSON 的情況，仍須另外以線上來源核查。

## HTTP 200 仍宣告區段內容時拒絕快取

即使上游回傳 `200 OK`、主體是合法 OSM JSON，只要同時帶有 `Content-Range`，仍視為中介代理回應契約矛盾／可能為部分內容，拒絕建立建築快照，並要求對未讀的串流發出 best-effort 取消。保留原有 `503`、`no-store`、重試冷卻與有日期舊快照備援。新增合成 HTTP 200＋`Content-Range` 回歸，驗證回應不會建立或替換可信的建築資料；**未觀察到公開 Overpass 真實回傳此異常**。此防護不代表已完成線上逐棟幾何／入口查驗。

本次另依 [CI 42969972487](https://github.com/Miiduoa/graduation/actions/runs/42969972487) 的失敗紀錄，修正跨模組 Web 限時動態測試對 React 被動 effect 清理時機的非同步斷言（`revokeObjectURL`）。只調整測試等待，不變更社群功能或公開權限；此 CI 失敗和靜宜建築輪廓無關，不應稱為地圖功能錯誤。

## OSM way 節點閉合身分（2026-11-12）

OSM 的「閉合 way」除了第一與最後一筆座標相同，**首尾必須引用同一個 node ID**。
兩個不同 OSM 節點就算剛好有相同經緯度，來源仍可能是未閉合的線，
不能當作有完整屋頂與牆面的建築。當 Overpass 回應含 `nodes` 時，
目前會同時檢查節點 ID 為正整數、數量與 `geometry` 頂點數一致、
首尾 ID 完全相同，以及**除結尾閉合節點外不得重複任何內部 node ID**。
若同一 OSM 節點 ID 被安排在不同幾何位置，即使座標外框本身合法，
仍是互相矛盾的來源結構，拒絕該 way（含 relation outer/inner 成員），
不憑座標自行替來源閉合。當 relation 外環與中庭內環**都提供** `nodes` 時，還須檢查兩環沒有共用 node ID；同一 OSM 節點不能在不同座標代表兩個角落，也不能用共用節點表示彼此分離的庭院。若上游未提供 `nodes`，仍沿用原有幾何閉合、
自交及白名單驗證，不冒稱已完成節點 ID 核對。新增合成正反例，
尚未拿真實 Overpass 回應測試此新分支，既有地點及跨校共用架構不變。

## 上游冷卻時間與手機重試介面

若 Overpass 回應 **HTTP 400（查詢無效）、403（拒絕存取）或 406（來源拒絕）**，後端不再每 10 分鐘重送相同固定查詢，而是至少冷卻 24 小時並對用戶端提供 `Retry-After`。持續重送無效查詢／已遭拒絕的請求可能造成公開服務停權；參考 [Overpass 服務使用與封鎖說明](https://overpass.ch/guides/overpass-api-ip-banned)。**429、503** 仍依上游合法 `Retry-After` 判斷（最少 10 分鐘、最多 24 小時），其他一般錯誤維持 10 分鐘。冷卻時不捏造新建築：未滿七日上限的既有快照標示過期，否則退回 POI／平面圖／外部導航。已擴充 400／403／406 模擬 HTTP 回歸，包含未讀 body 取消、24 小時不重送、到期恢復、舊快照保留；**不是線上 Overpass 出現這些狀態的實測**。

後端 `/api/public/campus-footprints` 遇到來源故障或限制時會回 HTTP 503，可能附上 `Retry-After`（秒數）。3D 導覽現在讀取合法的正整數秒數（最多採用 24 小時），顯示約略剩餘分鐘數，並在冷卻期間停用「重新讀取建築輪廓」。到期可以重新嘗試，但不能保證公開 Overpass 已恢復；地點選擇、平面地圖與既有步行導航仍可使用。缺少或異常 `Retry-After` 時，保留既有手動重試，不從未知標頭推測服務狀態。

React 回歸以**合成** 503 與 `Retry-After: 600`，檢查 10 分鐘內按鈕停用、不重複呼叫 API、原有步行導航可用，待冷卻到期後可以重試並顯示合法回應。這不是公開 Overpass 的真實限流測量，也不表示現地路線或校舍入口已驗證。

若手機瀏覽器將導覽分頁放到背景、節流或暫停計時器，回到頁面時會透過 `pageshow`／`visibilitychange` 重新對照**原本伺服器提供的絕對冷卻期限**，並在前景每分鐘更新剩餘分鐘顯示。已到期即重新開放手動重試，不須等待可能被延遲的舊計時器；不到期時仍停用按鈕。切回頁面**不自動呼叫 API**，原地點和導航保持可操作。新增合成 503／10 分鐘以及瀏覽器恢復事件的 React 回歸；不等於真實手機背景排程或公開 Overpass 限流實測。

## OSM 圖徵修訂時間與資料庫時間一致性

若 Overpass 提供的建築 way 最後編輯日期晚於該回應的 `osm3s.timestamp_osm_base`（容許最多五分鐘來源時鐘差），不能把這筆版本號／日期當成可信的來源證據。伺服器會移除相互矛盾的 way 版本與編輯日期；瀏覽器也會在接到快照後再次防護。若回應未提供資料庫同步日期，使用本次 HTTP 抓取時間作為最晚上界。**已通過獨立白名單、外框與建築標籤檢查的幾何仍保留**，其高度來源與示意限制不變。此驗證不能代替 OSM 節點的幾何更新查核，更不代表現地測量。

新增 API 與瀏覽器資料解析的合成回歸，涵蓋編輯時間超前來源快照、不超前及缺少同步日期的舊格式；真實 Overpass 與靜宜逐棟對照、同裝置競品驗收仍未完成。

## 失效備援期間仍可重試，不清空舊 3D

當 Overpass 更新失敗、後端仍提供未逾七日上限的**有日期舊快照**時，API 維持 HTTP 200 與 `stale=true`／`private, no-store`，並在後端冷卻期附 `Retry-After` 秒數。前端同樣檢查合法的冷卻秒數，禁用過早重試；**即使回應是 200，也不把舊資料誤當新鮮輪廓**。

現在舊快照資訊區可手動「重新讀取建築輪廓」。重試等待中仍保留先前合格的舊 3D 量體、來源日期與步行導航，不會因載入狀態讓舊圖突然消失；若網路逾時或失敗仍繼續標示舊資料，不以沒有驗證的新幾何覆蓋。取得成功的新快照才取消舊資料狀態。合成 API／React 測試涵蓋 90 分鐘來源冷卻、剩餘時間、等待期間仍顯示舊輪廓、連線失敗後保留及更新成功後清除舊資料標示。

這只是**受控 API 回應與 React 模擬**，不代表已於靜宜現地確認 OSM 建築、真實入口／路網，亦非 Safari／Android GPU 或競品的量測證據。

## 舊快照更新失敗的可見回饋

若使用者手動更新有日期的舊輪廓，但網路請求失敗、回應不符來源契約或在 15 秒內未完成，導覽會在保留舊 3D、OSM 來源日期與步行導航的同時，顯示「更新未成功」；不會讓重試結束看起來像成功同步。再次開始手動更新會清除上次失敗訊息，成功取得合法快照後維持清除。原有冷卻時間與七日資料上限不變。React 合成回歸增加失敗訊息及重試／恢復後清除斷言；尚未實測手機輔助科技或靜宜現場 Overpass。

### 2026-11-11｜已開啟空間視窗的資料年齡保護

### 2026-11-11｜相同 OSM 建築清單重新排序，不再觸發不必要的場景重建

在已驗證的多棟建築快照中，同一組 POI、來源、修訂、高度及外框可能因上游／中介序列化順序不同而排列不同。先前一致性比較以陣列索引對齊，即使全部建築內容相同，只要次序改變就交給 React 一個新陣列，可能導致 Three.js 場景重建。現在依唯一 POI ID 對照，完整比對所有建築來源標記與各頂點座標；**只換順序**則沿用舊陣列參考，任何建物增減、修訂、樓高或外框變動仍更新。來源若出現重複 POI ID，絕不視為相同快照。新增合成 Vitest 範例，涵蓋順序反轉、修訂／座標變更及重複 POI。Node 22 的獨立純函式型別檢查與 9 種斷言通過；目前 stacked PR 的正式 Vitest、Spatial Browser、CI、CodeQL 尚無對應 head 的驗證紀錄，也沒有手機 GPU 基準測試數據。這不證明任何一棟校舍或路線的現地正確性。


### 2026-11-12｜已刪除或明示不可見的 OSM 建築不產生 3D

即使靜宜來源白名單 ID、building 標籤與多邊形座標都符合既有檢查，若上游 OSM 元素明示 `visible=false`（或帶有格式矛盾的 `visible` 欄位），不得用其歷史／不可信幾何重建「現存」建築。現在對外層 way／relation 以及 relation 的 outer／inner 成員分別檢查可見性；未提供欄位（正常 Overpass 回應常見）或明示 `visible=true` 保留原有流程。偵測到不可見元素即撤除該棟 3D，原有地點、OSM 署名和平面導覽不受影響。

此修補使用**合成異常 OSM metadata** 測試，而非宣稱已發現靜宜或公開 Overpass 真實回覆 `visible=false`；未證實實地建築現況、實際建築高度、入口與可走路線。正式測試結果以對應 commit 的 CI／Spatial／CodeQL 為準。

### 2026-11-12｜同一 OSM 閉合節點必須只有一個座標

當 Overpass 提供 way 的 `nodes` 與 `geometry` 時，先核對首尾是同一 node ID，再要求該 ID 的首尾**經緯度完全一致**。舊解析器允許首尾相差不超過 `1e-9` 度的幾何容差；若兩端明確宣稱是同一 OSM 節點，卻被提供成不同座標，就不能用容差補成封閉屋頂。新檢查同時套用一般建築 way 和希嘉學苑 relation 的外環／中庭內環；不符合則不產生該建築 3D，仍保留已核對 POI 及外部導航。未附 `nodes` 的既有幾何格式仍走原容差檢查，**不宣稱已驗證 OSM 節點身分**。

已加入合成的 `5e-10` 度端點差異與合法閉合正反例測試；這不表示已觀測到真實 OSM 具有矛盾節點，也不代表完成靜宜實地校舍或競品驗收。正式 CI、Campus Spatial Browser、CodeQL 必須核對此提交的 head。


### 示意高度的視覺辨識（2026-11-12）

在 3D 場景裡，**沒有 OSM 公尺高度標籤**的 12m 示意建築改用半透明、低飽和量體；具有可解析 OSM 高度標籤的建築保持不透明。選取建築和切換明暗模式時仍保留這個區別，避免看起來都像同等可信的實測立面。OSM 高度標籤本身**不等於校方測量**；任何量體都不代表入口、樓層、屋頂或實際可通行路徑。已加入合成 Three.js 物件/材質回歸，真機 Safari/Android 和視覺辨識度尚待驗證。

## 連續失敗的 Overpass 回源保護（2026-11-12）

公開 Overpass 固定查詢在網路中斷、來源格式異常或其他連續回源失敗時，不再永遠每 10 分鐘重試。
在**同一 Node.js 程序**內，連續失敗的冷卻從 10、20、40、80 分鐘逐次延長，最多 24 小時；
先前對 HTTP 400／403／406 的 24 小時冷卻及合法 429／503 `Retry-After` 都只可能延長、不會被縮短。
成功取得可通過既有來源與幾何驗證的快照才將連續失敗次數歸零。冷卻期間保持已核實且
未超過七天保留上限的過期輪廓標示，逾期即退回校園 POI／平面地圖，不虛構建築或路線。

即使使用者將已開啟的 3D 視窗停留多日或手機背景頁延遲執行計時器，前端也以「伺服器抓取時間／OSM 資料庫同步時間各自七日」的**較早期限**為硬上限。逾期立即移除舊 3D 外框與舊日期，保留校園地點、平面圖與外部導航；有在途刷新也不能因失敗／逾時讓已逾期外框復活，只有取得重新驗證的新快照才恢復。React 合成回歸覆蓋背景恢復、期限計時器、刷新成功／失敗／逾時；尚非現地導覽驗收。

新增受控 `fetch` 失敗回歸測試，驗證前兩次為 600／1200 秒、冷卻中不重送、成功後恢復
600 秒起算，以及過期快照日期仍可見。當五個訪客同時等待**同一個失敗的上游請求**時，
只記一次失敗，避免把五個等候者誤當成五次查詢，立即拉長到數小時。這些是合成來源測試，
**不代表真實公開 Overpass 連線驗收**。
此計數器及快取僅位於單一伺服器程序；多執行個體／serverless 冷啟動時不具跨執行個體
限流保證，正式大規模流量前仍應使用可共享的來源快取或鎖定機制，並遵守公共服務用量政策。


### 跨建築 OSM node ID 一致性（2026-11-13）

同一份 Overpass 回應裡，不同已核對校舍的 way（含 relation outer／inner）可能引用相同 OSM node。**同一 node ID 只能代表同一組經緯度**；即使各自的建築外框都閉合、面積與 POI 距離合理，若跨建築把同一 node 指到相距很遠的兩個位置，整份來源快照就不可信。解析器現在會在建立 3D 前交叉檢查有提供 `nodes` 的已核對 way／relation 成員；發現矛盾即拒絕快照，不把這些輪廓標記為新資料。沒有 `nodes` 的幾何資料仍只能套用原有閉合、拓樸、POI 與來源驗證，**不能宣稱已核對節點身分**。

新增 API 正反回歸：兩棟各自合法、節點編號不同可以接受；兩棟各自合法但跨 way 重用相同 node ID 卻指向不同經緯度時，API 以 503／no-store 備援，不快取矛盾輪廓。測試使用**合成矛盾資料**，沒有證據顯示靜宜真實 OSM 現況發生這種錯誤，也不是 Overpass live 端到端驗收或實際量測。

### 中庭內 POI 與建築實體距離核對（2026-11-13）

原本 POI 只要位於 OSM 建築的**外環**裡，就直接通過對位，即使外環中間有被挖空的中庭。若來源日後改為很大的中庭，距離實際建築牆面超過原有 30 公尺容錯範圍，系統仍可能把那個 POI 錯接到完整建築量體。現在服務端解析 Overpass 和前端解析 API 快照時，均依**外環減去已核對內環**的建築實際平面範圍核對：落在外環實體內直接接受；在外環外或中庭內，必須與任何真實內／外環邊界相距不超過原有 30 公尺，否則不生成該棟 3D 量體。保留現有 OSM relation 成員 ID、幾何與中庭閉合檢查，沒有推定入口或可步行道路。

新增合成的大／小中庭回歸：同一已核對 POI 距中庭牆面約 12–13 公尺時可接受；距約 40 公尺時由服務端及客戶端雙重拒絕；不改其他學校 POI。**測試中的方形輪廓完全是合成情境，不是希嘉學苑現地輪廓**。沒有用此結果推論建築高度、真實路網或競品優勢。

## OSM 建築現況條件的保守處理（2026-11-13）

OSM 可能同時保有 `building=yes` 與 `building:condition=*`；完整建築標籤不等於整棟牆面、屋頂仍完整。對於 [OSM building:condition](https://wiki.openstreetmap.org/wiki/Key:building:condition) 明示 `partly_ruinous`、`mainly_ruinous`、`completely_ruinous`、`recognizable_remains` 或 `ruinous` 的已核對圖徵，現有整棟等高度擠出模型會錯畫成完整建築，因此先排除 3D 量體，保留已知 POI 與原有導航；空白或非文字的條件亦不充當完整建築證據。`good`、`preserved`、`renovated`、`reconstructed` 與無此條件標籤的有效建物則不因本規則額外拒絕，仍必須通過原有來源、分類、幾何、POI 與高度檢查。該 OSM key 的可查證性亦有爭議，因此這是**避免錯誤立體示意的資料防護**，不是現場結構安全鑑定，也不是宣稱靜宜校舍實際有毀損。對應 Vitest 使用合成標籤正反例，仍需真實 Overpass 和現地驗收；無資料時不捏造樓高、入口或可行走道路。

**2026-11-13 後續修正**：過去只排除一小組明確的毀損值，遇到 `building:condition=collapsed`、`unsafe` 或未知／非標準的單值時仍可能繪製完整校舍。現改成只有明確已審閱的 `good`、`preserved`、`renovated`、`reconstructed` 能通過這個可選的條件欄位；未標示條件仍按既有建築來源與幾何驗證。其他單值一律保守略過該 3D 量體，不擅自判定它是安全或損毀建築。合成回歸補上毀損／未知值及含斜線、換行、冒號的歧義值，與實際靜宜校舍現況無關。

### Overpass 閘道過載 502／504 冷卻保護（2026-11-13）

公開 Overpass 或中介閘道在過載時可能回傳 HTTP 502／504（不只 429／503）。先前這兩種錯誤會直接走一般 10 分鐘遞增重試，即使回應有合法 `Retry-After` 也被忽略。現在將 502／504 納入既有的上游冷卻處理：有 `Retry-After` 時遵守原本 10 分鐘至 24 小時的界限，無有效指示時沿用遞增失敗退避；同一個 Node 程序內冷卻期間不重複查詢。保留七天限制內且明示日期的過期 3D 快照，否則回到 POI／平面地圖，不推測建築與路線。

新增合成 HTTP 502／504 正反回歸：分別驗證 3600／1800 秒來源指示、無標頭時 600 秒、冷卻截止前不回源、到期後成功恢復，以及已有來源快照時 HTTP 200／`stale=true`／`private, no-store` 的退路。這些測試不代表已實際連線到公開 Overpass，也未量測靜宜建築、找教室、步行路線或手機效能；本 commit 的 CI／Campus Spatial Browser／CodeQL 必須以其最新 head 結果為準。

### 複合建築現況不得被解讀成完好量體（2026-11-13）

當已核對 OSM way 同時回報單一 `building=yes` 與含分號、逗號或管線符號的複合 `building:condition`（例如 `good;ruinous`、`renovated,mainly_ruinous`、甚至 `good;preserved`）時，解析器不再將它們當成已確認的完好校舍來擠出 3D。單一有效的 `good`／`preserved`／`renovated`／`reconstructed` 與未標記情境仍不受影響。原有已核對地點與外部導航保留，不據此推斷靜宜建築損壞。新增合成標籤 Vitest，包含六種複合條件的拒絕與大寫／空白單值的接受；實際 Overpass、校園現地和競品同條件驗收仍未取得。


## Overpass 超長重試等待標頭的安全上限（2026-11-13）

當公開 Overpass 上游回傳 429／502／503／504 並附帶 `Retry-After` 的十進位秒數時，數字字串可能極長。過去直接用 `Number(value) * 1000` 換算；超過浮點數範圍會變成 `Infinity`，被當作無效標頭退回 **10 分鐘**，即使上游其實要求暫停更久。現在先移除多餘的前導零，再以字串位數比較是否達到 **24 小時冷卻上限**，最後才轉換仍在安全範圍內的秒數。合法且帶前導零的較短等待（例如 `0001800`）仍按 30 分鐘處理；零或無法辨識的標頭沿用既有最低冷卻與漸進退避。此修補不變更固定 OSM 白名單、座標、建築高度、來源署名及快照有效期限。

回歸測試使用合成 HTTP 502／503 與長達 350 位的等待數字，確認冷卻期間不向公開服務重複請求、到期後才可恢復。這是防止數值溢位造成過早重試，不表示真實 Overpass 已傳回如此長的標頭；多部署實例間仍未建立共享冷卻。

## 繁體中文與臺灣地區 OSM 建築名稱的一致性（2026-11-13）

已核對的 OSM way ID 即使未變，也可能在後續編修時改名。既有檢查只核對主標籤 `name` 與 `name:zh`；若 `name:zh=蓋夏圖書館`，但 `name:zh-TW=希嘉學苑`，原本可能仍把同一輪廓冠上「蓋夏圖書館」並畫出立體建物。現在同時檢查可選的 `name:zh`、`name:zh-TW`、`name:zh-Hant`：**任何一個有值但不是既有已核對 POI 名稱，或非文字／空白，都拒絕該輪廓**；只有這些中文標籤一致時才允許不同的英語主名稱。沒有任何中文名稱標籤時仍延續既有主名稱規則，未替任何建築新增臆測名稱。

新增四組接受與六組拒絕回歸，包含只有臺灣繁體名稱搭配英文主名、三種中文標籤一致、地區標籤互相衝突，以及非文字與空白。所有衝突皆為**合成測試資料，不代表靜宜現行 OSM 已存在錯名**；此檢查不會把 OSM 標籤當成校方命名核准，也無法代替真人核對最新官方資訊與現地位置。仍保留來源署名、POI、平面導航與跨校權限隔離；沒有修改建築樓高、入口或室內道路。


### Identity 傳輸長度矛盾的快速拒絕（2026-11-13）

公開 Overpass 回應若宣告 `Content-Length: 0`，即使是 identity（未壓縮）傳輸，也不可能包含完整的建築 JSON。原本已攔截壓縮編碼的零位元組宣告，但 identity 仍要等到串流結束才核對長度。另一種情況是 identity 宣告只含 1 個位元組、實際首批已收到更多資料，若上游此後不結束串流，也會耗盡 12 秒期限。

現在將**任何編碼的零長度宣告**於讀取前拒絕，並對 identity 每批串流即時核對已讀位元組是否超出宣告；明顯不一致時不再等待 EOF。延續 503／`no-store`／冷卻及已核實、未逾期快照備援，best-effort 取消不等待可能永不完成的上游 `cancel()`。正常長度一致的 identity、非零壓縮傳輸與沒有 `Content-Length` 的分塊回應保留既有驗證流程。新增兩組會停滯的**合成串流**回歸（identity 的零長度與首批超長），需以當前 head 的 Web Tests／CI 結果驗收；不代表真實 Overpass 曾回覆這些異常，也不是現地導航或競品比較證據。

### 2026-11-13：排除單數廢墟與受損建築分類

即使校舍的 OSM way ID 已在經對位的白名單內，若來源後續將 `building=*` 改為 `ruin` 或 `damaged`，不應再依舊有 POI 身分畫出完整屋頂及立面。這兩種含糊／毀損分類現在比照既有的 `ruins`、`ruined`、`collapsed` 排除 3D 量體，保留原有地點標記、平面圖與外部導航，不能反過來判定現場建物受損或可進入。相關 OSM 參考：[building=ruins 與可能誤標類型](https://wiki.openstreetmap.org/wiki/Tag:building%3Druins)。

驗證包含解析器的拒絕測試，以及 API 對兩種來源分類都不得寫入新快照、必須回傳 503／`no-store` 並遵守冷卻的合成回歸。這些不是靜宜現行 OSM 已變更、公共 Overpass 真實傳輸或校園實測的證據。仍須通過此 head 的正式 CI、Campus Spatial Browser、CodeQL 與指定 App 審查；未完成前不合併或部署。

### OSM 樓層數標記與完整地上量體的矛盾檢查（2026-11-13）

`building:levels=*` 是地上樓層**數量**，不是公尺高度，不能據此乘出建築樓高。過去固定白名單校舍即使被編輯成 `building:levels=0`、負數、複合值或無法解讀的文字，仍可能繼續顯示完整的 12m 示意量體。現在只有明確、有限且大於 0、最多 100 的十進位地上層數標記能通過此額外資料檢查；完全缺少此可選標籤不會影響原有判斷，例如 `1`、`5` 的正整數值可通過；`1.5` 這類小數依 [OSM building:levels 標籤規範](https://wiki.openstreetmap.org/wiki/Key:building:levels) 不接受。這個 100 層僅是保守的資料審閱上限，不是靜宜建築高度或樓層的事實判斷；超出時先保留 POI 而不繪製整棟 3D。合法層數**仍完全不拿來推估公尺高度**，無明示 height 的輪廓仍標示「12 公尺示意」。

新增 parser 正反向及 API 503／no-store／快取冷卻測試，涵蓋合成的零、負數、分隔值、非數字、超出審閱上限與合理層數。這些測試只防護資料編輯／解讀矛盾，**沒有查出靜宜真實 Overpass 存在此問題**；正式結果應依本 commit 的 Web Tests、Spatial Browser、CodeQL，仍須完成現地幾何、路線、手機／輔助工具及競品同條件比較。

### 2026-11-13｜Apple 地圖步行導航入口（待實機／現地驗收）

3D 空間導覽除了原有的 Google 步行導航，新增使用者可選的 Apple 地圖步行連結，使用同一已選地點標記的經緯度，不新增或推斷校舍入口、樓層、校園步道或無障礙路線。Apple 連結採相容舊版 iOS 的 `maps.apple.com/?daddr=...&dirflg=w`，由外部地圖服務自行計算路線。兩個外部導航均關聯同一份 `aria-describedby` 安全提醒，WebGL 失敗時仍可選地點並使用連結。適用跨校共用 UI，不改來源、權限、建築輪廓、OSM 署名。參考 [Apple Map Links](https://developer.apple.com/library/archive/featuredarticles/iPhoneURLScheme_Reference/MapLinks/MapLinks.html)。

新增 URL 參數及 React 選擇／外部導航／WebGL 降級回歸。此項驗證**僅檢查連結格式與標記座標**，不表示 Apple／Google 真正算路成功，更不證明實際可通行、教室入口或競品優勢。仍需 iPhone Safari、Android 以及靜宜同機同任務現地驗收。

## OSM relation 與 way 的來源修訂標籤（2026-11-14）

已核對希嘉學苑 relation/9246899 的 outer 與 inner 輪廓。若 Overpass 提供合法 version／UTC timestamp，保留該 relation 自身修訂資訊，畫面明確標為「OSM relation 版本」；一般建築 way 標為「OSM way 版本」，不混用。

relation 修訂時間反映自身標籤／成員列表的編輯，**不是成員 way 或節點幾何更新時間**；即使 relation 版本不變，內外環的成員外框仍可能被另外編輯。way 版本同樣不涵蓋單獨修改的節點。前後端核對版本及 UTC 日期、來源與資料庫快照時效；不合法的修訂標籤不顯示，不影響其他已核驗的幾何。這些是合成解析器及 UI 回歸，不是線上 Overpass 或現地查證證據，亦不代表確認樓高、入口或道路。

## 3D 地點選單標示（2026-11-14）

在空間導覽「想去哪裡」選單中，只有目前可見、成功通過 API 與用戶端來源／校園 POI／幾何核對的建築，才在地點名稱後標示「（有 OSM 外框）」。載入中、來源失敗、快照被拒絕、非靜宜校區或被篩掉的建築均只保留原本地點名稱；選取地點 ID 與既有導航網址不變。此標示只協助辨認哪些地點在本次視窗具有立體外框，不是入口、樓層、路線或現場建築外觀的查證結論。
