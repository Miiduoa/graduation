# 活動查詢與個人行程：自然語句接續

日期：2026-11-16

接續 [失物招領與活動來源行程](./2026-11-16-event-calendar-lost-found.md)。本輪把已有的活動來源確認流程接入聊天輸入，並補上一般模型工具的來源界線。

## 可以直接使用的語句

| 語句 | 實際行為 |
| --- | --- |
| 查近期活動，並把第一個加入行事曆 | 讀取目前校園的近期活動；清單完整且順序可核對時選第 1 筆，重讀該筆來源，核對課表與個人行程後產生確認卡 |
| 查公開活動，接著將第二筆活動加入個人行程 | 同一流程，明確選第 2 筆；不改成第一筆、不猜缺漏的活動 |
| 把第二個加入行程 | 承接最近顯示的活動清單第 2 筆，重讀 exact source 後預覽；前一段若已轉為其他主題，不自行跳回舊清單 |
| 把上面那個活動加入行事曆 | 最新有效活動清單恰好只有一筆才選取；多筆則列出選項 |
| 把活動「校園攝影講座」加入行事曆 | 只接受清單中完全相符的名稱；同名多筆不猜測，由使用者選具體項目 |

這些確定性語句不呼叫雲端模型，不需模型 ready 或模型傳輸同意，仍需有效的 Platform session、相同校園與使用者的新增個人行程權限。解析器只接受完整、有限的語句；未支援的日期篩選、改期、報名、多筆操作及附帶要求不會被刪掉後偷偷套用這條流程。

## 一句話串接兩個功能

新查詢只接受第 1–5 筆。後端 `event-preview` 的輸入擴充為二選一：

```ts
{ schoolId, conversationId, routeToken?, event: { schoolId, source, id } }
// 或
{ schoolId, conversationId, routeToken?, discovery: { index: 2 } }
```

`discovery` 只接受一個整數 `index`。客戶端不能在其中提供標題、時間、其他學校、路徑或查詢篩選。兩個輸入同時存在、都不存在、或含額外欄位，都在任何 adapter 存取前拒絕。

執行順序：

1. 沿用獨立 `event-preview` bootstrap，取得伺服器產生的 conversation 與 route token。
2. 查核 `createPersonalEvent` 權限。
3. 使用同一 adapter，固定呼叫目前校園的 `publicCampus('events', 5)`。
4. 驗證整份來源、每筆身分、順序與完整性，才依指定序位取出 `{schoolId, source, id}`。
5. 重用原 `prepareCampusEventRequest()`，重新讀取 exact source，核對完整時間與已同步課表、個人行程。
6. 準備具有 `publicEventGuard` 的原確認卡；使用者按確認後，仍要重驗來源、權限、revision 與時間，寫入並完整回讀。

清單不完整、來源無法使用、排序不符或第 N 筆不存在時，不選取替代項目。可核對的活動仍顯示為具序號的選項；使用者可明確選一筆後進入原 exact-source 預覽。空清單不代表全校沒有活動。

清單只有選擇身分的作用。卡片不採用清單或模型提供的日期、時間或名稱。來源在清單讀取後改名，預覽採用 fresh source；在預覽與確認間再變動，原卡的來源指紋驗證拒絕寫入。

## 已顯示清單的接續規則

- 清楚顯示每個選項的序號；序號依完整選項列計算，不依摘要最多展開三筆的文字計算。
- 活動身分只能來自經過驗證的 `eventTargets`，不從回答文字、標題猜測或自行拼接 URL 取得。
- 不帶「活動」的指代只承接最近非預覽回覆；明確帶「活動」才可找最近的活動清單。
- 最新活動清單即使為空或驗證失敗，也不往前找舊成功清單作替代。
- 單筆活動預覽不是新的完整清單，不會把原本第 2 筆突然變成第 1 筆。
- 重新查詢並直接預覽第 N 筆，會建立新的活動查詢邊界；這次若只回傳單筆預覽，後續序號須先重新取得清單，不會跳回更舊的查詢。只有從既有清單點選的預覽才保留原清單順序。這個邊界由客戶端的實際發起方式記錄，不信任伺服器回覆額外夾帶的旗標。
- 這個／那個需要唯一候選；名稱需要完全相符且唯一；序號不存在就說明範圍。
- 有待確認卡、執行結果不明或正在恢復的操作，先保留原卡並提示處理；不自動撤銷或覆蓋。

自然語句與活動按鈕共用同一預覽實作。活動 route 不改寫主要聊天 route；確認、取消與回執恢復仍綁定活動卡原 conversation。停止、登出、切帳與切校會取消目前請求並丟棄晚到結果。停止或網路失敗時保留原語句，供使用者恢復。

## 一般模型路徑的來源保護

之前，模型可以先查公開活動，再呼叫一般 `propose_personal_event`，造成卡片缺少活動來源 guard。本輪加入 runtime 檢查：

- 原問題明確要求把活動來源／清單／序號加入行程，不能先用一般個人行程提議繞過來源預覽，也不能改成不相干的讀書安排。
- 一旦嘗試 `get_campus_events`，包括參數錯誤、來源失敗或不可用，後續一般個人行程提議會要求明確選擇來源。
- 權限／ledger 等待後、簽卡前再次檢查，避免並行讀取改變來源狀態。
- 一般模型成功讀活動後也提供經驗證、有順序的 `eventTargets`；模型之後失敗時保留已核對結果。
- 以最後一次活動讀取為準；最後一次失敗不重新暴露更早的清單，晚到的早期讀取也不能覆蓋較新狀態。
- 活動結果直接由來源格式化，並標記 `dataRead`；模型口頭宣稱新增成功不會變成執行結果。

名稱包含「活動」、但自行完整指定名稱／日期／起訖時間的私人行程仍沿原流程。真正由已讀作業產生且帶 `studyGuard` 的獨立讀書安排，也仍可與活動查詢並存。

## 資源與未變更的契約

Discovery 與原結構化預覽共用每帳號每分鐘 3 次／每小時 10 次限制。來源讀取使用既有匿名 Firebase app、固定 school、實際 API budget 與每次讀取 guard。Discovery 整體上限 20 秒、清單階段 12 秒，來源預覽維持原 16 秒上限並受外層取消約束；前端活動預覽等待上限為 25 秒。查詢後才跨過活動開始時間，也不發出可確認卡。

儲存內容仍是活動標題與時間；地點作來源參考。這不是活動報名、推播提醒或訂閱改期。重複確認同一張卡沿既有 mutation ID 只寫一筆；不同卡不宣稱具活動 ID 層級的全域去重。

本輪沒有新增外部 API、資料庫 migration、套件或部署旗標，也沒有擴張學校私人資料授權。能力目錄仍是 45 項服務、15 項可讀、其中 5 項可準備確認內容。實際來源與寫入仍依部署設定、目前登入與個別權限決定。

## 驗證與前次 CI 修正

新增案例涵蓋來源第 2 筆、全或無清單驗證、清單到 exact source 的變更、空／部分／無序／不足、同名與指代歧義、最新空清單不回退、另一主題與預覽隔離、無 model ready／consent、原卡與主要 route 保留、帳校變更、停止、deadline、來源開始時間競態、API 額度、auth、模型先提議後讀取與讀取失敗後猜測、逐卡確認與去重。

前次遠端 Web Tests 唯一失敗是 `campusEventFlow.test.ts` 中 prepare 使用經過時間、confirm 使用固定 fixture 時間，導致 CI 可能出現 `iat > now`。本輪讓測試在 prepare 前固定時鐘，再在對應權限等待中推進同一個時鐘。簽章與正式時間驗證規則保持原要求。

完整本機及精確 head 的遠端驗證記於 PR #631。程式與測試成功不代表已合併或上線；repository 的指定 GitHub App「審查通過」仍須有該版本的真實核可。
