# 首頁課務代辦

## 使用者現在可以做什麼

首頁在課表與待辦前加入「nuni 代辦」。登入平台帳號後，已讀到的作業與測驗會依未來截止時間排序，先顯示三件。當來源讀取完整，系統會替七天內最先到期的一件準備 30 分鐘的行程預覽，使用者不用先開啟聊天或輸入問題。

預覽會重新讀取原作業、課程資格、已同步課表及個人行程。使用者按確認後才會建立個人行程；頁面必須讀回相同紀錄，才顯示「已核對並加入個人行事曆」與該行程的連結。

同一登入狀態、帳號及校園，每十五分鐘最多自動準備一次，避免進出首頁消耗既有查詢配額。手動「找 30 分鐘」保留可用。部分課程讀取失敗時，自動安排先暫停，已讀到的單筆待辦仍能手動交給後端重新確認。

## 資料與規劃範圍

- 首頁只將 `rows.nuni.data.tasks` 傳給這個入口，保留原始 `courseId`、`id`、`kind`。Firebase 課程不會被當成平台課程送出。
- 初始清單是目前帳號可存取的 nuni 課程；伺服器仍重新核對每筆課程與目前校園的資格。前端清單不構成寫入授權。
- 時段使用既有課務規劃器：今天起七天內、截止前、08:00–22:00 的已知課間空堂，避開個人事件並保留前後十分鐘。
- 規劃採用已同步資料；首頁顯示的未同步本機課表不會被誤稱為已核對來源。缺課表、沒有期限、沒有可用空檔或權限失效，都會保留具體原因。
- 這條流程不傳送課務資料給語言模型，不需要模型金鑰或聊天同意。它是既有任務執行能力的直接入口，不代表背景推播或作業繳交。

## 直接規劃 API

新增 `POST /api/nuni/assistant/plan`，沿用同源檢查、登入 Cookie、`X-Campus-Session`、校園與執行個體綁定，以及原有帳號配額。

```json
{
  "schoolId": "pu",
  "conversationId": "opaque-operation-id",
  "routeToken": "server-issued-route-token",
  "task": {
    "workspaceId": "source-workspace-id",
    "taskId": "source-task-id",
    "kind": "assignment"
  }
}
```

第一次請求不帶 `routeToken`，只取得新的伺服器綁定；下一次才讀取選取的原始資料並回傳預覽。客戶端不提供標題、截止時間或任意事件內容作為授權依據。

有預覽時回傳既有簽章確認卡與 `expiresAt`。`confirm`、`cancel`、`reconcile` 繼續使用既有端點。`capability` 另標示 `planning` 與 `writesEnabled`，不以模型的 `ready` 狀態代表規劃是否可用。

## 執行與復原

確認前先核對本機事件衝突與未完成同步，再保留原卡片的恢復紀錄。伺服器確認時重新檢查原作業狀態、期限、課程資格、行事曆版本、時段與建立行程權限。只有完整回執符合原卡片、本機已更新，且已保存後續追蹤證據時，才清除待核對紀錄。

送出後失去回覆只查核原操作，不會自動重新新增。重新開啟首頁會讀取同一份、受登入身分綁定的執行紀錄；聊天入口若新增待核對操作，首頁也會在下一次規劃或確認前讀到並停止新操作。切換帳號、校園或登入失效時，晚到結果不能改寫新範圍。

尚未送出的五分鐘預覽，在期限前十五秒撤下；本機取消也只適用於沒有送出與恢復紀錄的預覽。已送出的操作沒有本機逾時刪除機制。

若伺服器確認查無紀錄、原提議已無法執行，使用者可以要求停止。對過期提議，伺服器還必須持有相同程序世代、執行個體、綁定與簽發清單，並確認從未送出寫入、沒有未明結果，才回報撤銷。曾送出寫入或失去原簽發證據的操作，不能用「目前沒讀到」宣稱已取消。

## 安排後持續核對

已完成的安排會留下原始簽章卡片、原登入 context、conversation ID 與已核對時間。同一台裝置重新開啟首頁、重新登入同一帳號，或將首頁切回前景時，先重新核對這些安排，再選擇尚未安排的課務。前景自動核對最多每分鐘一次；使用者也可以主動按「更新安排狀態」。不在首頁持續輪詢，關閉頁面後也不會執行背景工作。

追蹤由 `POST /api/nuni/assistant/followup` 提供。請求只帶原始 `conversationId`、`issuedContext`、`token`、`args` 與目前校園，仍須通過目前登入的同源及 session 驗證。伺服器以目前帳號、校園及原 context 驗證簽章，從簽章中的 `studyGuard` 取得課程與作業識別，再重新讀取來源、課程資格與行事曆。客戶端不能自行指定另一份作業，也不能把這條只讀查核轉成確認、改期或刪除授權。過期卡片僅能在簽章及帳號範圍仍有效時用於查核。

| 最新查核結果 | 首頁行為 |
| --- | --- |
| 已安排／準備中 | 顯示原時間及行事曆、作業連結，不再替同一作業準備重複預覽 |
| 原準備時間已結束、來源仍未繳交 | 顯示仍待繳交或作答，不將時間經過視為作業完成 |
| 作業內容或期限變更 | 顯示目前期限，提醒核對原安排是否合適 |
| 原行程有變更、遺失或與新安排衝突 | 保留原準備時間，連到行事曆供核對 |
| 來源已繳交／已停止收件 | 顯示來源的真實狀態，不自動刪除原行程 |
| 簽章已核對，但來源或行事曆暫時不可讀 | 保留該任務的追蹤、不重排該任務；其他未安排任務仍由規劃 API 重新核對 |
| 請求失敗、回應格式或範圍無法核對 | 保留原證據並暫停新規劃，提供重試 |

成功卡片只在回執、本機資料及相同行程的追蹤都核對完成後，收成任務列上的簡潔狀態。未明結果、錯誤回執或本機保存失敗仍保留原查核操作。已不在近期待辦中的項目收在「最近安排」，並顯示需要確認的件數。

追蹤證據按平台帳號與校園保存在此裝置；所有新增與清理共用相同的 Web Lock，從讀取、修改、寫入到讀回都在鎖內完成。無法取得這項儲存能力時，保留待核對紀錄，不宣稱保存成功。最多保留 24 筆且不默默覆蓋；規劃與確認前會檢查容量，保存時再於鎖內檢查，跨分頁競爭若使保存失敗則保留原待核對紀錄。只有來源重新讀回已繳交或停止收件、原行程仍相符且已結束超過七天，才移除舊追蹤證據。清理不更動行事曆。

這份記憶不是跨裝置同步。清除瀏覽器資料、換裝置、簽章金鑰更換或來源權限永久消失，都可能需要額外處理；這一版沒有伺服器排程、背景推播、自動改期或代為繳交作業。

## 競爭標準與本輪取捨

截至 2026-11-13 的官方說明，[Motion](https://www.usemotion.com/help/time-management/auto-scheduling/reference-auto-scheduling/how-auto-scheduling-works-behind-the-scenes) 已支援按期限、優先級、時間及可用空檔安排，並回應新的行程與衝突；[Reclaim Agents](https://help.reclaim.ai/en/articles/16995155-agents-overview-automate-smart-calendar-events) 已可持續管理專注時間、習慣與緩衝，並提供預覽模式。[Reclaim 2.0 的任務](https://help.reclaim.ai/en/articles/17438753-switching-from-reclaim-1-0-to-2-0)不再自動各自建立獨立時段，因此不能沿用舊版描述。學習產品 [UniTable](https://apps.apple.com/us/app/unitable-ai-academic-partner/id6745899492) 的開發者版本紀錄也已公布 Moodle 課務同步與新期限通知。

本輪補足的是「安排後，對照原作業持續核對」：辨識來源真的繳交、內容變更、行程變動與資料未知，並防止同裝置重複安排。這些實作與合成測試還不能證明整體超越競品。跨裝置任務記憶、可觀測的背景觸發、經確認的改期流程及真實校園帳號驗證，仍是後續要補齊的比較項目。

## 驗證方式

新增路由測試使用真正的 `handleNuni` 分派與簽章／回執流程，覆蓋預覽零寫入、確認、重送、來源變更、到期、權限及跨帳號／校園隔離。首頁整合測試使用真實的恢復紀錄與本機事件儲存，另外驗證雙擊、斷線、錯誤回執、晚到回應、來源讀取不完整、冷卻時間及重新安排。

`scripts/qa/today-agent` 掛載實際的首頁代辦元件，以固定合成資料進行 Chromium 窄螢幕與桌面操作驗證。這些驗證不使用正式學生帳號，也不代表正式站已發布；遠端檢查與發布狀態應對照 PR 的精確提交。
