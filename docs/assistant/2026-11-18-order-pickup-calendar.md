# 訂單取餐時間串接個人行事曆

## 本輪完成的任務

從 main `d4bc4cbf418eee804842b8834e19c6a28202ce89` 獨立開發，沿用主線既有的 Platform 訂單讀取與個人行程確認機制。沒有搬入已關閉的 #631 或依賴該分支的 #684／#689。

使用者可以說：

> 把我最近一筆訂單的取餐時間加入行事曆，預留15分鐘

Agent 依序核對目前校園的本人訂單、取餐時間、課表與個人行程，提供一張已綁定來源的確認卡。按下確認後，重新讀取同一筆訂單，再透過原有 CAS／mutationId 機制儲存並讀回行程。查詢與預覽都不建立訂單、不付款、不寫入行事曆；整條流程不呼叫語言模型。

這次新增的是 Web 與手機瀏覽器的流程。沒有新增套件、資料表、權限種類或部署開關，也沒有變更正式環境設定。

## 來源與時間

- 只能從 API 已授權、與目前 schoolId 相符且唯一的 realm 選取最近一筆訂單；無可核對來源、多工作區或最新建立時間相同時，不猜選擇。
- 由既有近期五筆清單的建立時間決定最新項目，再讀該 ID 的詳情。最新訂單已取消、付款未完成或已取餐時，不偷偷改選較舊的有效訂單。
- 取餐來源必須提供 `requestedPickupAt`、明確時區與有效日期。非整分鐘資料不會被無聲截去秒數；取餐時間必須尚未到來。
- 支援 `paid`、`accepted`、`preparing`、`ready`。正常狀態進展可以繼續，取消、拒絕、逾期付款與已取餐則停止首次寫入。
- 預留時間預設15分鐘，可明確指定5到120分鐘。事件依台灣時間建立，跨午夜保留正確結束日期。
- 指紋綁定原 tenant、order、取餐地點與取餐時間。確認期間出現新訂單，不會改選新訂單。

## 執行與恢復

`pickupGuard` 放在伺服器簽章內；瀏覽器收到的 `sourceBound: 'food-pickup'` 只供介面呈現，不能授予執行權限。

確認沿用原本的帳號、session、對話、校園、期限、助理權限與 ledger revision 核對；第一次寫入前再驗證原訂單。確認成功必須讀回相同 mutationId 的完整事件。連點或重送會回原回執，結果不明時先核對原操作，不建立替代行程。

如果行程先前已成功寫入，後來訂單取消或完成，重送仍回覆先前成功的行程回執。這條功能在準備與確認時核對來源；儲存後不會在背景持續同步訂單，也不會自動修改或刪除已建立行程。

一般改期、平移、挑選及模型重新規劃不能把來源 guard 去除：介面隱藏相關控制，直接修改 API 也拒絕這類來源卡。取消未執行提議、讀回結果與既有恢復紀錄仍可使用。

## 不依賴模型的入口

前後端共用完整句子辨識器。只有既有 V2 planning 能力啟用且有目前登入帳號／session 時，才顯示取餐安排建議與無模型送出入口。建議按鈕只填入草稿。

符合辨識的請求可以在模型服務未設定或暫時不可用時執行；一般問題保留原本的模型外送同意規則。無法完整理解的取餐轉行程要求只回具體範例，不把未知條件丟給模型猜訂單或日期。

取餐回覆一律 `dataRead: true`，包括失敗與重新整理後恢復的卡片；私人門市與取餐時間不進入後續模型歷史。明確指定日期／時間的普通行程，例如「明天19:00到20:00整理訂單」，仍走原本行程流程。
