# 角色任務情境與指定訂單的跨功能安排

## 使用問題與結果

同一個帳號可能同時修課、授課或經營門市。助理如果把所有問題都交給學生資料來源，教師的「作業」會被解讀成本人待繳作業，店家的「訂單」也可能變成本人的購餐紀錄。本輪將工作情境與實際授權分開，讓建議、工具選擇、直接查詢與後續對話使用相同情境。

另一個問題是「最近訂單」只適用於唯一工作區。訂單詳情現在提供「預覽這筆取餐安排」，使用當前明確選定的工作區及訂單，接續課表、個人行事曆、簽章確認與讀回回執。

本輪基於 PR #706 的 `1dcdae9df306503c93630207827e5bf837abcc32`，整合主線 `6b0dbe30ac788742658f7a134d0be5f61bdbb230` 後獨立實作。沒有帶回已關閉 #631 或其相依分支的內容。

## 六種工作情境

| 情境 | 任務重點 | 本輪實際能力 |
| --- | --- | --- |
| 學生與個人 | 課表、作業、學習、生活安排 | 保留既有本人讀取與準備操作，新增指定訂單取餐安排 |
| 教師與助教 | 備課、授課、批改與核閱 | 個人時間與授課服務入口；未新增授課名單、待批改或批次評分 reader／writer |
| 店家 | 接單、出餐、商品與營運 | 個人時間與門市工作區；不把買家訂單當門市營運資料 |
| 社團幹部 | 社團動態、活動籌備 | 本人可見社團、個人籌備時間與社團管理入口 |
| 校務與課務 | 資格、課務與核閱 | 個人時間、公開服務與校務核閱入口 |
| 平台營運 | 帳號、資格、維運 | 個人時間與管理入口；管理頁重新確認平台營運資格 |

`assistantRoleProfiles.ts` 只收固定 ID，重用既有 `CampusRole` 作為呈現映射。任何情境都不產生新角色、權限或來源資格。`CampusRole.admin` 不等於 `NuniPrincipal.isPlatformOperator`。目前 Platform principal 沒有完整的校園角色集合；一般使用者先選本次工作情境，可信平台營運 principal 可取得相應呈現預設。沒有從姓名、電子郵件或提示詞猜測管理權限。

介面區分「可查詢」、「可準備，確認後執行」與「前往服務處理」。切換情境不改變帳號，且在待確認卡或結果不明的操作處理完成前鎖定。草稿文字保留；送往模型的歷史只取相同情境的一般對話，直接讀取結果、服務指引與其他情境的私人內容不混入。

## 執行與資料來源限制

- `taskProfile` 由 BFF 精確白名單驗證，外部 profile 物件、未知 ID 或權限欄位在私人來源讀取前拒絕。
- Runner 依固定工具範圍篩選模型工具、直接查詢與預讀；`createTools.call` 在參數修補、權限查詢及快取之前再次限制工具。
- 非學生情境不預讀學生待繳、教材、匯入成績或買家訂單。開啟課程／訂單頁的 `entityId` 也不能間接讀取這些來源。
- 本機查詢在讀取前先依完整解析結果分類，送出按鈕與實際執行共用相同路由。非學生仍能查自己的課表與個人行程；作業及匯入成績導向角色服務指引，換行或特殊空白不能改讀學生來源。
- 尚無角色專用 reader 的工作，使用固定服務指引接續目的頁，不將資料缺口寫成零筆待辦或已完成處理。`get_campus_info` 目前仍是官方來源及服務入口，不是公告或活動內容 reader。
- 明確的個人行程仍共用既有來源、衝突、權限、簽章、使用者確認與讀回流程。備課行程不會替課程排課；盤點行程不會修改店家或員工班表。
- 固定角色指引與取餐規劃不呼叫模型。即使某條直接任務允許沒有模型外送同意，真正呼叫模型前仍再次檢查同意，不可經例外回落到模型。

## 指定訂單 → 個人行事曆

`POST /api/nuni/assistant/pickup-plan` 接受：

```ts
{
  schoolId,
  conversationId,
  routeToken?,
  target: { tenantId, orderId, durationMinutes? }
}
```

目標不接受客戶端提供的取餐日期、地點、標題或角色。第一次回覆伺服器產生的 conversation／route token；取得綁定後，重新以原目標準備預覽。預留時間預設 15 分鐘，合約接受 5–120 分鐘整數，介面提供 5、10、15、20、30、60 分鐘。

伺服器先確認選定工作區屬於目前校園，再透過目前帳號讀取精確訂單；讀完再核對來源資格。多工作區不改選「最新一筆」，選定訂單無權讀取或已失效也不改查其他訂單。取餐時間與地點只能來自訂單。

之後使用原取餐流程檢查課表和個人行程，產生來源綁定簽章卡。確認時重新驗證原訂單、狀態、地點與時間，再以原 mutation ID 寫入並精確讀回。取餐行程不會修改訂單、付款、發送通知或建立推播提醒。

### 失敗與恢復

- 確認前沒有行事曆寫入，送出前先保存原簽章及 mutation ID。
- 結果不明時先核對原操作，不自動重新建立。
- 重新載入只恢復本工作區、本訂單的卡片；其他訂單與課務紀錄完整保留。
- 客戶端解碼 token 只篩選應顯示的恢復紀錄，不能授權操作。伺服器仍驗證原簽章與來源。
- 帳號、session、校園、工作區或訂單切換使舊請求取消；晚到回覆不能顯示在新來源。
- 訂單失效或寫入關閉時停止新確認，原執行結果仍可核對。

## 驗證與發布

共用合約測試核對角色與真實工具清單、服務分類、輸入限制及固定指引。Web 回歸包含真實 BFF／Runner／工具／簽章／回執、角色資料隔離、模型同意、指定訂單與介面恢復。`selected-pickup-browser.yml` 使用實際訂單詳情和真實 HTTP BFF／簽章流程，僅在帳號、訂單及儲存來源使用合成資料；驗收 1440px、390px 與儲存後遺失回應再重載的情境，並保存來源 hash、請求紀錄與截圖。

測試數與精確提交結果以 PR 最新紀錄及該版本 CI 為準。這是 Web／手機瀏覽器功能；不代表原生 iOS／Android、真實帳號、教師批改、門市交易、背景同步或所有跨功能任務已完成驗收。合併與部署仍依主線既有規則辦理。
