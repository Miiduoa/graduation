# 靜宜校園 3D：公開建築輪廓實作與驗收

## 目前入口

靜宜地圖 `/map?schoolId=pu` →「空間導覽」。開啟視窗後，Web 端才初始化 Three.js，並嘗試讀取同站 `/api/public/campus-footprints` 的輪廓快照。取得建築輪廓時，依經緯度換算成公尺後立體擠出；資料讀取失敗時仍提供原本的地點標記、列表與步行導航，不用任何假建築補滿畫面。

請勿把此版本描述為「靜宜數位孿生」、「真實 3D 建築」或「可室內導航」。目前是**以已知外輪廓繪出的建築量體示意**，不包含立面、屋頂、地勢、入口、高精度高度、樓板或無障礙通道。

## 來源與資料邊界

1. 校舍名稱、編號、用途及主顧樓樓層以[靜宜大學官方校園地圖實境導覽](https://www.pu.edu.tw/p/404-1000-1131.php?Lang=zh-tw)核對。官方另有[校史沙鹿校區地圖](https://archives.pu.edu.tw/p/412-1121-4218.php)，僅供核對，不重製照片、校方圖像及 720° 環景。
2. 建築座標及 OSM way ID 沿用專案共用 `packages/shared/src/providenceCampus.ts` 已記載來源的資料。此功能只請求其中 `cross-checked` 且來源為 OpenStreetMap way 的地點，不把公車站、停車場或單點建物硬擠成立體建築。
3. 伺服器向固定的 [OpenStreetMap Overpass](https://overpass-api.de/) 服務查詢指定 way ID，並檢查來源、閉合輪廓、座標是否在靜宜附近、合理面積、重複 way、形狀自交、非相鄰邊界相接與重疊。輪廓必須涵蓋對應的校舍 POI，或其邊界距離該 POI 不超過 30 公尺；避免 OSM way 遷移後仍冠上原校舍名稱。這是資料漂移容差，**不代表入口位置已驗證**。限制最多 128 筆來源圖徵、每棟最多 160 個頂點；避免把外站任意資料顯示成靜宜的校舍。
4. 即使 way ID 已在白名單內，也要確認 Overpass 回傳仍具有有效的 `building=*` 標籤；已移除建物標籤或標成 `building=no`、`construction`、`proposed`、`roof`、`ruins` 等不呈現完整建築量體。即使保留 `building=yes`，如同時帶有非否定的 `demolished:building`、`disused:building`、`abandoned:building`、`construction:building` 等生命週期標籤，也先拒絕渲染並待來源重新核對；這類互相矛盾的標籤不能當作建築仍存在或可進入的證據。另檢查 OSM 也常使用的非前綴生命週期標籤（如 `building=yes` 同時有 `ruins=yes`、`demolished=yes`、`construction=yes`），以及 `ruins:building=*`；不將已成廢墟、拆除或施工中的圖徵擠出成完好的地面建築。明確的 `no`／`false`／`0` 狀態不會單憑該欄位排除正常建築。 若生命週期標籤存在卻是空字串、只有空白或非文字／`null`，視為狀態不明，**不繪製完整建築**；只有標籤不存在或明確否定值才可繼續檢查其他條件。此判斷已加入 parser 與公開 API 回歸測試。這是保守的資料呈現規則，不等於每個 OSM 標籤均經實地確認；參考 [OSM 廢墟標籤](https://wiki.openstreetmap.org/wiki/Key:ruins:building) 及[停用／廢棄標籤](https://wiki.openstreetmap.org/wiki/Key:abandoned)。無來源時保留地點標記而不補造建築。此判斷只表示 OSM 圖徵可用於外框示意，**不證明建物目前開放或可進入**。
5. 目前只支援地面起算的整棟外框量體；若白名單 OSM way 同時帶有 `building:part=*` 且不是明確 `no`／`false`／`0`，或誤以 `building=part` 標示，**不把它畫成完整校舍**。OSM 的 [Simple 3D Buildings](https://wiki.openstreetmap.org/wiki/Simple_3D_buildings) 明確區分整棟 `building=*` 與多段 `building:part=*`：後者可能只代表不同高度的某個分段。空字串、非字串亦不視作已確認的完整建築；仍保留 POI、平面地圖與導航。這項保護不代表已找出隱藏於其他 way 的所有 3D building parts，也不等於完成了真實建築外觀。已補 parser 與 API 回歸。
6. 若 OSM 另有非零或無法確認為零的 `min_height`／`building:min_level`，代表圖徵可能從高於地面的標高開始；目前量體是由地面直接擠出，無法正確呈現這種高架／架空建築部位，因此**先排除該圖徵**，保留已核對的地點標記與導航，不補造底部牆面。只有明確的零偏移才按一般外框處理。此規則依 [OSM `min_height` 定義](https://wiki.openstreetmap.org/wiki/Key:min_height) 與 [`building:min_level` 定義](https://wiki.openstreetmap.org/wiki/Key:building:min_level) 設計，並有模擬 OSM 標籤回歸，**不代表已實地確認哪些靜宜建築有架空結構**。
7. 若 OSM `height` tag 是可解析的公尺數值，僅用於示意高度；支援明確公尺小數至六位，例如 `18.125 m` 或 `18.125m`，避免把有效的來源高度誤換成 12 公尺。明確的 `50 ft`、`50 feet`、`50'6"` 等英呎／英吋標籤，現在依 `1 ft = 0.3048 m`、`1 in = 0.0254 m` 精確換算；英吋不得達 12，其他單位、區間、逗號小數及超出合理範圍的值仍拒絕。換算結果仍是 OSM 使用者標註，**不代表校方測量或實地驗證**。**只有完全沒有 `height` 標籤**時，才以 12 公尺的視覺示意值繪製；如果標籤明確存在，但值是無法解析的單位、空白、`null`、非文字或不合理數值，會直接略過該立體量體，保留 POI、平面地圖與導航。不得把「資料明確矛盾或格式未知」與「沒有高度資料」混為一談，憑空畫成 12 公尺。OSM 使用者標註不等於校方或實地測量。`building:levels` 不用公式直接猜高度。此解析有模擬標籤回歸，但實際靜宜 way 是否含此格式仍待線上查核。
8. 立體化來源需顯示 **© OpenStreetMap 貢獻者** 與[授權資訊](https://www.openstreetmap.org/copyright)。OSM 原始資料遵循 ODbL；如未來將修改後的建築資料對外散布，需再檢查相應署名與資料庫授權義務。正式產品應確認快照更新、API 使用政策與容量。

## 選定校舍的高度來源標示

空間導覽選定靜宜校舍後，詳細資訊會對**該棟**通過檢查的 OSM 外框說明高度依據，而不只在全校資訊列寫「OSM 標註或 12 公尺示意」。若來源有合法的 `height`，顯示轉換後公尺數與「OSM 使用者標註，非校方實測」；若沒有高度標籤，只顯示「12 公尺示意，非實際樓高」。已選地點沒有可用外框時，明確寫明只顯示原地點標記、**不是已確認的入口**；在地圖套用同校地點篩選後，選取資訊依當下可見外框重算，不延續已被篩掉的舊高度。

這是 React 元件與資料來源呈現修補，回歸使用合成 OSM 資料的三種情境（標註、示意、無外框）；**未進行真實 Overpass 逐棟查核，也不能據此宣稱現地樓高或導航正確**。

## 可靠性

- **非完整 HTTP 2xx 回應不作為建築來源**：公開 Overpass 完整 JSON 查詢只接受 HTTP `200 OK`。Fetch 的 `response.ok` 對 `203 Non-Authoritative Information` 與 `206 Partial Content` 仍為 true，但這些狀態不足以證明取得完整、未被代理改寫的 OSM 輪廓；即使 body 可解析為合法 JSON，也不建立新的 24 小時快照。異常回應立即嘗試取消未讀串流，依既有 503／`no-store`／10 分鐘冷卻流程處理；先前仍在七天期限內的已驗證快照維持標示來源日期的 `stale` 備援。新增 203、206 及原有快照更新遇 206 的 API 回歸；**尚未取得真實 Overpass 發出此類狀態的樣本**。

- **HTTP `Content-Length` 格式必須正確**：若 Overpass 或中介代理宣稱有回應長度，只接受純十進位非負整數，且不得超過 500,000 bytes。空字串、科學記號、十六進位、小數及超大數一律拒絕並嘗試取消未讀串流；不能把 `Number()` 可轉換的字串誤認為合法 HTTP 長度。沒有此標頭的合法分塊回應仍按逐塊解碼 byte 上限讀取。新增模擬回歸驗證無效長度在 12 秒總逾時前快速回傳 503／`no-store` 且不反覆回源。尚未取得公開 Overpass 真實異常標頭樣本。

- **拒絕上游重新導向，守住伺服器出站範圍**：Overpass 查詢僅使用固定 `https://overpass-api.de/api/interpreter`，並設定 Fetch `redirect: 'error'`。若來源回傳 `Location` 指向其他網站、內網位址或同站其他路徑，伺服器不自動跟隨，依既有 503／`no-store`／冷卻備援；避免固定公開資料源被 3xx 改寫為任意伺服器請求。新增模擬 302 指向 `127.0.0.1` 的 API 回歸，驗證 Fetch 選項、拒絕與快取隔離；另外以 Node.js 22 原生 Fetch 的本地 HTTP 重新導向試驗核對 `redirect: 'error'` 不會請求目標。**不是**對公開 Overpass 真實連線或內網漏洞的入侵測試。若未來合法換網址，需重新審查固定端點與來源政策，不自動信任跳轉。

- **服務端完整請求期限**：除了向上游傳送 `AbortSignal`，伺服器現在對 **fetch 與串流 body 讀取整段流程**設 12 秒獨立期限。即使不可靠代理不回應中止訊號、連線或回應本體永遠不結束，也能解除共用 pending 狀態，依原 10 分鐘失敗冷卻回傳 503／no-store；沒有直接將失敗的資料當作有效輪廓。新增 2 組假上游「永不回應」與「headers 已收到但 body 永不結束」的受控時鐘回歸，另驗證冷卻後可以重新取得輪廓。**這是伺服器 request 狀態的防卡住測試，不代表公開 Overpass 或實機網路已實測**。中止訊號不受遵守時，底層連線的釋放仍取決於網路實作；正式高流量需額外監控連線與並行資源。
- **超量／異常 Content-Length 先行拒絕**：若上游 HTTP 標頭明示超過 500 KB，或長度格式非法，伺服器尚未讀取 body 即回到 503／冷卻流程，同時對尚未讀取的串流發送 best-effort 取消，不把已拒絕的回應留在背景傳輸。即使 `cancel()` 永不完成也不會阻塞 API；新增超量及多種非法標頭格式的模擬回歸，要求 1 秒內結束且避免再次回源。此測試只驗證應用層取消訊號，不保證代理／TCP 已立即斷線。
- **超量回應的取消不阻塞 503**：逐塊串流讀取超過 500 KB 時，取消上游 reader 仍會發出，但**不等待 `reader.cancel()` Promise** 才結束原本已確認的超量錯誤；有些代理或串流在取消後永遠不 settle，舊行為必須拖到 12 秒整體 deadline 才回傳 503。新增永不完成的 `cancel()` 模擬，要求 1 秒內（遠短於整體 deadline）得到 503／`no-store`，避免無效資料持續佔用共用 pending 狀態。取消底層網路資源仍屬 best-effort，且本測試不是公開 Overpass 實際傳輸量測。
- **Overpass 資料庫同步時間**：若上游 JSON 附帶 `osm3s.timestamp_osm_base`，會另外檢查它是否為有效 UTC 日期、沒有超前伺服器時間逾五分鐘，且與查詢當下相差不超過 **48 小時**；否則不將整份輪廓誤標成最新快照，改走既有舊快照期限或 503／地點標記備援。這是上游**資料庫複寫狀態**，不是建築 way 最後編輯日期，也不是實地確認時間。若回應**整個省略 `osm3s`**，為相容舊格式／既有測試資料，仍只依建物白名單、幾何與抓取時間檢查；但**明確包含 `osm3s` 卻缺少 `timestamp_osm_base` 或設為 `null`**，屬來源同步日期不完整，現在會拒絕新快照，保留先前有日期標註的合格過期備援或回傳 503。此修補有拒絕新快取、保持舊快照的回歸案例；**尚未取得真實 Overpass 成功回應**。
- **同步延遲會縮短新鮮快照壽命**：有合法 `osm3s.timestamp_osm_base` 時，新鮮快取期限取「HTTP 抓取後 24 小時」與「OSM 資料庫同步後 48 小時」較早者。若資料庫已落後 47 小時 30 分，建築快照最多只可再被標成新鮮 30 分鐘，CDN `s-maxage` 也不得超過該期限；到期後需重新詢問上游。若上游仍未追上，走既有有日期標示的舊快照／503 備援，不假稱資料仍新。缺少同步 metadata 的舊格式仍沿用原 24 小時快取規則。已補受控時鐘回歸，真實 CDN 與 Overpass 時延尚待驗證。
- **瀏覽器再次檢查同步時效**：即使 CDN 或中介快取仍回傳 `stale=false`，只要裝置端計算已達 `OSM 資料庫同步時間 + 48 小時`，前端也會把仍在七天備援期限內的輪廓標記為「暫用舊快照」，不誤稱最新；`osmBaseAt` 缺省的舊回應仍依原 HTTP 抓取後 24 小時標準判斷。這是前端的二次防護，不代表已完成線上 CDN 或校園現況測試。
- **日期顯示不混淆**：API 另外傳回經來源驗證的 `osmBaseAt`，3D 視窗同時標示「資料讀取」與「OSM 資料庫同步」。兩者不可互稱，且都不是實地查證日期。前端會再次檢查同步時間的 UTC 格式、與原始快照抓取時間的先後關係（最多 5 分鐘時鐘差），以及兩者不超過 48 小時；遭修改的異常來源日期不得在視窗顯示為可靠資料。沒有 `osm3s.timestamp_osm_base` 的舊快照保留既有輪廓檢查，但不憑空顯示同步日期。此處以 mock API／React 回歸驗證，尚未確認公開 Overpass 真實同步時間。
- 服務端有 24 小時記憶體快照，CDN 公用快取最多 1 小時且**不可超過該快照剩餘有效秒數**：例如在快照失效前 10 秒讀取，回應 `s-maxage=10` 而不是額外快取 1 小時。快照過期後必須回源確認，失敗時依下方規則標示舊資料或停用建築，不延長「最新」狀態。此行為已有模擬時鐘與 HTTP 標頭回歸；尚未在真實 CDN 驗證。
- 服務端有 24 小時記憶體快照、同時請求共用、一般上游失敗後至少 10 分鐘冷卻；若 Overpass 回傳 HTTP 429／503 並提供有效 `Retry-After`（秒數或 HTTP 日期），尊重較長的伺服器等待要求（上限 24 小時），並回傳對應剩餘等待秒數供客戶端參考。不會在被限制時每 10 分鐘強制重試。避免使用者每次開 3D 都直接對 Overpass 發出大量請求。另有 500 KB 逐塊串流回應上限及識別 nuni 的 User-Agent，避免惡意／異常回應一次耗盡記憶體並符合公開 Overpass 的使用辨識要求。跨多台伺服器的冷卻不會共享；若流量成長，應改成受控的離線定期快照，而不是大量查公開 Overpass。
- 向 Overpass 請求 `out meta geom`，公開輪廓附 OSM way 版本與最後編輯時間（僅保留 `version`、`timestamp`，不回傳編輯者帳號等資訊）；在選取建築時顯示。**圖徵最後編輯時間不是資料抓取時間，更不是現場查證時間；OSM way 的節點可能移動而不改變 way 版本。** 舊快照或缺少合法 metadata 時不虛構版本；若 way 最後編輯時間比伺服器／裝置時鐘超前逾五分鐘，也只移除不可信的版本與日期，保留已通過獨立位置／建築標籤／外框驗證的輪廓，不宣稱該筆編輯時間已核實。
- **非成功 HTTP 回應也要釋放串流**：`fetch` 在收到 HTTP 標頭後即完成，Overpass／代理回傳 406、429、503 或其他非 2xx 時，錯誤回應的 body 仍可能持續傳送。既然我們只需要狀態碼與 `Retry-After`，後端現在會對未讀取的錯誤 body 立即發出 best-effort `cancel()`，不等待取消 Promise 才進入既有冷卻／503；避免已確知的上游拒絕仍持續佔用無用串流。新增 406／429／503／500、取消永不完成的模擬回歸，檢查快速結束、`no-store`、冷卻與不重試。這只證明應用層發出取消，**不代表公開服務已解除拒絕或代理的 TCP 連線已實際釋放**。
- **HTTP 406 存取阻擋保護**：公開 Overpass 伺服器若回傳 406（可能代表 User-Agent／來源遭拒），不再每 10 分鐘對同一來源重試，而是於目前服務實例暫停回源至少 **24 小時**。無快照時 API 回傳 503／`no-store` 與剩餘 `Retry-After`；仍在七天期限內的既有快照只作**標日期的舊資料備援**，不重新標為最新。此決策避免因反覆查詢加劇公共服務的拒絕／封鎖；回應 406 的根本原因仍須查看服務端記錄與上游政策，**24 小時並不保證解除封鎖**。已新增受控時鐘 API 回歸，非即時線上解除封鎖驗證。參考 [overpass.ch 對 406 與封鎖的說明](https://overpass.ch/guides/overpass-api-ip-banned)。
- 公開 Overpass 可能因負載限制回傳 429／503。現在會識別 `Retry-After` 的秒數或 HTTP 日期，遵守較長的冷卻並在舊快照仍有效時繼續標示舊資料。無快照時維持 503／`no-store`，不將 429 當成成功抓取建築輪廓。測試使用模擬回應，**不等於實際對公共 API 的容量或 SLA 驗證**。
- Overpass 回應若同時包含兩筆相同的**已核對建築 way ID**，即使其一的輪廓與標籤看似正確，也拒絕整份回應；同一圖徵不可能在一次查詢中同時具有兩種高度或外框。不能依回應順序默默取第一筆並宣稱來源可信。其他未列入建物白名單的圖徵不影響既有安全資料。已加入 parser 與 503／不快取 API 回歸。
- 除了服務端拒絕重複的已核對 OSM way ID，**前端也拒絕 API 快照中重複的已核對校舍 POI ID**，不論重複項的樓高、名稱或外框是否合法、順序如何。出現矛盾時整份校舍量體快照不呈現，保留原地點標記、步行導航及手動重試入口；非白名單的停車場或其他地點不會冒充校舍。已新增來源重複、異常第二筆與調換順序的回歸案例。這是防止資料混淆，不是線上 OSM 的逐棟實地證據。
- Overpass 的 JSON **即使 HTTP 200 也可能附帶 `remark`**（例如查詢逾時、記憶體不足），且 `elements` 可能只回傳部分結果。API 現在會拒絕所有帶頂層 `remark` 的回應，不把局部建物當成 24 小時完整成功快照；已有快照時依下述期限顯示過期備援，否則 503。此情況納入 API 回歸測試。參考 [Overpass 回應錯誤說明](https://overpass.ch/guides/overpass-api-errors)。
- 已有快照但更新失敗時會回傳來源時間與 `stale`，前端標明「暫用舊快照」。**HTTP 抓取日期或可驗證的 OSM 資料庫同步日期滿七天（取較早失效者）即不再提供舊建築輪廓**，改回傳 503 並保留原地點標記／平面地圖／外部步行導航，避免把長期失效資料看成現況。七天只是過期防護門檻，不等同現場核實期限。首次無快照且連線失敗時也只顯示原地點標記。
- 建築輪廓請求失敗時，靜宜 3D 視窗提供「重新讀取建築輪廓」，不用關閉空間導覽即可重試；重新讀取只發生在使用者點擊後，不自動無限輪詢。API 仍遵守 Overpass 的失敗冷卻與 Retry-After；按重試不保證服務已恢復，失敗時既有 POI、平面圖與導航仍可操作。
- **校園地圖篩選時同步限縮建築**：空間視窗仍開啟時，若使用者切換為只顯示部分地點，3D 只接受目前 `model.points` 內的 POI 所對應建築輪廓。畫面上的「公開建築輪廓」棟數、選定地點的 OSM 版本資訊及相機最高量體取景，都以目前可見 POI 為準；已被篩掉的舊輪廓不應暗中拉遠視角或在資訊列繼續計數。用同校清單更新的元件回歸與無可見 POI 的 Three.js 相機斷言保護這個行為。這是模擬地圖清單／WebGL 邊界測試，並非手機 GPU 實測。
- **狹窄螢幕選定長形校舍時的取景**：先前相機只依地圖總半徑推算固定 140–260 公尺選定範圍；即使實際 OSM 外輪廓在 POI 其中一側延伸更遠，320px 手機畫面仍可能裁切校舍。現在選定具有可用 OSM 外框的 POI 時，另以輪廓頂點相對該 POI 的經緯度公尺距離加上標記邊距來調整水平／縱深取景；不重新捏造輪廓、入口或中心點，也不讓其他未選定建築左右局部視角。新增合成長形外框對照狹窄視窗的 Three.js 相機回歸；測試是幾何／相機行為，仍不是靜宜真實校舍輪廓或手機 GPU 實測。\n- **選定建築時的局部取景**：從校園總覽點選某個 POI 後，相機只用該 POI 對應的建築高度（沒有 OSM 量體時沿用一般標記高度）決定垂直取景，不再因同一地圖仍顯示另一棟較高建築而拉遠、縮小目前要看的校舍。返回總覽時仍保留依所有可見量體最高點取景。新增「兩棟都在地圖、僅其中一棟被選定」的 Three.js 相機回歸；合成高度只用來測試取景邏輯，**不代表靜宜實際樓高或實機 GPU／校園辨識成果**。
- Three.js 僅在開啟空間視窗時載入；對話框關閉、場景失去可見性或 WebGL 失敗時沿用原本的資源釋放、焦點、鍵盤、低動態與備援流程.前端建築輪廓請求最長等待 15 秒（含回應本體讀取），逾時中止請求，**即使上游代理或回應本體不遵守 AbortSignal、Promise 永不結束，也會獨立結束讀取提示**，保留原有 POI、平面地圖與步行導航。逾時後才到的合法資料不可重新覆蓋失敗狀態；使用者可自行重新讀取。元件回歸模擬不遵守 abort 的延遲回應與逾時後成功，驗證不會無限等待或使用過期請求結果。此測試不代表公開 Overpass 線上可用性、手機實機效能或現地驗收已完成。
- 前端對回傳資料再次檢查學校 ID、建築 ID、來源網址、名稱、範圍及數值，阻止跨校或惡意輪廓混入。另要求 API 快照明示 `OpenStreetMap`、標準 ISO 抓取日期與布林 stale；若裝置時間判定抓取日期或已提供的 OSM 資料庫同步日期已達七天、日期非法或超過五分鐘的未來時間，一律不顯示舊建築。即使快取錯報 `stale=false`，滿 24 小時仍顯示舊快照提示；裝置時鐘大幅失準時會保守回到 POI 與步行導航。尤其 `illustrative` 高度必須嚴格等於固定 12m，不能接受外部 API 中自行膨脹的 99m 示意樓高；若回應不一致，該建築不會顯示，保留原有 POI 導覽。

- **全校總覽地面與建築外框對齊**：過去總覽的地面尺寸／相機距離只看 POI 位置；若已驗證的 OSM 建築外框遠超過對應 POI，校舍可能落在地面以外並在窄螢幕被裁掉。現在統一用與 3D 量體相同的地理座標換算，擴展總覽地面及相機包覆範圍到**當前可見**的外框頂點；被篩掉的 POI 或未核實的輪廓不參與計算。新增 320px、合成長形外框的 Three.js 地面尺寸／相機回歸測試。這只是幾何與取景修補，尚未證實真實靜宜輪廓、GPU／視覺品質或競品優勢。

- **POI 與屋頂圖釘的對位**：OSM 外框可能在既有 POI 位置附近（允許最多 30 公尺誤差），但 POI 並不一定落在建築多邊形內。原本只要接受輪廓，就會把 POI 圖釘升到該棟示意／OSM 高度，造成屋頂以外的空中漂浮圖釘。現在只有 POI **確實位於已接受外框內，且 OSM 具有可解析的來源高度標註**才使用屋頂高度。若 OSM 沒有高度資料，即使 POI 落在建築外框內，12 公尺也只是視覺示意量體，圖釘必須留在原地面座標；外框外的 POI 也保留地面標記和資訊操作。建築量體及相機取景仍保留。新增來源外框內／距外框約 18 公尺的**合成**案例，檢查 Three.js 實際圖釘矩陣與建築擠出數；不把 POI 自動改寫成入口、教室或步行終點，也不將合成資料宣稱為靜宜現況。


- **上游回應讀取逾時也必須取消 body reader**：`fetch` 已拿到 200 標頭後，回應內容仍可能只傳一部分便停止；單靠中止原先的 `fetch` 不一定會取消已交付給 `ReadableStream` 的讀取器。現在 12 秒伺服器 deadline 會額外向 body reader 發送取消要求，不等待可能永遠不完成的取消 Promise；被中止的分段 JSON 不得被當成完整 OSM 快照。新增先送出語法完整的 JSON 片段、但永不結束串流的 API 回歸，檢查取消、503／`no-store` 與不快取。Node.js 22 原生串流的獨立重現觀察到取消要求一次且等待中的 read 結束；**正式專案測試、線上 Overpass 實況及網路連線是否真正釋放，仍以新 head CI／現地驗證為準**。

- **非地面 OSM 圖徵不擠出為地面校舍**：即使 way ID 已在校園白名單內，後續編輯仍可能帶入 `location=underground/underwater/roof/overhead`、非零 `layer`、`bridge=yes` 或 `tunnel=yes`。目前立體化只支援從地面開始的整棟外框；沒有可靠的基底高程、上下層幾何時，這些圖徵必須被排除，而不是把地下空間或懸空建物繪成從地面延伸的牆。沒有定位標籤、明示 `location=surface`／`layer=0` 與 `bridge=no` 等否定旗標時，仍須通過原有 way 白名單、座標、外框及樓高檢查。新增加 OSM parser 的正反例及 API 503／`no-store`／冷卻回歸，使用**合成標註**，不代表已發現靜宜真有地下或橋上校舍，也未完成實際 Overpass 抽樣。參考 [OSM location 語意](https://wiki.openstreetmap.org/wiki/Key:location) 和 [建築局部／基底高度](https://wiki.openstreetmap.org/wiki/Key:building:part)。
