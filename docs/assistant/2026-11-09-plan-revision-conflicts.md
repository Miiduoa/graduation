# 原行程修訂：完整預覽與時間衝突

## 重現與原因

在 0b629b50 的固定服務 fixture 中，使用真實修訂問題、runner、工具、簽卡與確認流程：

1. 保留「寫作業：樹與圖作業」18:00–19:00，要求把另一筆程式練習改到同一時段。
2. 原修訂問題包含「原安排」，一般文字路由因而只提供 propose_study_plan。
3. 同輪第一項成功簽卡，第二項由既有衝突規則回 EVENT_CONFLICT。
4. runner 留下第一張卡；handler 只核對保留內容，仍回 200。該剩餘卡可以確認並造成一筆 fixture 寫入，使用者要求修改的另一項消失。

另一個真實 runner fixture 證明：模型提出逐筆 personal_event 時，原修訂流程未提供該工具，之後自動改排目前未交作業。這是原修訂流程與一般規劃規則的整合缺口。

## 修訂範圍

每次修改都傳送既有 planProtection 結構，包括未勾選保留時的空 protectedIndices。這是原提議內容及修訂模式的識別，不是寫入授權。BFF 驗證後才設定內部 planRevision；外部請求不能自行提交這個內部欄位。

修訂只提供既有課表／行程／空堂讀取與逐筆 personal_event 預覽，保留工具預算及多輪提議。一般安排作業、點餐、開頁的自動補救不介入。相對日期不再被套用到整批；名稱、日期、起訖不經口語時間或作業名稱的補寫規則。每筆仍通過原 eventArgs、日期及衝突驗證後才簽卡。

修訂有任一步驟失敗或預算／輸出中止時，整份候選失效，不回傳剩餘可確認卡。EVENT_CONFLICT 回固定的時間衝突提示；其他失敗提示核對日期、時間與條件。工具曾失敗即使模型後續改提別的時間，也要求使用者再重新預覽，避免默默接受替代安排。模型無卡或非行程結果同樣不構成可用修訂。

UI 保留修改文字、保留選擇及另一題草稿。修正條件後可重試；已撤銷的原提議不重複撤銷。新卡仍須逐筆手動確認。

## 沿用的排程與執行政策

沒有新增第二套時間比較器，也沒有新增允許重疊選項。既有 Web 工具使用完整日期、跨日 endDate 與 +08:00（台北時間）比較半開區間；相接端點允許，全天結束日為排他。同批卡、已同步事件及可定位的課表都在簽卡前核對。

確認前的本機預檢、原 token／帳號／校園／參數摘要、有效期、ledger revision、前一步 hash、CAS 與結果讀回全部保留。未知結果仍只核對原操作。本輪不修改已寫入行程、簽章格式、權限或環境開關。

一般問答沒有修訂結構時仍沿用現有 partial-result 行為；手機 #540／#542 的批次與空堂政策不改動。

## 驗證與限制

固定 Node 服務契約使用真 handler、runner、工具、簽卡及確認；只替換帳號／資料 adapter 與模型 provider，且禁止外部 fetch。JSDOM 測試驗證錯誤提示、輸入保留、重試與手動確認；它不是真實瀏覽器驗收。

覆蓋保留與未保留項目的衝突、同批新增項目的衝突、完整跨日與台北時間、端點相接、同名項目、無效時間、舊卡及過期卡、零保留、多輪提議、一般問答隔離。實際最終版本的通過數、lint／typecheck 與 CI 狀態另附交付紀錄，不能由本文件推定。

成功代表所有已嘗試的步驟成功，不能證明模型從未漏掉一個未嘗試的未鎖定項目；使用者也可要求增刪，不能硬套原筆數。既有前後差異摘要及重新手動確認仍是必要步驟。同名且無可靠對應的變更仍依既有保留驗證拒絕，不使用模糊配對。

本輪沒有再次啟動瀏覽器，也沒有改環境以繞過 EPERM。沒有真實帳戶交易、校務抓取、部署或合併。
