# 各角色工作流程整理（2026-11-17）

## 這次要解決的問題

前一輪已整理「今天、課務、生活」及服務目錄，但工作身分仍容易與一般生活功能混在一起：店家需要先找到自己的門市，教師要區分授課課班與校方申訴，宿舍職員可能在未選校或登入失效時看到空白頁。角色名稱存在於程式中，也不表示相應服務已完成串接。

這輪把順序整理為「確認目前帳號與校園 → 顯示已獲授權的工作 → 完成一件事 → 查看結果或處理下一件」。一般日常仍保留；同一個人兼任教師、社團幹部或店員時，以實際課程、群組與門市資格顯示工作，不要求重新註冊或自行選一個更高權限的身分。

## 共同流程規則

1. **先核對範圍，再顯示工作。** 瀏覽校園與登入身分分開；選校不改授權。工作頁須明確取得目前帳號、學校或門市，再載入私有內容。
2. **登入應接回原位置。** 宿舍與教師入口保留校園；平台管理沿用原案件返回位置。帳號不同時重新確認服務資格。
3. **讀不到資料，不當成沒有待辦。** 無法讀取身分、申請、門市或申訴時，顯示重試，不自動切成新申請或空待辦。
4. **失敗可以接續。** 教師同帳同校的回覆草稿可跨篩選及讀取失敗保留；換帳號／校園時移除上一範圍的內容。處理結果不明先讀回，再決定下一步。
5. **完成後有去處。** 教師決策進已處理清單，門市操作可回工作台，宿舍居民需求有對應服務頁；主要工作以外的日常入口維持可找到但不搶占第一層。
6. **導覽不代替授權。** 工作卡與角色首頁只推薦已存在路徑；每個目的地仍核對自身服務資格。沒有修改伺服器 ACL、資料庫規則、登入 token 或服務開通旗標。

## 整合設計與驗證

首頁直接沿用已確認的課程來源，沒有為顯示教學身分再查一次課程。純授課帳號的課程清單只保留在教學待辦；兼任者的教學工作放在「我的工作」，超過兩門按需展開。每門課保留原本的來源網址，學校課程不被導向另一套 Google 課班。首頁 Agent 與對話助理使用各自的 React key，避免相鄰元件重用同一識別。

身分重試保留原按鈕與讀取狀態，確認期間停用舊工作入口。鍵盤操作成功後將焦點接到結果標題；結果為空時保留一次確認狀態並接回日常。校內角色使用目前帳號與校園的有效伺服器快照，撤權、快取資料、本機未確認寫入與 A→B→A 切換都不能復活先前的管理入口。

校方公告管理另區分資格確認中、已確認無權限與讀取失敗，三者均保留重新確認或同校公開公告出口。取得伺服器確認前暫停編輯；缺少會員或撤權不會停在無限等待。公告工作區依帳號與學校隔離，切換範圍或撤權會清除先前清單與編輯內容，舊查詢及儲存回應也不能影響新的工作區。

### 瀏覽器驗收

新增 `Role Workflows Browser` 工作流程，直接編譯實際工作身分、店家申請、營運與訂單元件，僅替換網站外框及合成 Session／API。檢查 1440px 淺色、390px 深色及 320px 淺色；涵蓋鍵盤重試與焦點、授課展開、補件入口、門市草稿返回、訂單收合、次要申請與瀏覽器返回。所有寫入請求及外部請求在測試環境拒絕並列入報告。

本機可完成元件編譯、Python／Node 語法及工作流程檢查，但 Chromium 啟動受執行環境的 socket 限制，沒有將本機執行列為瀏覽器通過。遠端 `82d7fcc` 的 [Role Workflows Browser](https://github.com/Miiduoa/graduation/actions/runs/44043130826) 已完成 **9 組情境、69 項檢查與 24 張截圖**，全部通過；下載的 ZIP digest 及 34 個產品／驗收來源 SHA256 均核對相符，並已目視三種尺寸的工作入口、店家總覽、訂單與草稿畫面。後續公告資格修補未修改這 34 個來源。最終提交的瀏覽器結果仍以本 PR 新 head 的該項檢查及 artifact 為準。
