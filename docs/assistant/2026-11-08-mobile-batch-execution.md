# 手機助理：多筆行程確認、逐筆執行與接續

## 使用者得到的能力

延續單筆行程的真實寫入、讀回核對及操作紀錄恢復，這次將最多四筆明確行程接成一個可完成的任務。使用者先看完整預覽，只確認一次，助理依序執行；任何一筆結果不明、內容不同或保存證據有警告，後面的安排都會暫停。

範例：

```text
幫我安排以下行程：
明天 19:00 到 20:00 英文讀書
後天 18:00 到 19:00 資料庫複習
```

畫面也提供「填寫多筆行程範例」，只填入可修改的文字，不自動送出或執行。輸入須有明確批次開頭，每筆各有日期、開始時間、結束時間與名稱，以換行或分號分隔。整批共用同一個台灣日期參考時間，不猜測時長、不解析讀書計畫的說明文字，也不把提醒、交作業、付款等額外要求吞進行程名稱。一筆無效就不建立可執行的部分草稿。

完成的行程逐筆顯示核對時間，並能開啟手機個人行事曆中的實際紀錄。進度不來自使用者勾選，也不來自模型宣稱成功。

## 執行與中斷

1. 保存完整且不可變更的安排，讀回確認保存內容。
2. 使用者核對所有行程後，按「確認加入 N 筆行程」。
3. 重新核對已存在的原操作，檢查整批尚未開始的時段、重複、重疊與剩餘容量。
4. 逐筆使用既有單筆執行器。每一筆在真正寫入前仍重新檢查活躍帳號、學校、時間、衝突與操作證據；只有取得相符的真實行程回執才進入下一筆。
5. 遇到不明結果或警告便停止後續，保留每筆已完成、待核對或尚未開始的狀態。
6. 使用者可以重新核對整份行程；原操作全部解決後，按「確認接續剩餘 N 筆行程」才會執行其餘安排。

整批預檢減少可預先發現的部分完成，但多筆不是同一個交易。處理途中其他畫面仍可能修改行事曆，或原生儲存可能失敗，因此已完成的行程不會因後一筆失敗而被刪除。

「停止後續行程」撤銷本次尚未開始的後續操作，不宣稱撤回已送進原生儲存的寫入。即使使用者離開畫面，晚到結果也不能驅動下一步。「取消尚未開始的行程」另保存取消決定，既有行程與待核對的原操作證據都保留。

## 恢復不等於授權

`assistantCalendarBatchStore.ts` 只保存 plan：批次 ID、帳號、學校、建立時間，以及固定順序的步驟 ID／完整事件。另可保存單向的 `cancelledAt`。它不保存寫入許可、已嘗試旗標或成功收據。

真正的操作仍由原本 `assistantCalendarJournal.ts` 保存：只有單筆執行器的持久 attempt 紀錄與實際 ledger 讀回才具有操作證據意義。批次內沒有操作證據的項目是尚未開始；紀錄讀不到時不能當作沒有操作。先前未知、被刪除或內容不同的操作只能沿用原 ID 核對，不能透過新批次另建一筆。

重新掛載助理畫面或重開 App 後，「找回的多筆行程」會讀取保存的安排，並重新核對原操作。沒有新的確認動作，就不建立新的單筆 proposal，也不呼叫寫入執行器。只有這次使用者明確確認後，才對成功查無既有 attempt 的剩餘項目建立全新的記憶體 proposal，交給原單筆執行器確認。

已保存但尚未執行的安排也能恢復，因此不會只找回第一筆收據，卻遺失後面原本要做的項目。切換回答模式保留安排；聊天全文、雲端對話與模式不跟著恢復。批次要求及其結果不會傳入之後的雲端或本地模型歷史。

## 範圍與容量

| 項目 | 契約 |
| --- | --- |
| 明確事件數 | 每批 2–4 筆；不自動推算日期或時長。 |
| 保存範圍 | 同一台手機、同一個已驗證帳號與學校。 |
| 帳號區隔 | Firebase 與 nuni 各用自己的 owner；雙登入不回退到另一個帳號。 |
| 批次安排 | 每個 owner／school 最多 64 份、256 KiB；不自動淘汰歷史。 |
| 單筆操作證據 | 沿用每個 owner／school 256 筆、512 KiB 的既有 journal 上限。 |
| 保存及唯讀期限 | 20 秒；逾時不把讀取失敗當成空紀錄。 |
| 每次批次執行期限 | 最長 80 秒；每筆仍有原本 20 秒期限。 |
| 重複安排 | 相同順序與完整事件重用未取消的 plan；相同名稱時段但不同完整內容不默默覆寫。 |
| 時段衝突 | 檢查同批事件與裝置個人行程；尚未整合完整課表／校方排程的衝突驗證。 |

批次保存使用獨立 namespace `campus.assistant-calendar-batches.v1`。嚴格驗證版本、欄位、scope、日期、重複及容量；保存需逐位元組讀回相同序列化內容。超量、損壞或讀回失敗保留原資料並停止新的安排。逾時不釋放仍未完成的原生 I/O 鎖。

行程是本專案的手機個人行程資料，不表示已同步 Apple／Google 行事曆、排程通知、向校方提交，或完成作業。清除 App 資料、移除 App 或換機後的恢復不在本輪範圍。

## 多張卡片的一致性

同一事件可能同時出現在單筆訊息、批次訊息及恢復區。每次確認或核對結果會更新相關可見卡片，恢復區不重複呈現已在聊天內的同一份安排。重新載入的證據也更新舊聊天卡，避免新查核發現行程不存在，畫面卻仍顯示舊成功狀態。

既有 canonical identity 只用於找回原操作；批次仍逐欄比較完整預覽事件，包含地點。找到同名稱與時段但內容不同的操作時，該步驟標為內容不同，不計入完成，也不把針對不同預覽的錯誤投影傳給其他原本相符的卡片。

## 驗證

新增測試使用真實批次 store、原單筆 journal、原執行器及個人 ledger，只在原生儲存邊界注入讀取失敗、回應遺失、暫停與晚到寫入。

- 解析：完整 2–4 筆、共同日期參考、標點、缺漏欄位、無效時間、交疊、複合操作及控制字元。
- 保存：不可變更的預覽、讀回驗證、scope、取消持久化、損壞、容量、並行與逾時。
- 執行：整批預檢、逐筆回執、未知結果停後續、相同 ID 核對、再次明確確認才接續，以及取消與登入切換。
- 畫面：完整預覽、一次確認、防連點、真實行程入口、停止後續、離開畫面與重開恢復。
- 整合：第二筆回應遺失不寫第三筆，晚到保存核對成功後再確認接續；單筆與批次共用原操作；雙登入、雲端歷史隔離與模式切換。

這些測試驗證受控情境下的結果，不等於真機被 OS 終止的實測或競品任務完成率比較。精確測試結果與提交狀態見 PR 的本輪驗證紀錄。
