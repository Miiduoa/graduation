# 角色任務定位與跨功能工作安排

本輪從 `f7f5acba2177562ed42ea73067d094b6e7946edb` 的 main 延伸既有 Web Platform Assistant V2。實作、測試與可用範圍以本文件列出的程式為準；合併、部署和真實帳號驗收另以 PR 的精確版本紀錄判定。

## 2026-11-24 原生 App 工作情境與校園圖書館

原生 App 的平台帳號助理現在也可選下表六種工作情境。學生仍可從課表接續查作業。其他五種情境提供各自的工作名稱和操作範例。校園帳號的雲端助理沿用該帳號自己的操作授權。

- **找工作時段**。在教師情境輸入「找明天下午一小時備課」。助理先讀這台手機上該帳號、該校園的課表與個人行程。範圍為台灣時間今天起七天內、每日 08:00–22:00，從兩堂已存課之間找出符合長度的空檔，避開既有行程並保留前後各十分鐘。缺少適用課表時會說明。門市班表、其他人的空閒和場地要在對應工作區查。
- **建立個人行程**。改說「安排明天下午一小時備課」，會先檢查平台帳號的「新增個人行程」設定，再預覽日期和起訖時間。按確認時重新核對權限、課表與個人行事曆。若時段已被占用，當次停止。成功後可開啟這台手機保存並讀回的行程。店家盤點、社團籌備、校務會議及平台維護使用同一收據流程。
- **找官方館藏與館址**。在 Web 輸入「查本校圖書館的館藏網址，這間圖書館在哪裡」。第一步依所選校園取得官方館藏入口，第二步才拿實際館名查同校地圖。缺少登錄館名時，地點查詢停止。原生 App 支援單句查館藏入口，點選可開啟校方網站，實際書目、在架狀態及開館時間以校方服務為準。

選擇教師、店家等工作情境只影響這次任務。授課概況、門市營運概況可由 Web V2 使用既有授權來源查詢；原生 App 目前將這些要求導向對應工作區。教師成績發布、店家退款、社團群發與平台帳號處置仍由各工作區核對對象與操作資格。

本次變更後，Web 的 46 個服務入口中，20 個列有可讀取的資料，5 個可準備待確認操作，26 個仍只提供服務入口。可準備操作的服務也可同時計入讀取。官方館藏名錄列有 21 所學校，地圖能否定位仍取決於該校的地點資料。

## 設計決定

Agent 採共用任務核心，各角色有自己的工作目的、可用工具、資料來源與回覆重點。同一個人可以同時是學生、助教、社團幹部和店家，使用者切換的是當次工作情境。實際資料權限仍由登入身分、校園、課程、社團或門市的正式服務核對。

| 情境 | 工作目的 | 主要資料範圍 | 本輪可直接使用的例子 |
| --- | --- | --- | --- |
| 學生與個人 | 安排課業與生活 | 本人課表、待繳作業、行程、買家訂單與可見社團 | 查待繳作業、找相關教材，再安排讀書時間 |
| 教師與助教 | 整理教學工作與準備時間 | 已授權授課課程的作業、測驗與收件概況；本人行程 | 查我的授課概況，安排明天下午一小時備課 |
| 店家 | 核對門市工作與工作時間 | 本人獲授權的門市、訂單與當班摘要；本人行程 | 查我的門市營運概況，安排明天下午半小時盤點 |
| 社團幹部 | 整理活動與籌備工作 | 本人可見社團、公開活動；本人行程 | 安排明天下午一小時社團籌備 |
| 校務與課務 | 整理校園資訊及行政工作 | 公開校園資訊、既有核閱工作區；本人行程 | 查校園公告，查學校電話；安排明天下午一小時行政會議 |
| 平台營運 | 維護平台服務與處理管理工作 | 公開資訊、經正式資格驗證的管理工作區；本人行程 | 查學校資訊，查公開交流；安排明天下午半小時維護檢查 |

教師不能以學生的修課清單當授課名單，店家不能以買家的訂單當門市營收。平台營運情境不等於取得所有學校的私人資料；校園管理角色也不等於平台營運資格。提示詞、網址參數或選單選項都不會授予權限。

這次保留既有多身分使用方式：沒有從姓名、電子郵件或一句「我是老師」推定身分。一般使用者可選工作情境；只有服務端已確認的平台營運身分會使用相應的初始情境。

## 本輪修正的實際缺口

### 角色範例與工具能力一致

原本社團、校務與平台營運範例要求查公告、學校電話或公開交流，但 profile 的工具清單沒有完整開放這些既有 reader；部分已支援要求也被廣泛的工作關鍵字規則導回服務入口。

現在六個情境都能使用已接通的公開公告、活動、公開交流與學校聯絡資料。角色指引、查詢解析與執行端重用同一份完整語法，包含發布、退款、核准、傳送訊息等其他要求的子句仍會保留其原意，不會因前半句查詢成功就被略過。

校園地圖也改為六個情境共同的查詢能力。教師等角色可以直接查地點，或由本人下一堂課的教室接續查位置；前端沿用原本的地圖讀取路徑及登入、校園與失效保護。這個流程只讀本人的同步課表，不會改讀學生名單或授課課程作為定位來源。

完整的「找備課空檔」在共用意圖解析器中保留為工作安排，前端和後端都不再把它當作公開課程搜尋。真的搜尋公開開課或含有「備課」字樣的課程，仍走原本的公開課程流程。

### 工作概況與個人時間形成真正依賴

新的工作時段規劃重用既有工具：

1. 讀取同句指定的授課／門市概況，或本人可見社團。
2. 核對安排當日的本人課表及個人行程。
3. 在指定時窗內找足夠長度的未來空檔。
4. 以使用者明確說出的工作名稱準備行程卡。
5. 使用者確認後，沿用既有簽章、權限重查、版本檢查、持久去重與回執查核。

同句的工作來源在安排之前或之後都會成為相依步驟。來源沒有完整核對、門市不唯一或無法確認權限時，依賴它的安排保持未完成；公車等無關查詢仍可繼續。

`找` 只查空檔；`安排` 或 `規劃` 才準備確認卡。例如：

```text
找明天下午一小時空檔備課
查我的授課概況，安排明天下午一小時備課，查公車
查我的門市營運概況，安排明天下午半小時盤點
安排明天下午一小時備課，安排明天下午半小時批改
```

支援的明確工作名稱是備課、批改、批改作業、盤點、備料、社團籌備、行政會議、維護檢查與平台維護。日期、時窗和需要的長度必須明確；支援 15–180 分鐘。沒有把任意來源文章或模型文字當作工作名稱。

同一回覆的多張待確認卡也會占用預定時段。例如先準備 13:00–14:00 備課，再安排半小時批改時會從剩餘空檔選擇，不產生兩張重疊卡。缺少已同步課表、資料不完整或只剩過去時段時，不推論使用者有空。

新增備課行程只代表安排了備課時間。它不會宣稱已備好課、已批改作業、已完成盤點、已更改員工班表或已通知學生。

### 重新查詢保留原本角色

原本唯讀續接會重新使用預設工具範圍。現在新發出的重試憑證使用版本 4，簽章包含固定 `taskProfile`，驗證與執行均沿用原情境；原角色不允許的工具不會因重試而變成可用。

續接仍綁定原帳號、登入 session、校園、對話、任務圖與期限，並保留原來的活動／門市識別。未過期舊版憑證因無法證明原角色情境，只能重查各角色共同可用的來源；其他舊任務須重新提出查詢。新發出的憑證一律包含情境，不把舊版未綁定情境推定成學生權限。

唯讀重試只重查選取項目及必要來源，沒有把 `work-session` 加入可重試動作。它不會重送行程提議、確認先前卡片、重新下單，或延長原憑證的有效期限。

## 功能覆蓋應如何計算

`assistantTaskPlan.ts` 的能力目錄在本輪基底包含 46 個服務入口，其中 19 個有 `read` 模式、5 個有 `prepare` 模式，27 個仍只有服務入口。`prepare` 與 `read` 有重疊；這些是程式契約的分類，不能當作已部署或真實帳號驗收的完成率。

| 功能群 | Web V2 現有能力 | 需要繼續接通的部分 |
| --- | --- | --- |
| 課表、作業、教材、行事曆 | 查本人同步課表、nuni 課務與教材，安排讀書／工作行程，確認後保存並查回 | 校方選課、完整校方 LMS 寫入 |
| 教師工作 | 讀已驗證授課概況，串接本人時間安排 | 批改、成績發布、學生名單的專用 reader／writer |
| 店家工作 | 讀已授權門市概況，串接本人工作時間 | 接單、退款、菜單與營運異動的專用 writer |
| 公開校園服務 | 公告、活動、地點、公車、學校資料、公開交流與失物摘要等既有 reader | 來源尚未接通的校園仍須顯示缺漏 |
| 點餐與訂單 | 查菜單與本人訂單，準備餐點；既有訂單取餐時間可串接個人行事曆 | 正式點餐仍遵守付款與功能開關，備單不等於已付款 |
| 社團 | 本人可見社團及動態，籌備時間安排 | 發布、群發、成員管理與活動報名 |
| 宿舍、請假、圖書館 | 提供對應服務入口 | Platform 身分適配與逐項正式讀寫回執 |
| 私人訊息、通知、平台處置 | 提供對應服務入口 | 專用讀取、發送、審核與操作回執 |

後續新功能應先定義實際任務，接上既有正式服務 API，再加入同一套任務圖。每個可寫工具需要明確輸入、服務端資源授權、可核對的預覽、適當的使用者確認、持久去重與成功回執。工具名稱出現在選單，不代表功能接通；打開頁面也不能記成完成操作。

跨服務任務不具有資料庫層級的共同交易。已完成的外部操作不能因後續一步失敗而直接重做；回覆須保留每步結果，重試範圍與補救行為由工具自己的契約決定。

## 執行環境

這輪產品路徑是 Platform Web `/ai-assistant` → 同源 BFF → `assistantV2/handler.ts` → `runner.ts` → 既有 scoped adapter。桌面與手機瀏覽器共用這一路徑。

原生 iOS／Android 的 platform device assistant、學校帳號 Firebase assistant，以及 `platform-public-agent` 候選服務是不同路徑。本輪 shared parser 的正確性修復會被引用端共用，但不能據此宣稱原生 App 已有完整角色工作流程。

保留原設定：`CAMPUS_ASSISTANT_ENABLED`、`CAMPUS_ASSISTANT_V2_ENABLED` 及個人行程寫入的 `CAMPUS_ASSISTANT_V2_WRITES_ENABLED`。沒有調整正式環境設定、增加付費模型或新套件。

公開活動轉行程仍要求明確選取活動及重新核對來源。本輪沒有放寬既有活動來源保護；單純安排個人工作時間不代表活動報名。真正管理動作仍在各正式工作區核對資格後處理。
