# 校園公告與店家自有訂餐連結

- 日期：2026-10-12
- 性質：評估與設計。**不改正式程式、不部署、不寫正式資料庫。**
- 正式後端：Fly `nuni-api`，原始碼在 `deploy/nuni-api/`（基底 `Miiduoa/nuni-prod`，見 `source.json`）。點餐相關 callable 目前另外跑在 Fly Functions（`backend/functions`）。
- 點餐總開關維持關：正式環境不要設 `ONLINE_ORDERING_ENABLED`、網頁不要設 `NEXT_PUBLIC_ONLINE_ORDERING`。本文件的「去訂餐」是導到店家自己的系統，不打開我們自己的建單、付款、發號碼。
- 現況錨點：
  - 公告：Firestore `schools/{schoolId}/announcements`；靜宜登入後 `puScraper` 只從 E校園 `index_menu.php` 抽系統通知。
  - 店家：Nuni 申請／審核（`/merchant`、`nuniMerchant.ts`）；菜單與接單仍是 Firebase `cafeterias`／`menus`，每店 `orderingEnabled` + `pilotStatus`。
  - 程式裡**還沒有** `merchantMode`。下方三態是建議新增，用來接「我們接單／只導連結／只展示」。

## A. 校園公告

目標：學生能看到**自己學校所有公開公告**（全校、處室、系所），壞了就標「暫時抓不到」，不拿過期快取假裝還是新的。

### A.1 各校來源怎麼盤

每間學校分開盤，不要假設「台灣大學都同一套」。建議固定五步：

1. **RSS／Atom**：先找 `/rss.php`、`/rss.xml`、頁尾「訂閱」。靜宜教務處 `https://acd.pu.edu.tw/rss.php` 回 404，校首頁與綜合業務組 `robots.txt` 是 `Allow: /`，**目前沒找到官方 RSS**。
2. **官方 API／開放資料**：查校務資訊公開、data.gov.tw、圖書館／行事曆 API。教育部「私立大專校院課程、採購及校務資訊公告網址」只有**入口網址**，不是公告內容 API。全國電子公布欄是政府機關用，**不是大學校內公告**。
3. **公告網頁**：台灣私校常見 iWeb 路徑 `/p/403-{站台}-{分類}-1.php`（列表）與 `/p/412-{站台}-{文號}.php`（內文）。列表通常有標題、日期、點閱；內文與 PDF 在詳情頁。
4. **處室／系所子站**：從該校「行政單位」「教學單位」索引把子網域掃一遍。同一則文常會在處室站與系所站各貼一次，後面用網址正規化去重。
5. **需登入來源**：E校園、TronClass 課程公告。這是**已登入學生本人**看得到的系統／課程通知，不能拿來填全校公開牆，也不能寫進公開 Firestore。

盤點產出（每校一份設定，不當共用爬蟲）：

| 欄位 | 用途 |
| --- | --- |
| `schoolId` | 例如 `pu` |
| `sourceId` | 穩定鍵，例如 `pu-dorac-course-select` |
| `office` / `department` | 處室或系所名稱 |
| `scope` | `campus`／`office`／`department` |
| `kind` | `rss`／`api`／`opendata`／`html_list`／`login_portal` |
| `listUrl` / `itemUrlTemplate` | 列表與內文 |
| `parsers[]` | 備援解析器，有順序 |
| `robots` / `rateLimit` | 禮貌抓取 |
| `owner` | 誰負責改版 |

沒有 RSS、沒有 API 時，**HTML 列表是正式做法**，不是權宜之計。改版偵測與多解析器是必要成本。

### A.2 每校一個獨立接法

建議：`CampusAnnouncementAdapter` 介面共用，**實作與設定按學校分開**。

```
schools/{schoolId}/announcement-sources/{sourceId}   # 設定、健康狀態
schools/{schoolId}/announcements/{announcementId}    # 正規化後的公開稿
```

Nuni-api 現況沒有公告同步表；第一版可繼續寫進現有 Firestore 公開集合（App 已讀 `schools/{schoolId}/announcements`），排程跑在 Fly Functions。之後若公告要進 Nuni 租戶資料，再單獨立案，不在這份文件實作。

新增學校流程：

1. 從該校行政／教學單位頁列出子站。
2. 每個子站記入種（RSS／API／HTML）、robots、抽樣 20 則能不能穩定抽出標題＋日期＋原文網址。
3. 寫該校 adapter 與至少兩種解析器。
4. 陰影抓取一週（只寫健康日誌，不對學生顯示）。
5. 通過才打開該 `sourceId`。
6. 學生端永遠帶原文連結；抓不到就顯示該來源「暫時抓不到」。

第一間學校：**靜宜**（下面 A.7 是實際來源，不是示意）。

### A.3 改版偵測與備援

每個來源同時掛：

- 主解析器（例如 iWeb 表格：序號／標題／日期）。
- 備援（例如只掃列表裡的 `a[href*=412-]`）。
- 健康檢查：連續失敗、抽出筆數驟降、必要欄位缺失、HTML 指紋大變。
- **失敗政策：該來源標記 `unavailable`，畫面寫「暫時抓不到」，不要繼續秀上一輪成功但可能已過期的稿。** 其他還活著的來源照常顯示。全校都掛了才顯示整頁失敗。

這和現有助理邏輯一致：來源讀取失敗要當失敗，不能說「目前沒有公告」。

### A.4 排程與禮貌抓取

| 類型 | 建議頻率 | 理由 |
| --- | --- | --- |
| 全校／教務／學務／總務／資訊 | 15–30 分鐘 | 停課、選課、網路維修要快 |
| 系所子站 | 1–3 小時 | 量多、緊急程度較低 |
| 需登入的 E校園系統通知 | 學生開啟校務頁或登入後拉，不對全校排程 | 有 session、不能對全校打 |

禮貌規則：跟 robots；每站同時最多 1 連線；兩次請求至少隔 2–5 秒；`If-None-Match`／`Last-Modified`；User-Agent 寫產品名稱與聯絡信箱；附件跟原文網址走，**不要把 PDF 整包搬進我們的儲存體**（除非以後有授權）。

### A.5 去重、分類、附件、原文

- **去重鍵**：正規化後的原文 URL（去掉 `Lang`、session、廣告參數）。沒有穩定 URL 才用「來源 + 標題 + 日期」。
- **分類**：`campus`（全校）／`office`（處室）／`department`（系所）。現有 App 類別 `general | academic | event | emergency | system` 當顯示標籤，由標題關鍵字與來源對照，不確定就 `general`。
- **附件**：只存檔名 + 原文 HTTPS 連結。不重寄、不改檔名欺騙成我們的檔。
- **畫面**：標題、日期、來源單位、一兩句摘要、原文按鈕、附件連結。內文以原文為準。

### A.6 著作權

靜宜子站頁尾多為「內容著作權屬於靜宜大學」。做法：

- 我們做**索引與導流**：標題、日期、來源、短摘要、連回原文。
- 不當「轉載全文」的新聞 App，不把內文 HTML 當產品正文。
- 摘要可取列表頁已公開的標題列，或內文前 80–120 字並標「摘要，全文見原文」。
- 上線前請使用者決定：要不要向靜宜秘書處／公共事務要書面授權（見 A.9）。沒有書面授權就維持摘要 + 連回。

### A.9 需要使用者決定

1. 第一期是否只做處室、系所第二期？

## B. 店家自有訂餐連結

有的店已經有 foodpanda、Uber Eats、iCHEF 雲端餐廳、LINE 官方帳號或自架網址，不想在我們這裡再收一次單、再收一次款。我們要能**給學生看菜單**，按「去訂餐」送到店家系統；**下單與付款都在店家那邊**。

點餐總開關維持關：就算以後某店設 `native_order`，正式環境沒開 `ONLINE_ORDERING_ENABLED` 也不能建單。`showcase_link` 不走 `createOrder`。

### B.1 建議的 `merchantMode` 三態

現況只有 `orderingEnabled`（布林）+ `pilotStatus`（`inactive | pilot | live`）。布林不夠表達「有菜單、但不在我們這點」。建議：

| `merchantMode` | 學生看到什麼 | 我們接單付款？ | 與現況怎麼合 |
| --- | --- | --- | --- |
| `native_order` | 菜單 + 點餐／結帳 | 是（仍受總開關與 `orderingEnabled` 擋） | 等於今天「可接單」 |
| `showcase_link` | 菜單 + **去訂餐**（外連） | 否 | 新；`orderingEnabled` 必須是 false |
| `info_only` | 地點、時間、來源說明；菜單可有可無 | 否，也沒有去訂餐 | 接近今天靜宜櫃位靜態目錄 |

規則：

- 總開關關時：`native_order` 對學生顯示成「這間店目前不能在 App 點餐」，**不要偷偷改成外連**。
- `showcase_link` 一定要有店家確認過的 `orderingUrl`（https、無帳密、可帶來源參數）。
- `info_only` 不放去訂餐；有官網就當「店家網站」而不是訂餐。
- Nuni 申請核准只代表進駐，不自動變成 `native_order`。現有缺項 `settings`／`menu`／`online-payment` 對 `showcase_link` 改成：條款、訂餐網址、菜單來源；**不要求**我們的線上付款資格。

### B.2 讀菜單的優先順序

每店選**一種主來源**，失敗才降級；不要同時爬三個平台再合併價錢。

| 優先 | 做法 | 能拿到 | 拿不到／不要假裝有 | 何時用 |
| --- | --- | --- | --- | --- |
| 1 | 店家平台**官方** API／匯出（店家在對方後台授權給我們） | 品項、價格、圖、供應狀態（看該 API 契約） | 未經 Partner 計畫就去打內部 XHR | 連鎖、POS、外送平台有開放合作 |
| 2 | 店家自己頁的結構化資料（JSON-LD `Menu`、Open Graph） | 常有品名、有時價格／圖 | 多數台灣點餐頁沒有完整 Menu schema | 自架網站先探測 |
| 3 | 頁面解析 | 不穩定的品名／價 | 登入牆、反爬、ToS 禁止；價格與售完極易過期 | 只當探測，不當正式來源 |
| 4 | 店家上傳 CSV／後台逐筆／菜單拍照＋人工建檔 | 我們資料庫裡有的欄 | 拍照不能自動當準確價格；OCR 只輔助人工 | 校內櫃位、LINE 點餐、沒 API 的店 |

同步：主來源成功才更新菜單；失敗則標「菜單可能過期」+ 最後成功時間，**價格文案固定「以店家頁面為準」**。超過約定時數（建議 24 小時）仍失敗：菜單仍可看但加過期提示，去訂餐按鈕保留（連結還在），不要用舊價讓學生以為能在我們這結帳。

### B.3 台灣常見點餐平台（可行性，不是已接上）

| 平台 | 菜單 | 訂單／付款狀態 | 正式可行性 |
| --- | --- | --- | --- |
| Uber Eats | 有官方 Menu API（Partner，`eats.store`）。**店家／整合商要加入 Uber 計畫**，不是公開爬蟲。 | 有 Partner 訂單 API；同樣要審核。沒有授權就沒有訂單號。 | 高（若通過 Partner）；工時含對方審核等待 |
| foodpanda | 有 Partner Catalog／POS Middleware。商家後台可匯出／改菜單，那是給店家自己用。 | 訂單 webhook 給已登記的 POS plugin，不是任意 URL。 | 高（若成為登記整合）；私下打 `tw.fd-api.com` **不當產品路徑**（ToS、易改版、可能違法） |
| iCHEF 雲端餐廳 | 公開文件以發票／ERP 為主，**沒有對第三方開放的菜單讀取 API**。店家後台把 POS 商品上到雲端餐廳網址。 | 訂單在 iCHEF POS；沒有給校園 App 的訂單 webhook 文件。 | 中：請店家貼雲端餐廳網址 + CSV；API 要對方商務同意才能算 |
| 綠界／藍新「線上店面」或自架 + 金流 | 菜單在店家網站 | 金流通知是**付款**不是菜單 | 菜單走 2／4；付款見 B.5 |
| LINE 官方帳號／LIFF 點餐 | 通常無公開菜單 API | 訂單在 LINE／店家後台 | 低：請店家貼 LIFF 或完整選單網址，菜單用 CSV |
| 校內櫃位、Google 表單、IG | 無 | 無 | 只做 `info_only` 或人工 CSV |

「去訂餐」一律新開店家網址，加上我們產生的來源標記（例如 `utm_source=nuni&utm_campaign=campus&ref=nuni-{schoolId}-{cafeteriaId}`）。對方吃不吃得到看平台；我們自己記這次點擊，**不能從 utm 反推訂單號**。

### B.4 在我們平台顯示訂單號碼、明細、付款狀態

學生從我們這裡按「去訂餐」之後，會問：號碼多少、點了什麼、錢付了沒。下面五種**由強到弱**。沒接到的欄位就空著，並走第 5 種誠實文案。**不要把「去訂餐點擊」當成已下單、已付款。**

現有 `Order` 有 `id`、`items`、`total`、`status`、`paymentStatus`、`queueNumber`。那是**我們建的單**。外連單應另建 `ExternalOrderLookup`（或明確標 `fulfillment=external`），預設只有：店家、學生帳號、出發時間、目的網址、來源標記。其他欄位看下面哪一條真的接到。

#### （1）店家平台官方 API／webhook

店家在對方後台把我們登記成整合，對方把訂單與狀態推過來，或我們用授權 token 去查。

| 可能有的欄位 | 條件 |
| --- | --- |
| 對方訂單號 | 幾乎一定有 |
| 品項、數量、客製 | Partner 訂單 payload 通常有 |
| 金額 | 通常有 |
| 付款狀態 | 有的平台分開「已下單／已付款／已取消」 |
| 取餐號 | **不一定有**（外送單常常沒有櫃檯叫號） |
| 即時出餐進度 | 看平台；沒文件就當沒有 |

- 誰同意：店家（上架條款 + 在對方系統按授權）；平台（Partner 合約）；學生（隱私權告知：我們會向店家系統查你的這筆訂單以便顯示）。
- 個資：訂單含姓名、電話、地址時，我們是受店家委託處理，目的僅「讓下單學生在 App 看到自己的單」。不要做行銷、跨店推薦。金鑰只放伺服器。
- 工時：接一條成熟 Partner API 約 40–80 人時 + **對方審核（可能數週，不算在人時裡）**。每多一個平台再加 24–40。

沒有 Partner 資格時，這條就是做不到，改走（2）（3）（5）。

#### （2）下單後導回我們，網址帶訂單號

店家把 Return／Success URL 設成我們的頁，例如 `https://nuni.tw/orders/external/return?merchantOrderNo=...`。

| 可能有的欄位 | 條件 |
| --- | --- |
| 對方訂單號 | 只有店家真的會導回、而且參數名稱我們有對過 |
| 付款成功／取消 | 有些金流 ReturnURL 會帶，**瀏覽器導回能被改**，不能當已付款證明 |
| 品項、取餐號 | 通常**不會**出現在 query string |

- 誰同意：店家在自己後台設 Return URL（上架同意**不能代替**這一步）。
- 注意：參數當提示，入帳以（1）或（4）的伺服器通知為準。沒通知就只顯示「店家回傳的單號，付款請以店家為準」。
- 工時：通用回跳頁 + 每種平台參數對照 16–24 人時。很多外送 App **不會**把使用者送回我們，這條對 foodpanda／Uber App 內結帳常常無效。

#### （3）店家後台貼／匯出；學生自行貼單號或上傳收據

| 可能有的欄位 | 條件 |
| --- | --- |
| 對方訂單號 | 學生或店家有貼且格式對 |
| 品項／金額 | 店家匯出 CSV 才比較完整；學生手貼不可靠 |
| 付款狀態 | 店家標記或 CSV 欄位；截圖**不能**自動當已付款 |
| 收據圖 | 只能當申訴附件，不當結構化狀態 |

- 誰同意：店家（上傳顧客訂單）；學生（主動貼自己的單號／收據）。
- 個資：收據常有姓名、電話、卡號前六後四、餐點。圖檔加密、限本人與該店、保留期限（建議訂單結束後 90 天）、不要拿去訓練模型。OCR 僅內部輔助，畫面仍寫「等待店家確認」，**自動辨識成功不自動改 paymentStatus**。
- 工時：貼單號 8–16 人時；店家 CSV 16–24；截圖上傳＋人工對單 24–32。這是沒 API 時的正路，不是丟臉的備援。

#### （4）合作金流（綠界、藍新、LINE Pay）交易通知

前提：**付款是打給店家的特店合約**，不是打給 Nuni。金流預設通知店家網址，不是通知我們。

綠界伺服器通知（ReturnURL POST）文件可見欄位包括：`MerchantTradeNo`、`TradeNo`、`RtnCode`（1＝付款成功）、`TradeAmt`、`PaymentDate`、`PaymentType`、自訂欄。**沒有餐點明細、沒有取餐號。** 要以 CheckMacValue 驗證，並回 `1|OK`。瀏覽器導回不能當入帳。

藍新 NotifyURL：解密後有商店訂單號、金額、`TradeStatus`（0 未付、1 已付、2 失敗、3 取消、6 退款）。同樣沒有完整菜單列。查詢 API 需要店家的 HashKey／商店代號。

LINE Pay：`confirmUrl` 會帶 `orderId`、`transactionId`；真正入帳要店家伺服器用 Channel 憑證打 confirm／查詢。我們不是該筆的特店，就**沒有合法憑證可查**。

| 可能有的欄位 | 沒有的欄位 |
| --- | --- |
| 店家訂單號、金流交易號、金額、付／未付／退款、付款時間、付款方式 | 品項、客製、取餐號、外送狀態 |

要讓通知打到我們，只能：

- 店家把 Notify／Return URL 指到我們（對方後台操作）；或
- 綠界等平台商（PlatformID）模式，Nuni 當平台、店家當子特店——這是**另一份金流合約**，不是上架打勾。

誰同意：店家（特店合約 + 設 URL 或加入平台商）；金流（合約）；學生（告知付款狀態由金流／店家提供）。  
個資：交易通知可能含 email、部分卡資訊。依金流條款與個資法第 19、20 條，僅用於顯示該學生該筆狀態與對帳，目的外利用要單獨同意。  
工時：每個金流 32–48 人時（驗簽、冪等、對帳、失敗重送）。**未當平台商、店家也沒改 NotifyURL → 這條拿不到任何狀態。**

#### （5）做不到時的誠實顯示

預設文案（學生「我的訂單」若只有一次外連點擊、沒有（1）–（4）的可靠回寫）：

> 訂單在店家系統，請到店家查看。  
> 我們沒有這筆的訂單號碼、餐點明細或付款狀態。

可附：店名、出發時間、「再次開啟店家訂餐頁」。不要產生假的 queueNumber，不要把 paymentStatus 設成 paid。這和現有取餐號原則相同：號碼只認伺服器來的。

工時：8–16 人時（狀態機 + 文案 + 助理不要說「你的餐好了」）。

### B.5 上架即同意，以及為何仍要到對方系統授權

使用者認定：**店家來我們平台上架，就是同意把訂單／付款資料給我們顯示。** 這份同意要寫進進駐條款，當作我們和店家之間的契約。它**不能**代替 foodpanda、Uber、iCHEF、綠界、LINE Pay 的技術授權。

條款應明寫（上架送出前必勾，預設不勾）：

1. 店家授權我們展示店名、位置、營業時間、菜單（含價、圖、供應狀態）。
2. 若店家使用自有訂餐系統：授權我們向該系統或金流，**僅為讓該筆消費者在 Nuni 查看訂單號、明細、付款與取餐狀態**而讀取資料。
3. 價格與是否接單以店家系統為準；Nuni 不收這筆的款（`showcase_link`）。
4. 店家保證其有權把該資料提供給我們（已在對方平台允許整合，或使用對方提供的官方合作方式）。
5. 學生個資僅供履約顯示與客服爭議，不用於行銷；合作結束後依約定刪除。
6. 未完成「連結你的訂餐系統」前，學生端只會看到第（5）點的誠實文案——**同意我們去讀，不代表我們已經讀得到。**

現有 Nuni 進駐表（`/merchant`）只有營業主體與聯絡資料，核准後缺項是營運設定、菜單、線上付款。建議核准後營運設定增加一步：

**連結你的訂餐系統**（可跳過 → `info_only` 或之後再連）：

1. 選類型：Uber Eats／foodpanda／iCHEF 網址／自架網址／僅金流／先不上連結。
2. 貼訂餐網址（必填才能進入 `showcase_link`）。
3. 依類型引導：
   - **OAuth**：跳到對方授權畫面，回來存 refresh token（伺服器端）。按鈕文案「用你的 Uber Eats／foodpanda 商家帳號授權」。授權失敗就停在未連結，不假裝已同步。
   - **API 金鑰**：貼 HashKey／MerchantID／Channel secret 的**後台路徑截圖說明**，金鑰只進 secret store，畫面只顯示「已設定／未設定」。
   - **Webhook**：顯示我們核發的 Notify URL 與驗證用密鑰，逐步寫「到綠界後台 → 金流設定 → ReturnURL 貼這裡」。未完成偵測（例如還沒收到過驗證 ping）就標「等待店家在對方後台完成」。
4. 菜單來源：API 同步／CSV／稍後再傳。沒菜單也可以先 `showcase_link`（學生只看到去訂餐）。
5. 預覽「去訂餐」帶來源標記的實際 URL。

#### 為什麼上架同意之後，還是要在對方系統再按一次？

| 原因 | 說明 |
| --- | --- |
| 技術權限 | 訂單 API、金流查詢、webhook 驗簽用的 token／HashKey／Channel 憑證，發在**店家在對方的特店帳號**。我們的勾選產生不了這把鑰匙。對方只把通知打到合約裡登記的 URL。 |
| 第三方服務條款 | Uber／foodpanda／金流禁止把帳號借給未登記的整合商，也禁止爬內部 API。上架同意管的是 Nuni↔店家；管不到 Nuni↔Uber。未加入 Partner 就去拉菜單／訂單，會被斷權，也可能違約。 |
| 個資法 | 上架同意是店家對我們的意思表示。訂單當事人是學生。我們若要顯示其訂單，須有特定目的與合法基礎（履約／店家委託處理），並依第 8 條告知學生。金流或外送平台把資料給**未在合約中的第三人**，通常超出他們的告知範圍；必須由店家在對方後台把我們設成整合方或通知對象。關係企業分享都要單獨同意，何況跨公司平台。 |

因此產品要講清楚兩層：

- **層 A（上架）**：店家同意「可以給 Nuni 看、也可以給學生看自己的單」。沒這層我們不該去接。
- **層 B（連結系統）**：店家在 Uber／foodpanda／綠界「允許 Nuni 這一個客戶端」。沒這層我們**技術上讀不到**，畫面走 B.4（5）。

不要把層 A 的勾選畫成「已連結 Uber」。已連結＝OAuth 成功或已驗證 webhook／金鑰。

學生側：點「去訂餐」前短告知「接下來在店家網站點餐付款；除非店家已連結系統，否則訂單詳情要在店家那邊看。」

### B.6 店家授權同意（學生與平台）

- 學生：外連前告知離開 Nuni；若有訂單回寫，隱私權列出「店家訂餐系統、金流（名稱）」當利用對象。
- 平台：`showcase_link` 不開錢包、不開 `createOrder`。助理不准說「已經幫你點好」。
- 免責（菜單頁固定）：「價格、是否賣完、是否接單以店家訂餐頁為準。Nuni 不處理這筆的付款與退款。」

### B.7 階段與工時

| 階段 | 做什麼 | 人時 |
| --- | --- | --- |
| B0 資料模型 | `merchantMode`、`orderingUrl`、條款版本、連結狀態；總開關仍關 | 16–24 |
| B1 上架流程 | 條款勾選、連結引導、未連結時的誠實訂單頁 | 32–40 |
| B2 菜單 | CSV＋人工；過期提示；去訂餐＋來源標記 | 24–32 |
| B3 回跳＋手貼單號 | B.4（2）（3）（5） | 24–32 |
| B4 單一金流 webhook | 僅在有店家真的改 NotifyURL 或平台商合約之後 | 32–48／家 |
| B5 單一外送 Partner | 視審核；通過前不要做爬蟲版 | 40–80／家 |

建議順序：B0 → B1 → B2 → B3（5）先上。B4／B5 等第一間真實店家指出平台再做，避免先做沒人授權的 API。

### B.8 需要使用者決定

1. 沒連系統的店，能不能上架成 `showcase_link`（只有網址＋誠實訂單文案）？建議可以。
2. 第一家真實店用哪一個外部系統？沒有這答案就不要排 Uber／foodpanda 工時。
3. Nuni 要不要當綠界／藍新**平台商**（子特店）？那是金流合約，不是工程能勾過。
4. 收據截圖要不要做？做了就是個資與客服成本。
5. `info_only` 與現有靜宜櫃位靜態目錄是否合併成同一模式？建議是。
6. 條款與隱私權（`apps/web` 正式頁，不是 `docs/legal` 草稿）由誰改文、誰做法務審。
